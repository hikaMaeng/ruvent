# 아키텍처

## 1. 단일 작성자 엔진

큐, 실행, 로그의 쓰기 쪽을 **태스크 하나**가 소유한다
([`engine/mod.rs`](../crates/ruvent/src/engine/mod.rs)). 호출자는 채널로 연산을 보내고,
엔진은 쌓인 만큼 꺼내 메모리에서 적용한다.

이 모양에서 세 가지가 "구현"이 아니라 "결과"로 나온다.

| 성질 | 왜 성립하나 |
| --- | --- |
| 배타 전달 | 두 소비자가 같은 순간에 큐를 보는 일이 없다. 잠금이 중재할 대상이 없다 |
| 전역 순서 | 연산이 하나씩 적용되므로 위치 번호 하나가 로그 전체의 안전한 커서다 |
| 이벤트 하나, 워커 하나 | 메시지는 가져간 쪽이 끝내거나 돌려줄 때까지 그쪽 것이다 |

### 큐 잠금은 잠금이 아니다

[`engine/queue.rs`](../crates/ruvent/src/engine/queue.rs)가 메시지 큐의 "잠금 관리" 전부다.

* 메시지를 주는 것은 `in_flight`를 켜는 일이다.
* 돌려받는 것은 가져간 쪽이 돌려주는 일(`release`·`nack`)이다. 지연을 주면 그만큼 뒤에 보인다.
* 기한(visibility)은 **요청한 소비자에게만** 걸린다. 같은 프로세스의 워커는 걸지 않는다.

행 잠금(`FOR UPDATE SKIP LOCKED`)이 필요했던 이유는 여러 프로세스가 같은 행을 두고
다퉜기 때문이다. 다툼이 없으면 그 장치도 없다.

## 2. 시계로 도는 것이 없다

엔진 태스크는 다음 넷 중 하나가 일어날 때까지 잔다.

| 깨우는 것 | 예 |
| --- | --- |
| 연산 도착 | submit, begin, finish … |
| 저널 쓰기 완료 보고 | 다음 쓰기를 시작해도 되는지가 여기서 정해진다 |
| 실제 기한 | 지연 재시도, 요청된 visibility, 대기 한도를 둔 소비자 |
| 저널 취합 창 종료 | 아래 4절 |

뒤의 둘은 타이머 **하나**를 공유하고, 기다릴 것이 있을 때만 걸린다. 가장 이른 기한이
바뀔 때만 다시 건다. 유휴 엔진은 런타임이 재우고 OS가 깨운다.

같은 원칙이 주변에도 적용된다.

| 대상 | 폴링 대신 |
| --- | --- |
| 빈 큐의 워커 | 엔진 안에 기한 없이 주차. 메시지 도착이 깨운다 |
| 구독자 | `Notify`. append가 깨운다 |
| 보존 한도 | append 시점에 앞에서 잘라낸다. 청소 타이머 없음 |
| 중복 제거 창 | 다음 실행이 끝날 때 만료분을 버린다 |
| 저널 압축 | 쓰기가 끝날 때 쓰레기 비율을 본다 |

`Stats::wakeups`가 엔진이 깨어난 횟수다. 테스트는 서비스가 떠 있는 채로 6시간 동안
이 값이 변하지 않음을 확인한다.

## 3. 소유는 구조로, 상한은 기한으로

원본은 리스와 heartbeat로 "죽은 워커"와 "느린 워커"를 구별했다. 워커와 큐가 다른
프로세스에 있을 때 필요한 장치다.

여기서는 메시지를 가져간 태스크가 핸들러 태스크를 **직접 기다린다**
([`worker/mod.rs`](../crates/ruvent/src/worker/mod.rs)). 반환·실패·panic·초과를 그 순간에
안다. 갱신할 것도 만료될 것도 없다.

heartbeat가 원래 못 잡던 것 — 살아서 멈춰 있는 핸들러 — 은 **스텝 기한**이 잡는다.
실행당 타이머 등록 한 번이고, 실제로 초과하기 전에는 깨어나지 않는다. 초과하면
핸들러 future를 drop하고(소유한 자식 프로세스·요청이 함께 사라진다) 백오프 뒤 다시 돌린다.

| 상황 | 처리 |
| --- | --- |
| `Ok(bytes)` | `finish`: 결과 이벤트 기록 + 메시지 삭제, 한 연산 |
| `Failure::Fatal` | `finish`(실패): `.failure` 이벤트 + 삭제 |
| `Failure::Retry { after }` | `release`: `after` 뒤 재실행 |
| panic, 기한 초과 | `release`: 백오프 뒤 재실행 |
| 시도 횟수 소진 | `.failure` 기록, 메시지는 dead letter로 |

펜싱은 남는다. 실행마다 엔진이 시도 번호를 발급하고, 번호가 맞지 않는 쪽의 기록·완료는
거부된다. 기록이 아닌 부수효과 직전에는 `cx.fence()`로 확인한다.

## 4. 이벤트 하나는 워커 하나

한 이벤트가 자기 수명을 유지하면서 여러 워커에게 쓰이는 구조는 없다.

* **반응자가 둘이면 이벤트를 둘 발급한다.** 리액션 표에 큐가 둘이면
  [`State::append`](../crates/ruvent/src/engine/state.rs)가 큐마다 **별개의 일감**을 넣는다.
  식별자(`EventId::reaction(queue, fact)`)도, 실행도, 결과도 각자의 것이다.
* **같은 키의 재제출은 같은 이벤트다.** 실행 중이면 버리고(`Begin::Duplicate`), 끝난
  뒤면 저장된 결과를 다시 알린다(`Begin::Settled`). 실행에 "합류"하지 않는다.
* **결과는 하나다.** 명령을 보낸 쪽의 reply 채널로 간다.

대신 이벤트의 발급과 소비가 싸야 한다. 그래서:

| 비용 | 처리 |
| --- | --- |
| 파생 이벤트의 문자열 필드 | `Arc<str>` 공유. 복사 대신 참조 수 증가 |
| 식별자 | xxh3 128비트. 키 없는 진행 이벤트는 해시 없이 위치에서 생성 |
| 내용 지문 | xxh3 |
| 사실 기록과 다음 일감 적재 | 같은 스텝. 그 사이를 잇는 커서·재조정·리더가 없다 |

## 5. 저널: 무엇을, 언제, 어떻게

### 무엇을 — 재시작이 이어가는 데 필요한 것만

| 대상 | 디스크 | 언제까지 | 근거 |
| --- | --- | --- | --- |
| 큐 메시지 | 기록 | 끝날 때까지 | 아직 빚진 일은 이것뿐이다 |
| 실행의 시도 횟수 | 기록 | 끝날 때까지 | 프로세스를 죽이는 메시지도 횟수가 소진되어야 한다 |
| 끝난 실행의 결과 | 설정 시에만 | 중복 제거 창 | 켜면 완료 하나가 디스크 쓰기 하나가 된다 |
| 사실·결과 이벤트 | 지정한 채널만 | 메모리 보존 한도와 같음 | 기계는 이것이 필요 없다. 사실이 부른 일감은 큐에 있다 |
| 진행 이벤트 | **기록 안 함** | — | 양이 가장 많고 가치가 가장 낮으며, 재실행하면 다른 내용이다 |
| visibility, "지금 누가 실행 중" | 기록 안 함 | — | 재시작하면 안 끝난 일은 그냥 다시 빚진 일이다 |

설정으로 더 줄일 수 있다.

```rust
App::open("data/app.journal")
    .persist_events(Events::Channels(vec!["audit.".into()]))   // 이 채널의 사실만 남긴다
    .service(Service::new("preview").accept("preview.run", preview).transient())  // 이 서비스의 일감은 적지 않는다
```

### 언제 — 창이 닫힐 때, 그리고 앞선 쓰기가 끝났을 때만

기본값(`Durability::Scheduled { window }`)에서는 아무것도 디스크를 기다리지 않는다.

* 디스크와 메모리가 **처음 달라지는 순간** 창이 열린다. 유휴 중에는 창도 타이머도 없다.
* 창이 닫히면 쓴다. 단 **앞선 쓰기가 끝나 있어야 한다.** 이 판단은 시간이 아니라 상태다.

| 장치 | 무엇을 막나 | 위치 |
| --- | --- | --- |
| `flight` 하나 | 진행 중인 쓰기가 있으면 작성자에게 아무것도 넘기지 않는다 | `Core::schedule` |
| 레코드 번호 사슬 | 배치는 자기가 잇는 번호(`prev`)를 들고 온다. 저널은 다르면 **쓰지 않고 거부**한다 | `FileJournal::append` |
| 재생 시 사슬 검사 | 순서를 어긴 프레임에서 재생을 멈춘다 | `FileJournal::open` |
| 잠금 파일 | 다른 프로세스나 두 번째 엔진이 같은 저널을 여는 것 자체를 막는다 | `<path>.journal.lock` |
| 같은 `flight`를 타는 압축 | 스냅샷이 append 중인 파일을 갈아치울 수 없다 | `Core::compact` |

디스크가 느리면 쓰기가 겹치는 것이 아니라, 그동안 변화가 메모리에서 계속 상쇄·병합되어
다음 쓰기가 **더 작아진다.**

### 어떻게 — 이력이 아니라 순변화

엔진은 연산을 하나하나 적지 않는다. 쓸 때가 되면
[`State::harvest`](../crates/ruvent/src/engine/state.rs)가 "저널이 마지막으로 알던 것과
지금이 어떻게 다른가"만 뽑는다.

* 두 쓰기 사이에 들어왔다 끝난 일은 **한 바이트도 쓰지 않는다.**
* 변하지 않은 백로그는 다시 쓰지 않는다.
* 레코드는 이력이 아니라 **선언**이다: "이 메시지는 있다/없다", "이 실행은 이 상태다".
  순서대로 덮어쓰면 상태가 복원된다.

대체된 선언이 살아 있는 선언보다 충분히 많아지면(`Compaction`) 전체 스냅샷으로 접는다.
스냅샷은 같은 레코드 종류로 이루어지며, 새 파일을 쓰고 rename으로 교체한다.

### 파일 형식

```text
[len u32][crc32 u32]  [kind u8][prev u64][through u64][bincode(Vec<Record>)]
                      '---------------- crc 대상 ----------------'
```

append 전용이므로 크래시가 손상시킬 수 있는 것은 마지막 프레임뿐이고, 그 프레임은
길이나 CRC 검사에서 걸려 열 때 잘린다.

### 에폭

크래시는 이미 발행된 이벤트를 잃을 수 있다. 위치가 기억된 곳에서 이어지면 새 인스턴스가
클라이언트가 이미 본 위치를 **다른 이벤트에** 재발급한다. 그래서 위치는
`epoch << 40 | counter`이고, 에폭은 시작할 때마다 올라가며 가장 먼저 디스크에 기록된다.

## 6. 읽기 쪽

[`engine/log.rs`](../crates/ruvent/src/engine/log.rs). 전달은 인계가 아니라 **읽기**다.

* 구독은 위치 하나를 들고 앞으로 당겨 읽는다. 로그 자체가 버퍼다.
* 연결별 메일박스가 없으므로 넘칠 것이 없고, replay에서 live로 넘어가는 인계 구간도 없다.
* 느린 독자는 자기만 늦는다. 보존 한도 밖으로 밀리면 `Subscription::lagged()`가 참이 된다.
* 채널 여러 개를 구독해도 커서는 숫자 하나다.
* `audience = Worker` 이벤트는 채널 색인에 아예 들어가지 않는다.
* 로그는 개수·바이트·나이로 한정된다(`Retention`).

## 7. 게이트웨이와 전송

[`gateway/mod.rs`](../crates/ruvent/src/gateway/mod.rs). 게이트웨이는 프로토콜을 모른다.

| 호출 방식 | 대상 전송 |
| --- | --- |
| `serve(connection, identity)` | 연결이 있는 것: WebSocket, WebRTC 데이터 채널, gRPC 스트림 |
| `submit` / `poll` | 연결이 없는 것: HTTP 롱폴링, 단발 RPC |

클라이언트의 위치가 클라이언트가 든 숫자이므로 서버에 세션 상태가 필요 없고, 그래서
두 방식이 같은 게이트웨이 위에서 나란히 돈다.

어떤 action을 받는지는 정책이 아니라 **라우트 표**가 정한다. 표는 `Service::accept`
등록에서 만들어지고, 표에 없는 action은 거부된다.
