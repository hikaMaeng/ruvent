# 변이 테스트 — 2026-11-22

## 설정

| 항목 | 값 |
| --- | --- |
| 도구 | cargo-mutants 27.1.0 |
| 대상 파일 | `engine/state.rs`, `engine/queue.rs`, `engine/log.rs`, `engine/mod.rs`, `journal/file.rs` |
| 판정에 쓴 테스트 | `--lib --test runtime --test acceptance` (정적 수준 제외) |
| 속성 테스트 사례 수 | `PROPTEST_CASES=256` (평소 2,048 / `--deep` 100,000) |
| 병렬 | `--jobs 8` |
| 변이당 시간 제한 | 300초 |
| 환경 | Threadripper 3960X, Windows, rustc 1.96.0, debug 빌드 |

"시간 초과"는 변이가 테스트를 멈추게 한 경우다. 테스트가 통과하지 못했으므로 잡힌 것으로 센다.
"컴파일 불가"는 변이가 타입 검사를 통과하지 못한 경우다.

## 결과

아래 수치는 각 실행의 마지막 줄을 그대로 옮긴 것이다.

| 실행 | 원문 |
| --- | --- |
| 1차 (테스트 보강 전) | `427 mutants tested in 49m: 64 missed, 279 caught, 35 unviable, 49 timeouts` |
| 2차 (`--iterate`, 1차에서 놓친 것과 줄 번호가 바뀐 것) | `199 mutants tested in 37m: 11 missed, 139 caught, 4 unviable, 45 timeouts` |

1차에서 놓친 64건을 보고 테스트를 보강했고, 그 과정에서 실제 결함 하나(한 번의 쓰기에 같은 `Exec`가 두 번 실림)를
찾아 고쳤다. 2차에서 남은 11건 중 1건(`log.rs` `drop_through`의 `> 0` → `>= 0`)은 단위 테스트가 죽은 깨우개를
게시 전에 넣어 변이를 가리고 있었다. 게시 뒤에 넣도록 고친 테스트가 그 변이를 직접 주입했을 때 실패하는 것을
확인했다. 그 1건은 3차 전체 실행 없이 이 수동 주입으로만 확인했다.

## 남은 10건

| 위치 | 변이 | 분류 | 근거 |
| --- | --- | --- | --- |
| `engine/mod.rs` `Core::land` | `min_records / 2` → `% 2` | 동등 | 압축 판단을 매 쓰기마다 할 뿐 결과는 같다. 비용만 다르다 |
| `engine/mod.rs` `Core::serve_waiters` | `delivered > 0` → `>= 0` | 동등 | 0을 더하는 원자 연산 한 번이 늘 뿐이다 |
| `engine/log.rs` `LogIndex::missed` | `position < epoch_floor` → `<=` | 도달 불가 | 새 세대 위치는 `floor + 1`부터다. 서버가 발급하는 커서가 `floor`와 같을 수 없다 |
| `engine/log.rs` `Subscription::poll` | `channels.len() > 1` → `>= 1` | 동등 | 채널 하나의 결과는 이미 위치 순이고 `max` 이하라 정렬·자르기가 아무것도 바꾸지 않는다 |
| `engine/state.rs` `State::open_epoch` | `(epoch << 40) + 1` → `* 1` | 동등 | 첫 위치가 `floor`가 될 뿐 이전 세대 범위와 겹치지 않고 `lagged` 판정도 같다 |
| `engine/state.rs` `State::touch` | `!dirty && …` → `||` | 동등(수정 후) | 같은 키를 쓰기 대상에 한 번 더 올린다. 쓰기 루프가 이미 기록한 실행을 건너뛰도록 고친 뒤로는 기록되는 내용이 같다. `journal_lag`가 그만큼 크게 보일 수 있다 |
| `journal/file.rs` `FileJournal::open` | `NotFound` 가드 → 항상 참 | 이 플랫폼에서 미검증 | 읽기 오류를 빈 파일로 본다. Windows에서는 이어지는 쓰기 열기도 같은 이유로 실패해 결과가 같다. 유닉스의 "쓰기만 되는 파일"에서는 잘라 버릴 수 있으나 여기서 재현하지 못했다 |
| `journal/file.rs` `FileJournal::open` | `len < MAGIC.len()` → `<=` | 동등 | 정확히 헤더 길이인 파일에 같은 헤더를 다시 쓴다 |
| `journal/file.rs` `FileJournal::open` | `length < CHAIN` → `<=` | 동등 | 길이 17인 프레임은 레코드 본문이 비어 역직렬화에서 어차피 멈춘다 |
| `journal/file.rs` `FileJournal::open` | `good < bytes.len()` → `<=` | 동등 | 같은 길이로 자르고 동기화할 뿐이다 |

## 이 실행이 만든 테스트

[testing.md](../testing.md)의 표에서 "변이 테스트가 찾은 빈틈"으로 표시한 테스트와 불변식이 이 실행에서 나왔다.
대표적인 것:

* flush가 그 쓰기가 디스크에 닿기 전에 끝나지 않는다 (`a_flush_resolves_only_once_its_changes_are_on_disk`)
* 저널 쓰기 실패가 엔진을 멈춘다 (`a_failed_journal_write_stops_the_engine_and_says_why`)
* 찢어진 꼬리 뒤에 쓴 것이 다음 재시작에서 살아남는다 (`writes_after_a_torn_tail_survive_the_next_restart`)
* 새 구독이 기다리던 구독을 떼어 내지 않는다 (`a_new_reader_does_not_unhook_one_already_waiting`)
* 보존 한도가 비운 채널에서도 독자가 깨어난다 (`a_reader_is_woken_on_a_channel_retention_emptied`)
* 상태 기계 불변식: dirty 판정과 쓰기 대상의 일치, 보존 바이트, 중복 제거 표, 재시작 뒤 게시 로그
