# 개요

## 무엇인가

ruvent는 서비스 프레임워크다. 다만 서비스의 단위가 다르다.

| | 요청·응답 프레임워크 | ruvent |
| --- | --- | --- |
| 단위 | 엔드포인트 하나가 요청 하나에 답한다 | 함수 하나가 이벤트 하나에 반응하고 사실을 기록한다 |
| 흐름 | 콜스택 | 기록된 사실 → 등록된 반응 |
| 긴 작업 | 한 호출이 끝까지 붙든다 | 짧은 실행의 연쇄. 각 실행은 자기 스텝만큼만 일감을 쥔다 |
| 결과 전달 | 호출자에게 반환 | 로그에 적는다. 관심 있는 전부가 읽는다 |
| 재시도 | 호출자 책임 | 큐가 다시 준다. 중복은 실행 기록과 결정적 id가 흡수한다 |
| 팬아웃 | 호출자가 여러 번 부른다 | 반응자마다 이벤트를 따로 발급한다. 한 이벤트는 한 워커만 가져간다 |

## 무엇이 아닌가

* 독립 서버가 아니다. 프로세스 안에 들어가는 라이브러리다.
* 분산 브로커가 아니다. 엔진 하나는 프로세스 하나 안에서 돈다.
* 100% 무손실 저장소가 아니다(기본값 기준). 이벤트 큐는 입출력이 잦으므로 디스크를 기다리지
  않고, 재시작이 이어가는 데 필요한 것만 뒤따라 적는다. [제약](constraints.md) 참고.
* 이력 저장소가 아니다. 로그는 독자를 위한 한정된 버퍼다.

## 개념 여섯 개

**엔벨롭.** 모든 이벤트의 고정 계약이다. 엔진은 엔벨롭 필드만으로 라우팅·순서·중복을
판단하고 `payload`는 끝까지 불투명한 바이트로 둔다. 새 action을 추가해도 엔진은
바뀌지 않는다.

**큐 — 일감.** 메시지 하나를 정확히 한 워커에게 준다. 꺼내도 지워지지 않고, 끝내거나
돌려줄 때까지 그 워커의 것이다. 둘 이상이 처리해야 하면 메시지를 둘 발급한다.

**로그 — 관측.** append 전용이다. 읽어도 아무것도 바뀌지 않으므로 독자끼리 조율할
것이 없다. 구독은 위치 하나를 들고 앞으로 읽는 것이다.

**리액션 표.** `action → 큐 목록`. 사실이 기록되는 **같은 스텝**에서 큐마다 별개의 일감이
발급된다. 기록과 인계가 어긋날 수 없다.

**실행.** `transaction_key` 하나는 실행 하나다. 같은 키의 재제출은 같은 이벤트이므로
실행 중이면 버리고, 끝난 뒤면 저장된 결과를 다시 알리며, 내용이 다르면 충돌로 기록한다.

**펜싱.** 밀려난 시도는 그 순간부터 로그에 쓸 수 없다. 되돌릴 수 없는 부수효과
직전에는 `cx.fence()`로 지금 이 순간의 소유를 확인한다.

## 계층

```text
App / Service / Module        프레임워크 표면. 등록에서 큐·라우트·리액션을 유도
────────────────────────────
Worker            Gateway     워커 틀            전송 중립 클라이언트 경계
────────────────────────────
Engine                        단일 작성자: 큐 · 실행 · 로그 · 저널 스케줄러
────────────────────────────
Journal (plugin)              FileJournal 기본. 다른 매체는 trait 구현
```

전송(WebSocket, 롱폴링, WebRTC, gRPC …)은 `Transport` trait을 구현하는 별도 크레이트다.
