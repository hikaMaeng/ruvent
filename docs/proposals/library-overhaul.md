## 0. 원문과 원칙

### 0.1 v4를 정한 원문(2026-11-24)

> 난 내 지시가 이뤄지길 바라지 않아. 보다 비판적으로 고가용성에서의 안정성있는 이벤트 기반 서버 구축에 맞는 아키텍쳐를 만들고 싶어. 내 의견외에도 기존에 참고할 수 있는 모든 공학적인 지식으로 충분히 비판적으로 검토하고 리뷰하길 원한다.

> 하지만 굳이 그런 병렬화된 이벤트서버의 필요성을 느끼진 않아. 이벤트 특성상 차라리 여러 독립된 이벤트 서버를 부하에 맞게 운영하는게 낫기 때문이야. 이벤트 서버가 굳이 트랜젝션 단위의 부하를 책임질 이유는 없고 부하분산 자체도 독립된 이벤트서버에게 알아서 할당하는 라우터는 별도 작성이라는 입장이다

> 중요한건 하나의 단일 이벤트서버가 엄청나게 자원효율적으로 이벤트를 처리하고 발송하는 것이다
> 유일한 약점인 발송부하는 프록시를 이용해 몇개의 프록시에게만 전가하는 것으로 갈음할 수 있기 때문이다

비판 검토의 남은 지적(C2~C10, C13~C15)을 반영해 v4를 쓰겠느냐는 질문에 사용자는 "v4 작성"이라고 답했다. 그 이전 판의 원문은 9장에 있다.

### 0.2 원칙

* **서버 하나 = 장부 하나.** 등록·착수·완료·삭제·회수의 상태는 서버마다 단일 작성자 하나가 바꾼다. 서버 안에서 분할하거나 복제하지 않는다.
* **용량과 가용성은 독립 서버의 수로 얻는다.** 서버 선택은 별도 라우터가 한다(이 계획의 범위 밖). 서버끼리는 상태를 나누지 않는다. 선례는 NSQ다(9.6).
* **목표는 단일 서버의 자원 효율이다.** 같은 일을 더 적은 CPU, 메모리, 디스크 쓰기, 시스템 호출로 한다. 판단이 갈리면 이 기준으로 고른다.
* **발송 팬아웃은 프록시가 진다.** 서버의 발송 비용은 프록시 수에 비례하게 만든다.
* **서버는 업무 payload를 해석하지 않는다.** 조립, 합산, 업무 재시도 정책은 워커와 저장소의 몫이다.
* **전달 의미를 계약으로 밝힌다.**
  * 착수용 이벤트는 **최소 1회 실행**이다. lease 만료, 완료 유실, 서버 재기동은 재실행을 낳는다. 워커의 업무 멱등은 필수다.
  * 발송용 이벤트는 **1회성**이다. 보내면 끝이다.
* **평상시 건별 응답은 없다.**
  * 영속 경로는 생산자별 **누적 커밋 확인**만 비동기로 준다(2.4).
  * 휘발 방송은 응답이 전혀 없다.
* **과부하로 거절하지 않는다.**
  * 일시 몰림은 메모리와 디스크로 흡수한다.
  * 디스크 고수위에서만 생산 연결의 읽기를 늦춘다(TCP 흐름 제어).
  * 설정·형식 오류는 연결마다 종류별 첫 1회만 알린다(2.8).
* **이상 처리는 클라이언트 책임이다.** 다만 그 규칙(같은 업무는 같은 키, 재시도 예산, jitter)을 클라이언트 계약에 적는다(2.9).
* **원자성.** 한 완료와 그 후속은 한 스텝에 적용되고, 한 영속 프레임 안에서 찢어지지 않는다.
* **순서는 이벤트의 인과(후속)로 만든다.** 배정 순서는 보장하지 않는다.
* **타이머는 선언된 일회성만 쓴다.**
  * 지금 `TIMERS`에 다섯 곳이 선언돼 있다(`tests/static/architecture.rs:95`).
  * 이번 개편은 두 가지를 더한다: lease 기한 휠, 누적 확인의 시간 문턱.
  * 둘 다 가장 이른 기한에만 깨고 비면 잠든다. 폴링과 주기 타이머는 없다.

## 2. 구조

```text
 생산자 ──(라우터, 별도)──► 서버 A ◄── 워커(모든 서버에 직접)
                              │
                              └──► 프록시 몇 대 ──► 수많은 구독 클라이언트

 서버 하나의 안:
   ┌──────────────────────────────────────────────────────────────┐
   │ 코어별 I/O 스레드: 연결 소유, 본문 직접 수신, 벡터 송신       │
   │   생산 연결(데이터)   작업 연결(제어+배달)   관찰 연결          │
   └───────┬─────────────────────▲───────────────────────────────┘
           │ 쌍별 SPSC            │ 결과·송신 순번
   ┌───────▼─────────────────────┴───────────────────────────────┐
   │ 장부(단일 작성자): 메타만. 생산자 순번표, credit, lease 휠    │
   └───────┬──────────────────────────────────────────▲──────────┘
           │ 레코드 묶음                               │ 커밋 번호
   ┌───────▼──────────────────────────────────────────┴──────────┐
   │ 로그 작성기: 영속 채널 = 세그먼트 로그(본문의 유일한 사본)    │
   │ 스왑 스레드: 휘발 채널 = 메모리 + 스왑(재기동 때 버림)        │
   └──────────────────────────────────────────────────────────────┘
```

### 2.1 장부

* **이벤트당 메타만 쥔다.** 논리 id, `WorkKey`, kind, 채널, 타입, 상태, 시도 표지·lease, 재시도 수, 자격 귀속, `reply`·`correlation`, 필요 커밋 번호, 본문 위치(캐시 참조 또는 세그먼트 위치).
* **논리 id는 회수해도 바뀌지 않는다.** 시도는 착수 표지(`ClaimToken`: 세대, 순번)로 구분한다. 늦은 완료·연장은 지금처럼 표지 불일치로 막는다.
  * 지금은 회수가 id를 새로 준다(`state/mod.rs:476`). 그래서 이벤트 고유키가 회수 때마다 바뀌고, 결과 id로 중복을 막는 소비자 규칙도 깨진다(비판 C3).
  * 명시 `claim(id)`·삭제는 논리 id로 하고, 회수된 이벤트에도 그대로 닿는다.
* **검사는 메타만으로 한다.** 권한, 타입, 후속 검증, 중복, 키 지정 삭제가 모두 그렇다. 도메인 payload를 읽는 검사는 지금 코드에 없다(`state/mod.rs:329·553·605`).
* **출력은 값이다.** 인코딩은 I/O 스레드가 한다.
* **입력.** 생산자–소비자 쌍별 SPSC 링을 순환하고, 링마다 한 차례의 연산 수·시간에 상한을 둔다.
* **자료구조.** 조밀한 슬롯 배열 + `id→slot` 인덱스 + 슬롯 세대 + 채널별 대기 순서를 쓴다. 지금의 트리·맵 조합과 장부 단독으로 비교한다(M0).

### 2.2 연결과 I/O 스레드

* **코어별 I/O 스레드.** 연결 하나의 읽기·쓰기·인코딩·이름 사전은 그 연결을 소유한 스레드만 다룬다. 스레드 간 전달은 모두 쌍별 SPSC다.
* **연결 역할(비판 C7).** `Hello`에서 역할을 밝힌다. 역할마다 흐름 제어가 다르다.

  | 역할 | 들어오는 것 | 흐름 제어 |
  | --- | --- | --- |
  | 생산 | 등록, 삭제 | 디스크 고수위에서만 읽기를 늦춘다 |
  | 작업 | credit, 완료(후속 포함), 연장, 명시 착수 | **읽기를 멈추지 않는다.** 메모리가 차면 들어오는 본문을 디스크로 흘려 읽는다. 제어용 메모리·링·디스크를 예약한다 |
  | 관찰 | 구독, 해지 | 들어오는 것이 작아 해당 없음 |

  * 한 TCP 줄에서 큰 등록 뒤의 완료는 앞 바이트를 다 읽어야 보인다. 그래서 메모리가 찬 순간 해제 경로(완료)를 살리려면, 완료가 오는 연결을 멈추지 않아야 한다.
  * 생산과 작업을 함께 하는 앱은 연결을 둘 연다. 클라이언트 SDK가 감춘다.
* **수신.** 머리를 읽어 본문 길이를 알면, 할당 전에 메모리 회계를 거쳐 그 이벤트의 본문 버퍼에 소켓에서 바로 읽는다. 프레임 전체를 먼저 할당하지 않는다.
* **송신.** 연결별 머리와 공유 본문을 벡터 쓰기로 보낸다. 부분 쓰기는 남은 iovec에서 잇는다. 작은 본문의 연속 버퍼 문턱은 측정으로 정한다.
* **막힘 분리.** I/O 스레드는 입력 링이 차도 결과 링 소비, 쓰기 완료, 공간 반환을 계속 한다.
* **느린 수신자.** 연결별 미송신이 회계를 넘으면 뒤쪽을 그 연결의 디스크 큐로 내리고, 쓸 수 있을 때 올린다. 끊는 것은 연결이 실제로 닫혔을 때뿐이다(G5 대체). 프록시 연결은 수천 클라이언트의 대표이므로 이 경로가 특히 중요하다.

### 2.3 연결별 송신 순서

* **장부 순서 부류**(커밋 확인, 배달, 발송, 오류 통보)는 장부가 결정하는 순간 (연결, 연결별 송신 순번, 필요 커밋 번호)를 붙인다. 연결 소유자는 다음 순번이고, 커밋이 끝났고, 본문이 준비된 것만 내보낸다. 지금의 `route` 의미를 일반화한 것이다: 개별 게이트, 같은 연결의 선행 보류, 세대 전환 전체 게이트.
* **발송 대상은 등록을 처리한 순간의 구독 집합**이다. 장부가 구독 집합 버전을 넘긴다.
* **시험.** 지금의 A/B 순서 시험(`durability.rs:44·60`)을 다음으로 넓힌다: 장부와 연결 소유자가 다른 코어, 본문이 세그먼트에만 있는 이벤트, 세대 전환이 낀 배치.

### 2.4 생산: 생산자 순번과 누적 커밋 확인 (비판 C2, C3)

```text
Hello{역할=생산, producer_id}          → Welcome{server_id, 세대, committed = 그 생산자의 마지막 커밋 순번}
Register{seq = committed+1, …}  ─┐
Register{seq = committed+2, …}   ├─ 응답을 기다리지 않고 연속으로
Delete{seq = …}                 ─┘
                                 ← Committed{seq}   (N건마다 또는 T 뒤, 누적)
```

* **생산자 id.** 클라이언트가 정하고 보존하는 UUID다. 같은 id로 새 연결이 오면 서버가 옛 연결을 닫는다. 이것으로 옛 인스턴스의 늦은 쓰기를 막는다.
* **순번.** 생산자의 등록·삭제(생산 연결)와 완료(작업 연결의 별도 생산자 id)에 연속 순번을 붙인다.
  * 순번이 마지막 적용 순번 이하면 중복이다. 조용히 버린다.
  * 순번에 빈자리가 있으면 프로토콜 오류다. 종류별 첫 1회 통보(2.8) 뒤 연결을 닫는다.
* **누적 커밋 확인.**
  * `Committed{seq}`는 그 생산자의 seq까지 효과가 커밋됐다는 뜻이다. Strict는 fsync, Scheduled는 쓰기 반영, volatile은 장부 적용이 기준이다.
  * 수량 문턱 N과 시간 문턱 T 중 먼저 오는 것에서 보낸다. T는 미확인분이 생길 때 한 번 거는 일회성 기한이다.
  * 100만 건/초에 N = 256이면 확인 레코드는 약 3,906개/초, 건별 응답의 0.4%다(설계식).
  * 클라이언트는 확인되지 않은 구간만 보관하고, 재접속하면 `Welcome`의 `committed` 뒤만 다시 보낸다.
* **휘발 방송**(생산자 id 없는 발송용 등록)은 순번도 확인도 없다.
* **생산자 순번표(서버).** 생산자마다 (마지막 적용 순번, 마지막 커밋 순번, 살아 있는 연결)을 둔다.
  * 메모리는 생산자 수에 비례한다. 활성 생산자 10만 개 × 64 B ≈ 6.4 MB다(가정에 따른 계산).
  * v3.3의 시간 창 키 맵(100만/초·1시간 약 148 GB)과 달리 처리량과 무관하다.
  * 영속은 묶음마다 `Producer(id, seq)` 레코드 하나로 한다. 이벤트마다 기록하지 않는다. 체크포인트에 표 전체를 둔다. 그래서 재기동 뒤에도 멱등이 남는다.
* **보조: 논리 키 창.** 생산자 순번이 없는 경로(임시 HTTP 등록, 여러 독립 생산자가 같은 업무를 내는 경우)를 위한 것이다.
  * 키는 활성에서 빠지는 순간 들어간다. 그래야 오래 대기한 이벤트의 늦은 재전송도 막는다.
  * 구간 두 개를 돌리고, 장부가 연산을 처리할 때 현재 시각으로 회전한다(타이머 없음).
  * 창 W는 분 단위 설정이다(V3). SQS FIFO는 5분, NATS JetStream은 기본 2분이다.
  * 같은 키에 다른 명령이 오면 충돌이다. 그 키를 무시하지 않고 종류별 첫 1회 통보한다.
* **완료 안의 후속.** 후속 id가 활성이거나 창에 있을 때, 내용까지 같으면 그 후속만 생략한다. 내용이 다르면 완료 전체를 적용하지 않는다(충돌 통보). v3.3의 "건너뛰고 적용"은 필요한 일을 빠뜨리므로 버렸다.
* **id.** 생산자 순번이 있으면 최상위 nil id를 허용한다. 서버가 붙인 id는 커밋 확인과 함께 알릴 필요가 없다. 재전송이 순번으로 걸러지기 때문이다. 순번이 없는 경로에서는 id가 필수다.

### 2.5 소비: credit 분배 (비판 C6, C9)

```text
작업 연결: Credit{채널, 타입들, 개수 n, 바이트 b}
장부: credit 있는 워커를 고른다 → Delivery{엔벨롭 + 본문, 착수 표지, lease}   (착수와 배달이 하나)
워커: Complete{표지, 후속…, credit +1}  |  Extend{표지}  |  (아무것도 안 하면 lease 만료 → 회수)
```

* **credit은 미리 낸 수락이다.** 워커가 받을지 정한다는 원문의 의미가 그대로다. 거절은 credit을 내지 않는 것이다. 서버는 credit이 있는 워커에게 본문까지 바로 보낸다. 제안 → 수락 → 착수 왕복이 없다.
* **권한.** credit을 받을 때 그 채널의 `Claim` 권한을 검사한다. 본문은 credit을 통과한 연결에만 간다.
* **워커 고르기(V1).** 기본은 **참여 등록순으로 credit이 남은 첫 워커**다. 사용자 원문의 "순서대로"를 지키면서, credit이 없는 워커는 건너뛰므로 기다리지 않는다. 대안은 가중 순환이다.
* **credit이 0이면** 일은 대기열에서 새 credit을 기다린다. 재순회 타이머가 없다. v3의 5·10·20 ms 지수 재순회와 그 상한 문제(19번째 지연 1,310.72초)가 사라진다.
* **Offer 모드(선택).** 크기·메타를 보고 개별로 심사해야 하는 워커만 쓴다.
  * 머리 전용 `Offer` → `Accept`/`Decline`
  * 거절한 워커에게는 그 워커가 다시 `ready`를 보낼 때까지 그 이벤트를 다시 내밀지 않는다. 그래서 헛도는 일이 없다.
  * 응답 기한은 송신 대기를 포함해 잰다.
* **lease.**
  * 기한은 배달을 소켓에 다 쓴 순간부터 잰다. 휠이 기한에 (논리 id, 표지)를 장부에 내고 장부가 회수를 정한다. 외부 등록이 없어도 진행된다.
  * 회수는 같은 논리 id로 대기열에 되돌리고, 재시도 수를 올리고, 표지를 새로 준다.
  * 긴 작업은 `Extend`로 늘린다.
  * 완료가 기한 뒤에 왔어도 회수 전이면 받는다. 지금과 같고, 계약에 적는다.
* **펜싱.** 착수 표지는 단조 증가한다. 워커 `Context`에 펜싱 토큰으로 내준다. 계약에는 "비가역 부작용은 업무 키의 유일 제약이나 하류 멱등 키로 보호, 덮어쓰기형 저장은 토큰으로 펜싱"을 적는다.
* **격리(DLQ, 비판 C9).**
  * 채널 설정 `isolate_after: n`. 회수 횟수가 n을 넘으면, 장부가 그 이벤트를 원본·회수 횟수와 함께 격리 채널의 착수용 영속 이벤트로 **한 스텝에** 옮긴다.
  * SDK의 `max_retries`(워커가 살아서 판단하는 경우)보다 크게 두어, 워커가 판단에 이르지 못하는 경우의 안전망으로 쓴다.
  * 이것은 서버 정책 최소화(D11)와 정적 시험(`architecture.rs:212~221`)을 바꾸는 결정이다(V4).
* **명시 `claim(id)`·관찰 `subscribe`.** 도구용으로 남긴다. 명시 착수도 커밋 가시성을 따른다(2.7).
* **발송용 이벤트.** 등록 순간의 구독자 전원에게 간다. 대개 그 구독자는 프록시다(2.9).

### 2.6 저장 (비판 C8, C13)

**영속 채널: 세그먼트 로그가 본문의 유일한 사본이다.**
* 로그 작성기는 레코드 묶음을 현재 세그먼트 파일에 이어 쓴다. 세그먼트는 크기 S에서 넘긴다(V6).
* 장부 메타는 본문 위치(세그먼트, 오프셋, 길이)를 쥔다.
* **본문 캐시.** 막 등록된 본문은 곧 배달되므로 메모리에 둔다. 회계가 높은 문턱을 넘으면 캐시에서 놓기만 한다. **쓰기가 없다.** v3.2의 "언로드 때 스왑에 한 번 더 쓰기"가 사라진다.
* **배달.** 캐시에 없으면 I/O 스레드가 세그먼트에서 위치 읽기를 한다(페이지 캐시 경유).
* **세그먼트 삭제.**
  * 세그먼트마다 살아 있는 이벤트 수를 센다. 0이 되고 체크포인트가 그 앞을 덮으면 통째로 지운다.
  * 사용자 전제("들어차고 신속하게 비워진다")에서는 대부분의 세그먼트가 금방 빈다. 압축이 거의 필요 없다.
* **이주.** 오래 남은 소수 이벤트가 큰 세그먼트를 붙잡으면, 로그 작성기가 그 본문을 현재 세그먼트로 옮겨 쓴다. 장부가 `Relocate` 레코드로 위치를 바꾼다. 옛 세그먼트는 읽는 쪽의 pin이 모두 풀린 뒤 지운다.
* **체크포인트.** 장부 메타, 생산자 순번표, 로그 위치를 쓴다. 본문은 위치로만 가리킨다. 계기는 꼬리 레코드 수이고, 주기 타이머는 쓰지 않는다.
* **복구.** 체크포인트를 읽고 그 뒤 꼬리만 **스트리밍으로** 재생한다. 본문은 필요할 때 읽는다. 복구 메모리는 메타 크기로 한정된다.
  * 지금은 파일 전체를 메모리에 올린다(`journal/file.rs:50`).
  * 마지막 프레임의 미완성 꼬리만 잘라 낸다. **중간 손상은 멈추고 보고한다.** 지금은 중간 손상 뒤의 정상 프레임까지 잘라 낸다.
* **원자성.** 한 완료의 변화(부모 제거, 후속 등록, 생산자 순번)는 한 프레임에 든다.
* **이전.** 지금의 v1 저널은 첫 기동 때 한 번 읽어 v4 체크포인트 + 첫 세그먼트로 옮긴다. 옛 파일은 성공한 뒤에만 지운다.

**휘발 채널: 메모리 + 스왑(v3.2 2.5에 수정 셋).**
* 메모리가 높은 문턱을 넘으면 채널 대기열의 꼬리 구간을 한 스왑 페이지로 내린다. 스텁과 스왑 구간 표지만 남긴다. 스왑은 동기화하지 않고, 재기동 때 버린다.
* **수정 1.** 스텁에 권한 판정용 채널 식별자를 둔다. 삭제는 원 채널 권한도 검사하기 때문이다(`state/mod.rs:609`).
* **수정 2.** 스왑 위치에 pin과 세대를 두고, 마지막 참조 뒤에만 재사용한다.
* **수정 3.** 로드는 기존 등록을 **복원**한다. 일반 `enqueue`를 다시 부르면 새 `WorkKey`, 기록, 통지가 생긴다(`state/mod.rs:410`).

**메모리 회계.**
* 할당 전에 바이트로 센다: 본문 캐시, 장부 메타, 스텁, 링, 연결 미송신, 스왑·로그 버퍼, 생산자 순번표, 키 창.
* 상한은 "고정 회계 상한 + 대기 이벤트 수 × 메타 크기"다. **N에 독립인 상한은 아니다.** 메타 크기는 M3에서 잰다. 메타까지 내려야 하는 규모는 V7이다.
* 디스크는 마지막 한계다. 고수위에서는 생산 연결의 읽기를 늦추고, 완료·체크포인트·이주용 공간을 남긴다. 저널 쓰기 실패는 지금처럼 엔진 정지다(`engine/mod.rs:285`).

### 2.7 커밋 가시성 (비판 C10)

* 영속 채널 이벤트는 **등록이 커밋되기 전에는 어떤 경로로도 다른 연결에 보이지 않는다.** 통지, 배달, Offer, 구독 backlog, 명시 착수가 모두 그렇다.
* 슬롯에 필요 커밋 번호를 둔다. backlog는 미커밋을 거르고, 명시 착수는 커밋까지 주차한다.
* 지금은 backlog와 착수 응답이 게이트를 우회한다(1장).
* 시험: 파일 쓰기를 막고, 미커밋 id에 backlog·명시 착수·Offer·배달을 시도한다. 아무것도 보이지 않아야 한다.

### 2.8 오류 통보 (비판 C4)

* 과부하로는 거절하지 않는다.
* 권한은 가능한 한 `Hello`(역할·채널 선언) 때 검사해 알린다.
* 그 밖의 설정·형식·충돌 오류는 **(연결, 종류)마다 첫 1회만** 짧은 프레임으로 알린다. 이후는 서버 계수기로 센다. 같은 사유는 합친다.
* 중복 무시와 늦은 완료(표지 불일치)는 정상이므로 알리지 않는다.
* 근거: 정상 상태에서는 0건이라 비용이 없다. 설정 실수 때는 통보 한 번이 성공 확률 0인 재발송 루프 전체를 없앤다.

### 2.9 여러 서버, 라우터, 프록시, 클라이언트 계약

* **서버 사이 상태 공유는 없다.**
* **라우터(별도 작성)는 생산 경로에만 둔다.** 같은 생산자는 같은 서버로 보내야 생산자 순번이 이어진다. 서버를 바꾸면 그 서버에서 새 생산자 순번으로 시작한다.
* **워커는 모든 서버에 직접 붙는다**(NSQ 소비자 방식). 착수, 완료, 재접속이 같은 서버로 간다.
* **결과 경로.** 결과 B는 A를 처리한 서버에서 나온다. 완료의 후속은 그 서버에 등록되기 때문이다. 그래서 요청자는 A를 보낸 서버를 듣거나, 모든 서버를 들어야 한다. 프록시는 자기가 맡은 채널을 모든 서버에서 구독한다.
* **서버를 잃을 때(사용자 결정의 대가).**
  * 대기 이벤트는 재기동까지 기다린다. 디스크를 잃으면 잃는다.
  * 클라이언트는 시간 초과 뒤 다른 서버로 새로 보낸다. 그 서버가 재기동하면 옛 이벤트가 다시 실행될 수 있다.
  * 그래서 워커 업무 멱등이 필수다. NSQ도 같은 계약을 문서화한다.
* **클라이언트 계약.**
  * 같은 업무는 **같은 논리 키**로 다시 보내고, 시도 번호만 바꾼다.
  * 지수 백오프 + full jitter, 재시도 예산(정상 요청 대비 비율 상한)
  * 업무 결과의 기한과 등록 커밋(누적 확인)의 기한을 분리한다.
  * 최소 1회 실행, 펜싱 토큰
  * 서버 id·세대가 바뀐 `Welcome`은 재기동을 뜻한다. 그 서버에 둔 미확인분은 다시 보낸다.

## 3. 대용량 페이로드 (비판 C15)

* 큰 페이로드는 조각 시리즈로 보낸다. 조각은 순서가 없고, **여러 서버로 흩어져 도착해도 된다.** 조각 워커는 조각마다 개별 파일로 쓰고 바로 완료한다.
* **완성 판정은 저장소가 한다.** `put`은 파일 내구성이 확보된 뒤 공유 비트맵의 비트를 조건부로 세운다. 완성을 만든 호출 하나만 `sealed_now`를 받는다.
* **비트맵 분할.** 큰 시리즈(1 GiB ÷ 256 KiB = 4,096조각)는 비트맵을 블록(예: 1,024비트)으로 나눈다. 블록이 찰 때만 완성 계수를 조건부 갱신하므로, 경합이 블록 수만큼으로 준다. S3 조건부 쓰기는 객체 하나 단위이기 때문이다.
* **의무를 상태와 함께 남긴다(outbox).**
  * `SEALED + 조립 의무`를 저장소의 한 원자적 변경으로 남긴다.
  * `ASSEMBLED + 결과 발행 의무`도 한 원자적 변경으로 남긴다.
  * 독립 발행자(별도 프로세스)가 남은 의무를 읽어 결과 R을 **불변 논리 키**로 등록하고, 커밋 확인(2.4)을 받은 뒤 의무를 지운다. 알림을 놓쳐도 미완 의무를 다시 찾을 수 있다.
  * R이 두 번 등록돼도 논리 키가 같으므로, 소비자는 키로 멱등 처리한다. 논리 id가 회수로 바뀌지 않는다(2.1).
* **조립 시도.** 만료·인계·펜싱을 둔다. 임시 객체는 세대별로 정리한다.
* **저장소 계약**(v3.2 3.2 유지): `open(manifest)`, 조건부 `put`, `begin_assemble`, 상태 `OPEN → SEALED → ASSEMBLED → PUBLISHED`(또는 `ABORTED`, `FAILED`), 공개 완료 오프셋까지의 `read`, `abort`·`remove`와 세대 묘비.
* **S3 계열.** multipart part는 마지막을 빼고 최소 5 MiB, 번호는 1~10,000이다. 조각 하나를 part 하나에 대응시키지 않는다.
* **큰 결과.** 저장소에 쓰고 결과 이벤트에는 참조만 싣는다. 받는 쪽은 공개 완료 오프셋까지 자기 속도로 읽는다.
* **채널 단위 저널 제외.** `volatile_channels: [패턴]`. 영속 부모 + 휘발 후속, 휘발 부모 + 영속 후속의 결과표를 시험으로 고정한다.

## 4. 프록시

* **역할: 발송 팬아웃 계층.** 프록시는 맡은 채널을 서버마다 한 번 구독하고, 받은 엔벨롭을 자기 클라이언트들에게 나눈다. 서버의 발송 비용은 프록시 수에 비례한다.
* **느린 클라이언트는 프록시가 처리한다.** 서버는 프록시 연결 하나만 본다. 프록시 연결이 느려지면 서버는 2.2의 디스크 큐로 받아 준다.
* **프록시가 죽으면** 그 프록시로 가던 발송은 잃는다. 발송은 1회성이다. 클라이언트는 다른 프록시에 다시 붙는다.
* **원 엔벨롭 스트림.** 허브가 `Arc<Envelope>`를 나눈다.
* **요청 교환 `Proxy::exchange(event)`.**
  * 프록시는 생산자 id를 갖고 요청을 순번과 함께 등록한다. 커밋 확인으로 등록 성공을 안다.
  * 응답 대기자는 (연결 세대, 요청 논리 키)에 귀속된다. 응답, 취소, 전체 기한, 연결 상실 중 먼저 온 것으로 끝난다.
  * 기한이 지나면 같은 논리 키로 결과를 다시 조회할 수 있어야 한다.
* **허브의 기존 불변식.** 신규 join은 자기 구독 표지를 기다리고, 이미 활성인 같은 사용자의 재호출은 즉시 성공한다(`hub/channels/mod.rs:156`).
* **접두사 구독.** 정확 이름은 해시, 접두사는 `.` 경계 트라이로 찾는다. 지금 권한 패턴의 `starts_with`(`names/mod.rs:170`)와의 차이를 시험한다.

M8 장애 시험:
1. 등록 append 전, 커밋 후 확인 전, 완료 커밋 후 결과 전달 전에 서버를 죽이고 재기동한다. 확정된 생산자 순번 유실 0, 같은 생산자 순번의 이중 적용 0, 복구 시간을 본다.
2. 첫 워커가 TCP 읽기를 영구히 멈춘 상태에서 다른 워커가 대기 건을 처리하는지 본다. 생산 연결을 막아도 작업 연결의 완료가 진행되는지 본다.
3. 파일 쓰기를 막고 미커밋 id의 backlog·명시 착수·Offer·배달을 시도한다(2.7).
4. 세그먼트 이주·삭제와 배달 읽기, 휘발 스왑 슬롯 재사용과 압축을 겹친다.
5. 조각의 마지막 비트, 조립 공개, R 커밋, 의무 삭제 각각의 직전·직후에 죽인다.

## 6. 단계

각 단계는 테스트·문서·`cargo xtask verify`·커밋으로 끝내고, 측정이 있는 단계는 보고서를 남긴다.

1. **계약 시험 정의.** 이 문서의 계약과 비판 검토의 반례를 테스트 이름이 붙은 목록으로 고정한다(`docs/testing.md` 지도). 정적 시험의 변경 목록도 여기서 정한다: `TIMERS`(휠, 확인 시간 문턱), 정책 단어(격리), 단일 엔진 소유. `Err(Duplicate)`와 건별 응답을 기대하는 시험은 새 계약으로 바꿀 목록에 넣는다.
2. **공통 기준선.** 지금 코드의 TCP 경로를 열린 부하로 잰다. 고유 완료율, p99.9, 자원.
3. **식별자와 커밋 경계.** 지금의 단일 장부 위에서 한다.
   * 회수 때 논리 id를 유지한다(시도 표지 분리).
   * 커밋 가시성(2.7)
   * 연결 역할(2.2)
   * 생산자 순번 + 누적 커밋 확인 + `Welcome`의 재전송 지점(2.4), 보조 키 창
   * 후속 충돌 규칙, 오류 첫 1회 통보(2.8)
   * wire v2. **기능 비트로 협상**한다. 그래야 단계별 중간판이 섞여도 `Hello`로 구분할 수 있다.
   * M7, M8-1·3.
4. **저장.** 세그먼트 로그, 본문 캐시, 체크포인트 + 스트리밍 복구, 중간 손상 정지, 이주와 pin, v1 저널 이전. 휘발 채널 스왑과 수정 셋. 메모리 회계. M3, M5, M8-4.
5. **I/O.** 코어별 I/O 스레드, 쌍별 SPSC, 연결별 송신 순번, 벡터 쓰기, 본문 직접 수신, 작업 연결의 디스크 흘려 읽기, 느린 수신자 디스크 큐. M0, M2, M8-2.
6. **credit 분배.** Credit/Delivery, 등록순 첫 워커, Offer 모드, lease 휠과 연장, 펜싱 토큰, 격리. SDK를 credit으로 바꾼다. M1.
7. **대용량.** 조각 저장소(파일 시스템, 그다음 객체 저장소), 비트맵 분할, outbox 발행자. M4, M8-5.
8. **프록시.** 팬아웃 계층과 교환. M2(프록시 경유), M6.
9. **apibondrust**로 실제 적용 검증.

| 서버 안 파티션·복제(비판 K1·K8) | 사용자 결정: 독립 서버를 부하에 맞게 여러 대. 대가(서버 상실 시 대기 이벤트 대기·유실, 재기동 뒤 재실행)는 계약에 적는다(2.9) |
| 순차 제안 + 지수 재순회(v3) | 첫 워커가 읽지 않으면 뒤 워커가 많아도 멈춘다. 재순회는 워커 상태를 모른 채 묻는 폴링이고 상한이 없다. credit으로 대체(2.5) |
| 수신 확인 전면 제거(v3.3) | 클라이언트가 보낸 것을 언제 버려도 되는지 영원히 모른다. 누적 확인은 건별 응답의 0.4%다(2.4). 휘발 방송은 무응답 유지 |
| 재접속 때만 순번 하나 알림(비판 초안) | 연결이 살아 있는 동안 재전송 버퍼를 비울 수 없다 |
| 1시간 시간 창 키 맵을 주 멱등 수단으로(v3.3) | 메모리가 처리량 × 창에 비례(100만/초·1시간 약 148 GB). 재기동·서버 변경에 무력. 생산자 순번이 주, 분 단위 키 창은 보조 |
| 중복 후속은 건너뛰고 완료 적용(v3.3) | 내용이 다른 필요한 일을 영구히 빠뜨린다. 같은 내용만 생략, 다르면 충돌 |
| 거절 전부 생략(v3.3 E16) | 설정 실수 때 성공 확률 0인 재발송이 끝없이 이어진다. 첫 1회 통보 |
| 영속 채널도 메모리 우선 + 스왑(v3.2) | 본문이 이미 디스크에 있는데 다시 쓴다. 재기동이 전체 재적재다. 세그먼트 로그 |
| 회수 때 id 교체(지금) | 이벤트 고유키가 바뀌어 멱등과 결과 소비자 규칙이 깨진다. 시도 표지로 구분 |
| 혼합 연결 하나 + TCP 흐름 제어(v3) | 메모리가 차면 완료도 못 읽는다. 연결 역할 분리 |
| 느린 수신자 끊기(G5) | 이벤트 유실. 연결 디스크 큐 |
| 메모리 예산 초과 시 `Busy` + `Room`(v2) | 과부하 거절 없음 |
| 저널 파일을 휘발 페이징에 재사용(v3, v3.1) | 휘발 채널은 재기동 때 버리는 스왑이 맞다. 영속 채널은 세그먼트 로그가 곧 저장소다 |
| 프로세스별 조각 계수 | 다중 프로세스에서 완성을 놓친다. 저장소 공유 비트맵 |
| 서버 조인 카운터 | 서버가 업무를 해석하게 된다 |
| 끊기면 배정분 즉시 회수 | 원격 실행기 이중 실행. lease 회수 |

### 9.1 코덱스 리뷰 1회차(v1 → v2)

### 9.2 사용자 결정(v2 → v3)

> 등록 착수 완료는 하나의 쓰레드가 맞아. 그래야 원자성유지에 힘이 안들기 때문이야. 하지만 등록 후 쓰레드 통지는 별도의 쓰레드 풀이 처리하지.

> … 단일 파일핸들에 파일을 붙이는게 아니라 개별 파일 핸들을 통해 조각을 임시 저장하고 이후 병합 파일을 생성한다면 더욱 빨리 메모리를 비워줄 수 있지.

> … 이벤트서버의 메모리 제한이 가까워지면 오히려 메모리를 차지하는 이벤트를 페이지 단위로 영속화하여 언로드 했다가 다시 페이지단위로 로드하는 구조로 문제를 해결하지 이벤트 송수신 거부는 없다.

> 모든 워커서버가 거부한 경우 약간 딜레이를 줬다가 다시 순회시키는 로직이 적합하겠지. 처음엔 매우 작은 5ms정도의 딜레이로 시작해서 거부가 한바퀴돌때마다 2배씩 증가시키면 충분할거라 생각해

v4에서 남은 것: 단일 장부, 장부 밖 I/O 스레드, 조각별 파일과 병합, 과부하 거절 없음, 휘발 채널 페이징. 지수 재순회는 credit으로 대체했다(7장).

### 9.3 코덱스 리뷰 2회차(v3 → v3.1)

> 1. 이벤트 등록은 멱등을 제공해야해. 멱등의 근간은 이벤트 고유키와 행위의 조합이다. … 헌데 고성능 이벤트서버는 모든 이벤트 수신에 대해 수신완료 반송을 하지 않는다.

* 문서: [overhaul-critique.md](overhaul-critique.md). 작성자 검토와 코덱스 독립 리뷰를 합쳤다.

* 의뢰문은 사용자 결정을 포함한 모든 결정을 근거와 함께 뒤집을 수 있게 했다. 작성자 검토는 넘기지 않았다.
* 기준(사용자): "엣지케이스가 근거가 되면 안된다." 지적마다 정상 운영에서 언제 생기는지를 적었다.
* 지적 C1~C15. 사용자는 C1(복제)·C12(파티션)를 받지 않고 독립 서버·라우터 분리·프록시 팬아웃을 정했다. 나머지를 v4에 반영했다.
* 선례: NSQ. 브로커 사이 복제가 없고, 소비자가 모든 노드에 붙고, 메모리 큐가 넘치면 디스크로 넘기며, 두 번 전달될 수 있음을 계약으로 밝힌다([Design](https://nsq.io/overview/design.html), [Features & Guarantees](https://nsq.io/overview/features_and_guarantees.html)).

**v3.3의 사실 오류(1장에서 고침).**
1. "연산 하나 = 프레임 하나"가 지금의 원자성: 부정확. append 프레임 하나에 여러 호출이 든다.
2. "이벤트는 커밋 뒤에만 다른 연결에 보인다": 부정확. backlog와 착수 응답이 게이트를 우회한다.
3. "모든 호출이 `Reply`를 받고 등록은 Strict 커밋 뒤": 부정확. 생성만 하고 도달은 보장하지 않으며, 발송용은 비게이트다.
4. "같은 완료 안의 같은 id는 형식 오류": 부정확. `Duplicate`다.
5. "Strict에서 적용 뒤 커밋 전에 죽으면 상태와 키가 함께 사라진다": 부정확. 프레임이 디스크에 남은 뒤 통지 전에 죽을 수 있다.
6. "응답 제거로 연산마다 프레임·소켓 쓰기가 하나씩 준다": 근거불일치. writer가 이미 묶어 쓴다.
7. "저널 작성기를 장부 밖으로 옮긴다"가 새 변화: 근거불일치. 이미 별도 태스크다.

v4는 아직 리뷰를 받지 않았다.
