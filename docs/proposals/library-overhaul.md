## 0. 원문과 원칙

### 0.1 개편 요구

> apibond는 원래 라이브러리를 실적용하면서 일어나는 일을 검토하기 위한 프로젝트일뿐이야. 당연히 라이브러리를 전면개편하는게 더 중요하다.
> 대용량 파일 처리에 대한 의견도 부족하고 내가 제안한 기초적인 이벤트 워커 분배에 대해서도 보다 성능과 처리량, 동시성을 고려하여 설계적으로 보완점을 찾는 과정도 없었다.

분배 모델과 대용량 처리의 원문은 [apibond-on-ruvent.md](apibond-on-ruvent.md) 1장에 그대로 있다. 분배 원문의 첫 단계는 "이벤트가 왔다는 **통지**"다. 본문 전달은 착수 뒤다.

### 0.2 v3를 결정한 원문(2026-11-24)

> 등록 착수 완료는 하나의 쓰레드가 맞아. 그래야 원자성유지에 힘이 안들기 때문이야.
> 하지만 등록 후 쓰레드 통지는 별도의 쓰레드 풀이 처리하지. 그게 가장 큰 비용이 발생하는데 거기서는 문제가 없기 때문에 전체적으로는 여전히 고속일거야.

> 아무리 빠르게 몰려도 개별 이벤트를 워커가 신속하게 제거할거라서 서버 메모리는 빠르게 차지 않아. … 단일 파일핸들에 파일을 붙이는게 아니라 개별 파일 핸들을 통해 조각을 임시 저장하고 이후 병합 파일을 생성한다면 더욱 빨리 메모리를 비워줄 수 있지.

> 나는 초 고성능 이벤트 서버를 통해 이벤트가 들어차고 신속하게 비워지는걸 원해. 또한 이벤트서버의 메모리 제한이 가까워지면 오히려 메모리를 차지하는 이벤트를 페이지 단위로 영속화하여 언로드 했다가 다시 페이지단위로 로드하는 구조로 문제를 해결하지 이벤트 송수신 거부는 없다.

> 모든 워커서버가 거부한 경우 약간 딜레이를 줬다가 다시 순회시키는 로직이 적합하겠지. 처음엔 매우 작은 5ms정도의 딜레이로 시작해서 거부가 한바퀴돌때마다 2배씩 증가시키면 충분할거라 생각해

> 난 초고성능 이벤트 서버를 완성하고 거의 모든 서비스의 핵심 엔진으로 쓰려고 하고 있어.

> 저널기능을 그대로 페이징 오프로딩에 쓸지는 고민해봐야해
> 페이징은 어디까지나 실행중 메모리 활용기능이기 때문이지

> 게다가 페이징단위로 관리하는건 로딩 배치단위일뿐 실제로는 이벤트가 하나씩 등록되어야한다

### 0.3 지킬 원칙

* **이벤트 서버의 역할은 불변이다.** 등록, 발송, 착수 원자성, 완료 시 제거.
* **원자성은 한 스레드가 만든다.** 등록·착수·완료·삭제·회수의 상태는 장부 스레드 하나만 바꾼다. 분할하지 않는다.
* **이벤트 송수신 거부는 없다.**
  * 거절 응답(`Busy` 같은)으로 등록을 돌려보내지 않는다.
  * 느린 수신자를 끊어서 이벤트를 잃게 하지도 않는다.
  * 메모리 압박은 페이지 언로드로 흡수한다. 디스크 쓰기보다 빠른 유입은 TCP 흐름 제어가 자연히 늦춘다. 이것은 거절이 아니다.
  * 처리량을 계속 넘는 부하는 워커를 늘려서 푼다.
* **순서는 이벤트의 단락성(인과)으로 만든다.** 배정 순서는 보장하지 않는다.
* **이벤트 하나는 워커 하나가 가져간다.**
* **lease 회수(Q6(b)).** 끊김으로 즉시 회수하지 않고 lease로 회수한다.
* **서버 규칙은 최소로 둔다(D11).**
* **타이머는 선언된 일회성만 쓴다.**
  * 지금 `TIMERS`에 다섯 곳이 선언돼 있다: snapshot, lane lease, handshake, 프록시 인증, 재접속 back-off(`tests/static/architecture.rs:86`).
  * 이번 개편은 전달 스레드의 타이머 휠 하나를 더한다. 이 휠이 맡는 것은 재순회 지연, 제안 응답 기한, lease 기한이다.
  * 폴링과 주기 타이머는 여전히 없다. 휠은 가장 이른 기한에만 한 번 깨고, 비면 잠든다.
* **등록·착수·완료는 멱등이다(0.4).** 멱등 키는 (이벤트 고유키, 행위)다. 보장은 시간 창 안에서만 한다. 발송은 1회성이고 멱등이 없다.
* **수신 확인을 보내지 않는다(0.4).** 클라이언트는 도달 여부를 알 수 없다. 재전송, 새 키로 재발송, 이상 감지는 모두 클라이언트 몫이다.
* **이벤트 서버는 운송만 한다(0.5).** 서버 사이에 공유하는 상태를 요구하는 기능을 넣지 않는다. 그래야 클라이언트가 여러 서버에 붙거나 라우터가 여러 서버에 나눠도 그대로 동작한다. 여러 조각을 모으는 일 같은 분산 처리는 워커 구성과 공유 저장소의 몫이다(3.2). 서버 여러 대의 클러스터링은 이번 범위가 아니다.

### 0.4 멱등과 수신 확인을 결정한 원문(2026-11-24)

> 그런데 원자성과 처리 능력에 대해 기본적으로 개선하면 될거 같아.
> 1. 이벤트 등록은 멱등을 제공해야해. 멱등의 근간은 이벤트 고유키와 행위의 조합이다. 이벤트서버가 응답하지 않은 경우 클라이언트는 재전송할 수 있다. 네트웍이 늦거나 어긋나도 그럴 수 있다. 헌데 고성능 이벤트서버는 모든 이벤트 수신에 대해 수신완료 반송을 하지 않는다. 클라이언트는 근본적으로 자신의 이벤트 전송이 서버에 도달했는지 안했는지 알 방법은 없다.
> 2. 이벤트 서버 입장에서의 멱등은 롱텀으로 보장하지 않는다. 멱등을 보장하는 맵은 행위별로 존재하고 맵에 이벤트키가 존재하면 이미 일어난 일로 보고 무시한다.
> 3. 예를들어 등록용 멱등맵은 지난 1시간동안 등록에 성공한 이벤트 키를 보관하고 새로운 등록요청이 오면 맵에 있는지 확인 후 없으면 등록을 진행한다. 만약 키가 있다면 무시할 것이다.
> 4. 맵은 시간 동시성의 부하를 피하기 위해 예를들면 시간마다 새로운 맵을 만들어서 등록하고 검색은 두개까지만 한다고 치면 3시라면 3시맵과 2시맵을 검색해서 멱등을 보장하고 3시가 되는 순간 1시맵은 지우면 될 것이다. 이런식으로 처리하면 맵관리도 일정 크기 이상늘어나지 않고 멱등 보장 시간도 자연스럽게 관리할 수 있다. 물론 이건 지시가 아니라 예다.
> 5. 이벤트 발송은 약간 미묘한데 클라이언트에게 잘 도착했는지 역시 알 수 없기 때문이다. 그리고 모르는게 이 서버의 기본정책이다. 따라서 발송에 대한 멱등은 필요없다. 발송하면 했다고 인식하고 1회성으로 끝나는거지 여러번 할 가능성이 존재하지 않기 때문이다.
> 6. 하지만 등록, 착수, 완료는 멱등을 보장해야한다.
> 7. 여러 이벤트 송수신의 이상점은 클라이언트가 알아서 책임진다. 기대하던 이벤트가 안오면 새 이벤트 키로 재발송하고 또 대기하고 이상함을 감지하는 등의 모든 책임은 전부 클라이언트측에 넘긴다.

### 0.5 서버의 범위를 정한 원문(2026-11-24)

> 이를 잘 생각해보면 이벤트 서버는 그저 이벤트 운송만 담당할 뿐 아무것도 안한다는 사실을 알 수 있고 더 나아가 클라이언트가 다수의 이벤트서버와 연결되거나 라우터가 이벤트 서버 다수에게 로드밸런싱해도 무방하다는 사실을 알 수 있다.
> 이벤트서버에 어떤 워커가 어떤 구조로 붙어있나의 문제일 뿐이다.
> … 워커서버는 별개로 운영하여 각 이벤트서버에는 다른 워커서버를 붙이더라도 그렇게 수집되는 청크를 중앙저장소에 두고 이를 감시하는 별도의 프로세스가 합산을 처리한다면 또한 문제가 없을 것이다.
> 모든 것은 각 상황에 맞는 분산처리 시스템의 정도에 달린 문제다.
> 지금은 여러 이벤트 서버를 한꺼번에 클러스터링하는 구조까지는 염두하지 않지만 이런 이벤트 유통만 철저하게 커버하고 나머지를 관심사에서 제거함으로서 얻는 확장성과 고가용성은 매우 크다

## 2. 구조

v2까지는 지금 엔진 안에서 고칠 곳을 찾았다. v3는 비용이 큰 일을 모두 엔진 밖 코어별 스레드로 빼고, 장부에는 원자성에 필요한 최소 상태만 남긴다.

```text
            코어 0                 코어 1                 코어 n-1
     ┌────────────────┐     ┌────────────────┐      ┌────────────────┐
소켓►│ I/O 스레드       │     │ I/O 스레드       │  …   │ I/O 스레드       │ 연결 소유(읽기·쓰기·인코딩)
     │ 수신: 본문을 바로 │     │                │      │                │
     │  이벤트 버퍼에    │     │                │      │                │
     │ 전달: 채널 소유분 │     │                │      │                │ 순차 제안·재순회 휠
     └──┬───────▲─────┘     └──┬───────▲─────┘      └──┬───────▲─────┘
        │ 연산   │ 결과·순번       │        │                  │        │
        ▼ (쌍별 SPSC)            ▼        │                  ▼        │
     ┌────────────────────────────────────────────────────────────────┐
     │ 장부 스레드(단일 작성자): 메타만. I/O 없음. 링을 순환하며 링당 할당량 │
     └────────────────────────────────────────────────────────────────┘
        │ 저널 묶음 ▲ 커밋 번호            │ 언로드 묶음 ▲ 로드된 이벤트(하나씩 재등록)
        ▼          │                     ▼              │
     ┌──────────────────────┐     ┌────────────────────────────────────┐
     │ 저널 작성기(지금 형식) │     │ 스왑 스레드: 실행 중 메모리 기능.    │
     │ 영속·복구 전용        │     │ 재기동하면 스왑 영역을 버린다        │
     └──────────────────────┘     └────────────────────────────────────┘
```

### 2.1 장부 스레드

* **쥐는 것(이벤트당 메타).**
  * id, `WorkKey`, kind, 채널, 타입, 상태, 착수 표지·lease, 재시도 수
  * 자격 귀속(`principal`, `key`, `claim`, `delegate`), `reply`·`correlation`, 서버 전용 필드의 존재 여부
  * **본문 버퍼 참조**. 장부는 이것을 넘겨주기만 하고 읽지 않는다
* **검사.** 지금의 모든 검사(권한, 타입, 후속 검증, 중복, 키 지정 삭제, 같은 자격의 재연결 완료)는 위 메타만으로 한다. 도메인 payload를 읽어야 하는 검사는 지금 코드에 없다(리뷰 확인).
* **출력.** 장부는 결과 **값**만 낸다. 인코딩(삭제 결과 바이트 등)은 I/O 스레드가 한다.
* **입력.** 장부는 생산자–소비자 쌍별 SPSC 링을 순환한다. 링마다 한 차례 처리할 연산 수와 시간에 상한을 둔다. 그래서 완료·반환·삭제가 등록 몰림에 밀려 굶지 않는다.
* **자료구조.** 조밀한 슬롯 배열과 `id→slot` 인덱스, 슬롯 세대, 채널별 대기 순서, `WorkKey`를 분리한다. FIFO 대기 순서와 키 재사용 검사는 유지한다. 지금의 트리·맵 조합과 비교해 측정한다(M0 장부 단독).

### 2.2 코어별 I/O 스레드

* **연결 소유.** 연결 하나의 읽기·쓰기·인코딩·연결별 이름 사전은 그 연결을 소유한 스레드만 다룬다.
* **수신: 프레임 전체 할당을 없앤다.** 머리를 읽고 본문 길이를 알면, 그 이벤트의 본문 버퍼를 할당해 소켓에서 바로 읽는다(2.5). 이것이 처음이자 마지막 복사다.
* **송신.** 연결별 머리(그 연결 사전으로 인코딩)와 공유 본문 버퍼를 벡터 쓰기로 보낸다. 부분 쓰기는 남은 iovec 오프셋에서 잇는다. 작은 본문은 연속 버퍼가 빠를 수 있으므로, 크기 문턱을 측정으로 정한다.
* **코어 간 전달.** 모든 경로를 생산자–소비자 쌍별 SPSC로 둔다. 장부→I/O, I/O→장부, I/O→I/O(제안을 다른 스레드의 연결로 보낼 때) 모두 그렇다. 한 링에 여러 생산자가 쓰지 않는다.
* **막힘 분리.** I/O 스레드는 입력 링이 가득 차도 결과 링 소비, 쓰기 완료, 공간 반환은 계속 처리한다. 입력이 막히면 그 연결의 소켓 읽기만 멈춘다(TCP 흐름 제어). 장부와 I/O가 서로를 기다리는 원형 대기가 없다.

### 2.3 연결별 송신 순서

경로가 여럿(장부→연결, 장부→채널 소유자→연결)이므로 링의 FIFO만으로는 합류 순서를 정할 수 없다(리뷰 지적). 그래서 송신을 두 부류로 나눈다.

* **장부 순서 부류: 응답, 발송, 착수 결과, 회수 통지.**
  * 장부가 결정하는 순간 (연결, 연결별 송신 순번, 필요 커밋 번호)를 붙인다.
  * 연결 소유자는 **다음 순번이고, 필요 커밋이 끝났고, 본문이 준비된** 앞부분만 내보낸다. 이것으로 지금의 `route` 의미를 일반화한다.
    * 개별 게이트
    * 같은 연결의 선행 보류(뒤 송신은 앞 송신의 커밋을 기다린다)
    * 세대 전환 배치 전체 게이트
  * 게이트가 없는 송신(Strict의 착수 응답)은 필요 커밋 번호가 0이다. 그래도 순번은 지킨다.
* **발송 대상은 등록을 처리한 순간의 구독 집합**이다. 장부가 구독 집합 버전을 넘겨, 나중에 가입한 연결이 앞선 발송을 받지 않게 한다.
* **제안 부류.** 제안은 장부가 아니라 채널 소유자가 만든다. 제안은 다른 송신과 순서를 맺지 않는다. 지켜야 할 조건은 하나다: **그 이벤트 등록의 공개 게이트(Strict면 등록 커밋)를 통과한 뒤에만 나간다.** 취소된 제안이 가진 순번은 명시적으로 닫는다.
* **시험.** 지금의 A/B 순서 시험(`durability.rs:33·44·60`)을 세 경우로 넓힌다: 채널 소유자와 연결 소유자가 다른 코어, A만 스왑된 이벤트, 세대 전환이 낀 배치.

### 2.4 착수 분배: 원문 모델

```text
장부: 등록 커밋 → "준비됨(WorkKey, id, 머리)"을 채널 소유 스레드로
채널 소유자: 워커 순서(참여 등록순)의 첫 워커부터
  Offer(머리: id·WorkKey·타입·크기·메타, 제안 번호)     ── 원문의 "통지". 본문 없음
    ├─ Accept(제안 번호) → 장부: 예상 (WorkKey, id)가 대기 중인지 검사 → 원자적으로 착수
    │                        → Claimed(엔벨롭 + 본문, 착수 표지)  ── 지금의 착수 응답과 같다
    ├─ Decline(제안 번호) → 다음 워커
    └─ 한 바퀴 전원 거절 → not_before = 지금 + 5 ms × 2^(바퀴−1) → 그때 첫 워커부터
```

* **통지는 머리만 싣는다.** 원문 그대로 "이벤트가 왔다"는 통지다.
  * 거절하는 워커에게 본문을 보내지 않는다.
  * 수락하면 착수 응답에 본문이 실려 오므로, 추가 왕복이 없다.
  * 본문은 `Claim` 권한을 통과한 뒤에만 나간다. 지금의 권한 경계가 그대로 유지된다.
  * 작은 본문을 통지에 함께 실을지는 문턱을 측정해 정한다(E10).
* **참여.** 착수 참여(`take(channel, types, 창)`)는 인증된 세션·채널·타입에 묶는다. 엔진은 이때 `Claim` 권한을 검사한다. 관찰 `subscribe`와는 별개다.
* **제안의 식별.** 제안 하나는 (`WorkKey`, 현재 id, 참여 세대, 제안 번호)다.
  * 채널 소유자는 수락·거절·기한 만료·끊김 중 **최초 종결 하나만** 적용하고, 창을 한 번만 돌려준다.
  * 늦게 온 수락·거절은 버린다.
  * 수락을 장부에 넘긴 뒤에는 결과가 올 때까지 다음 워커로 넘기지 않는다.
  * 장부는 예상 (`WorkKey`, id)와 대기 상태를 함께 검사한다. 회수로 id가 바뀌었거나, 이미 착수·삭제됐으면 실패를 돌려준다.
  * 워커는 성공 표지를 받은 뒤에만 실행한다.
* **무효화.** 삭제, 명시 `claim`, 회수가 생기면 장부가 채널 소유자에게 무효화를 보낸다. 미결 제안은 그 사실을 알고 정리된다.
* **한 이벤트는 한 시점에 한 워커에게만 제안된다.** 그래서 여러 워커가 같은 이벤트를 다투는 낭비가 없다.
* **묶음 제안.** 같은 워커에게 가는 여러 **독립 이벤트**의 제안을 한 프레임에 담고, 응답도 배열로 받는다. 이벤트별 결정과 첫 워커 우선권은 그대로다. 깨우기·머리·시스템 호출 비용을 여러 이벤트가 나눈다.
* **워커별 전달 창.**
  * 창은 한 워커에게 나가 있는 미결 제안 수(응답 전)의 상한이다. 참여할 때 알린다.
  * 창이 차 있으면 그 워커 차례에서 기다린다. 거절이 아니다.
  * 단계는 네 가지다: 창 대기, 송신 대기, 응답 대기, 착수 결과 대기. 응답 기한은 **Offer를 소켓에 다 쓴 순간**부터 잰다. 송신이 정체된 동안에는 기한이 흐르지 않는다.
  * 워커는 수락하기 전에 자기 실행 허가를 확보하고, 착수가 실패하면 반환한다. 실행 동시성은 워커가 관리한다.
  * 한 워커가 여러 채널에 참여하면, 창은 기본적으로 (연결, 채널)별이다. 공유 창 이름을 주면 여럿이 하나를 나눈다.
  * **처리량 경계(설계식, 실측 아님).** 모든 이벤트가 첫 워커를 거치므로, 첫 워커 창 W₁과 응답 시간 T₁이면 첫 제안 통과율은 대략 W₁/T₁ 이하다. 묶음 제안과 충분한 창이 이 경계를 올린다. M1에서 잰다.
* **재순회 지연(사용자 결정).**
  * 한 바퀴 전원 거절이면 이벤트마다 단조시계 기준 `not_before`를 확정한다. 지연은 5, 10, 20 ms … 로 늘어난다.
  * `ready`·새 참여·완료는 `not_before`를 **앞당기지 않는다.** 대상 목록만 갱신한다.
  * 참여자가 0명이면 바퀴로 세지 않고 첫 참여를 기다린다.
  * 순회 중 가입한 워커는 다음 바퀴부터 순서에 들어간다. 탈퇴한 워커는 그 자리에서 건너뛴다.
  * 상한은 원문에 없다. 미결 결정이다(E3).
* **응답 기한.** 기한이 지나면 그 제안을 거절로 종결한다(E4).
* **lease 기한.** 휠이 기한에 (`WorkKey`, 토큰)을 장부에 제출하고, 실제 회수 여부는 장부가 결정한다. 외부 등록이 없어도 회수가 진행된다. Q6(b)의 의미(끊김으로 즉시 회수하지 않음)는 그대로다(E5).
* **명시 `claim`·관찰 `subscribe`.** 도구용으로 남긴다.
* **발송용 이벤트.** 등록 순간의 구독자 전원에게 간다. 본문 버퍼를 공유해 보낸다.
* **wire.** 프로토콜 버전 2(무응답과 함께 6장 3단계에서 도입)에서 착수용 `Notice`와 경쟁 착수를 `Offer`/`Accept`/`Decline`(배열 가능)으로 바꾼다. v1 연결은 지금처럼 `Hello`에 `Bye`로 답한다. "저장소 밖 사용자 없음"은 코드로 증명할 수 없는 운영 전제다. 승인 때 확인한다(E11).

### 2.5 이벤트 저장과 페이징

**두 원칙(사용자 결정, 0.2).**
* **관리 단위는 이벤트 하나다.** 등록·착수·완료·삭제는 언제나 이벤트 하나씩 장부에 들어오고 나간다. 페이지는 언로드·로드를 묶어서 하는 **I/O 묶음 단위**일 뿐이다. 이벤트의 저장 위치나 수명 단위가 아니다.
* **페이징은 실행 중 메모리 기능이다. 저널과 분리한다.**
  * 저널은 영속과 복구를 맡고, 지금 형식과 원자성(연산 하나 = 프레임 하나)을 그대로 쓴다.
  * 페이징은 스왑 영역에 쓰고, 재기동하면 스왑 영역을 통째로 버린다. 복구는 저널만으로 한다.
  * 그래서 페이징이 복구 정확성에 끼어들지 않는다. 스왑 쓰기에는 동기화도, 커밋 경계도 필요 없다.

**이벤트의 본문 버퍼.**
* 이벤트마다 자기 본문 버퍼(`Bytes`, 참조 계수)를 갖는다. 지금의 수명 관리 방식 그대로다. 송신·심사 중인 쪽이 참조를 쥐므로, 완료된 이벤트의 바이트를 다른 곳에서 덮는 일이 없다.
* **수신.** 머리를 읽어 본문 길이를 알면, 그 길이만큼 버퍼를 할당해 소켓에서 바로 읽는다. 할당 전에 메모리 회계를 거친다.
  * 프레임 전체를 먼저 할당하지 않는다.
  * 작은 이벤트가 큰 프레임을 붙잡지도 않는다.
  * 할당기는 I/O 스레드별 크기 등급 slab을 쓴다(측정으로 확인).
* **송신.** 연결별 머리와 본문 버퍼를 벡터 쓰기로 보낸다. 팬아웃 N이면 같은 버퍼를 N번 참조한다.

**언로드(스왑 아웃).**
* **시점.** 메모리 회계가 높은 문턱을 넘는 순간에 시작하고, 낮은 문턱 밑으로 내려가면 멈춘다. 주기 검사는 없다.
* **대상.** 대기 중이고, 제안 중이 아니고, 착수 중이 아닌 이벤트다. 채널 대기열의 **꼬리**부터 고른다. 꼬리는 제안 커서에서 가장 멀다. `not_before`가 먼 이벤트도 대상이 된다.
* **묶음.** 장부가 한 채널의 연속된 꼬리 구간을 골라 스왑 스레드에 넘긴다. 스왑 스레드는 그 이벤트들의 메타와 본문을 한 페이지로 직렬화해 순차로 쓴다. 동기화는 하지 않는다.
* **쓰는 동안.** 이벤트는 메모리에 그대로 살아 있다. 그사이 삭제·착수된 이벤트는 쓰기가 끝난 뒤 내리지 않고, 페이지 안의 그 항목을 죽은 것으로 표시한다.
* **쓰기가 끝나면.**
  * 장부가 이벤트들을 메모리에서 내린다.
  * 채널 대기열에는 그 자리에 **스왑 구간 표지**(페이지 번호, 개수)를 하나 남긴다. 대기 순서가 보존된다.
  * 내린 이벤트마다 **스텁**(id → 페이지 번호, `WorkKey`, 상태 비트)만 남긴다.

**스왑된 이벤트에 대한 연산(장부는 디스크를 기다리지 않는다).**
* **삭제.** 스텁을 죽은 것으로 표시하고 끝낸다. 로드할 필요가 없다.
* **중복 id 검사.** 스텁 인덱스로 바로 판정한다.
* **lease 회수.** 해당 없다. 착수 중인 이벤트는 내리지 않는다.
* **명시 `claim(id)`.**
  * 장부가 그 연산을 **주차**하고 페이지 로드를 요청한 뒤, 다른 독립 연산을 계속한다.
  * 로드가 끝나면 주차한 연산을 이어서 처리한다.
  * 같은 id의 연산은 도착 순서대로 처리한다.

**로드(스왑 인).**
* 제안 커서가 스왑 구간 표지에 닿기 전에 미리 읽는다. 거리는 채널별 실제 제안 속도와 읽기 지연으로 잡는다.
* 스왑 스레드는 페이지 하나를 읽어 장부에 넘긴다. 장부는 이벤트를 **하나씩 다시 등록 상태로** 넣는다. 죽은 항목은 건너뛰고, 순서는 표지 자리 그대로다.
* 다 읽은 페이지의 스왑 공간은 바로 돌려준다. 스왑 영역은 고정 크기 슬롯의 파일이고, 빈 슬롯 목록으로 다시 쓴다. 페이지보다 큰 본문은 연속 슬롯 여러 개를 쓴다.
* 같은 페이지를 기다리는 요청은 읽기 하나로 합친다.

**저널과의 관계.**
* 영속 채널 이벤트는 등록할 때 지금처럼 저널에 적힌다. 언로드하면 스왑에 한 번 더 쓴다. 이 이중 쓰기는 메모리 압박 때만 생긴다.
* **저널 압축.** 압축(`rewrite`)은 살아 있는 이벤트의 본문이 필요하다. 스왑된 이벤트의 본문은 저널 작성기가 스왑 페이지에서 순차로 읽어 쓴다. 장부는 메타와 스왑 위치만 넘기므로 기다리지 않는다.
* **재기동.** 스왑 영역을 지우고 저널로 복구한다. 복구 중에 메모리가 상한에 닿으면 언로드가 같은 방식으로 작동한다.
* `volatile_channels`(3.4)는 저널에서만 빠진다. 페이징은 영속 채널과 휘발 채널에 똑같이 적용된다.

**메모리 상한.**
* 다음을 모두 **할당하기 전에** 바이트로 회계한다: 본문 버퍼, 장부 메타, 스텁, 링, 송신 중 버퍼, 스왑 쓰기·읽기 버퍼.
* 쓰기·완료·해제를 진행할 작업 공간은 따로 확보한다. 메모리가 가득 차도 비우는 일은 진행된다.
* 상한식: **고정 회계 상한 + 스왑된 이벤트 수 × 스텁 크기.** 스텁은 이벤트당 수십 바이트이고, 정확한 크기는 측정해 보고서에 적는다. 스텁까지 내려야 하는 규모(수억 건 대기)는 E6에서 판단한다.
* 마지막 상한은 디스크다.
  * 스왑 쓰기보다 빠른 유입은 입력 링과 TCP가 자연히 늦춘다.
  * 디스크가 가득 차는 것은 운영 장애다. 이때 등록은 적용되지 않는다. 알릴지는 E16을 따른다.

**느린 수신자: 끊지 않고 내린다.**
* 지금은 송신 버퍼가 차면 연결을 끊는다(G5). 이는 "송수신 거부 없음"과 충돌하므로 바꾼다.
* 연결별 미송신 목록이 메모리 회계를 넘으면, 뒤쪽 미송신분(머리와 본문)을 그 연결의 스왑 큐에 이어 적고, 쓸 수 있을 때 다시 올린다.
* 끊김은 연결이 실제로 닫혔을 때뿐이다.
* 시험(G5 대체): 한 연결이 멈춘 동안 다른 연결의 완료가 진행된다. 멈췄던 연결은 재개된 뒤 같은 순번을 빠짐없이 받는다.

**영속.**
* 저널 형식, 연산 하나 = 프레임 하나의 원자성, 시작 세대 순서(`engine/mod.rs:119`), 쓰기 실패 시 엔진 정지를 그대로 둔다.
* Strict의 공개 게이트는 2.3의 커밋 번호로 표현한다. 저널 작성기를 장부 밖 스레드로 옮기는 것은 그대로 할 수 있다. 장부는 묶음을 넘기고 커밋 번호를 받는다.
* 저널 형식을 최적화하는 일(본문을 다시 쓰는 압축을 줄이는 것 등)은 이 개편과 별개로, 측정(M5) 뒤에 판단한다.
* 운영 snapshot은 발송·감사 수집용이며 재생하지 않는다. 복구 경로와 섞지 않는다(`snapshot/mod.rs:107`).

### 2.6 멱등과 수신 확인 없음

**원칙(사용자 결정, 0.4).**
* 멱등 키는 (이벤트 고유키, 행위)다. 키가 이미 있으면 "이미 일어난 일"로 보고 조용히 무시한다.
* 보장은 시간 창 안에서만 한다.
* 서버는 수신 확인을 보내지 않는다. 발송은 1회성이다.

**행위별 보장 방법.**

| 행위 | 멱등 키 | 중복 판정 | 근거 |
| --- | --- | --- | --- |
| 등록(착수용·발송용·후속) | 이벤트 id | 활성 id 인덱스(스텁 포함) → 최근 키 맵 | 이 맵이 없으면 끝난 이벤트가 재전송으로 되살아난다. 발송용은 지금 아무 보호도 없다(1장) |
| 착수 | id | **상태 기계**: 이미 착수 중이거나 id가 없으면 무시 | 회수는 새 id를 준다(`state/mod.rs:477`). 그래서 옛 id의 늦은 착수가 새 차례에 닿지 않는다 |
| 완료 | id(+착수 표지) | **상태 기계**: id가 없으면 무시 | 부모가 이미 사라졌으므로 후속이 두 번 등록되지 않는다 |
| 삭제 | 삭제 요청의 `tag` | 최근 키 맵 | 원문 목록에는 없다. 그러나 지금은 중복 삭제가 반대되는 결과 이벤트를 하나 더 낸다(1장) |
| 발송·통지·제안·착수 응답 | 없음 | 없음 | 1회성(원문 5) |

* **착수·완료에 별도 맵이 필요 없는 이유.** 상태 기계는 "활성에서 빠진 id가 창 안에서 다시 활성이 되지 않는다"는 조건에서 이미 멱등이다. 그 조건을 만드는 것이 등록 쪽 최근 키 맵이다. 원문 2의 "행위별 맵"을 글자 그대로 두면 착수·완료마다 조회·삽입이 한 번씩 늘어나고 판정 결과는 같다(E14).
* **완료 안의 후속.** 후속 id가 활성이거나 최근 키 맵에 있으면 그 후속만 건너뛰고, 완료와 나머지 후속은 적용한다. 지금은 완료 전체를 `Duplicate`로 거절한다(`state/mod.rs:570`). 한 완료 안의 후속끼리 같은 id는 지금처럼 형식 오류다.

**최근 키 맵.**
* **들어가는 때: 키가 활성에서 빠지는 순간.**
  * 완료(부모 id), 삭제(지운 id와 `tag`), 회수(옛 id), 발송용 등록(활성이 되지 않으므로 즉시)
  * 대기 중인 이벤트는 이미 id 인덱스나 스텁에 있으므로 맵에 두 번 두지 않는다.
  * 창은 이벤트가 **사라진 때부터** 센다. 등록 때 넣으면, 오래 대기한 이벤트(1시에 등록, 3시 30분에 완료)의 늦은 재전송(3시 40분)이 창 밖이 되어 되살아난다.
  * 회수된 옛 id를 넣지 않으면 원래 등록의 늦은 재전송이 같은 일을 하나 더 만든다.
* **값.** 키는 클라이언트 UUID, 값은 행위 비트(등록, 삭제)다. 맵 하나로 (키, 행위) 조합을 표현한다. 조회 한 번에 두 행위를 함께 본다.
* **구간 회전(원문 4의 방식).**
  * 길이 W인 구간 두 개(현재, 직전)를 둔다. 조회는 둘 다 본다. 경계를 넘으면 직전을 버리고, 현재를 직전으로, 새 빈 맵을 현재로 둔다.
  * 보장 시간은 활성에서 빠진 뒤 W 이상, 2W 미만이다.
  * **타이머 없이 회전한다.** 장부가 연산을 처리할 때 이미 가진 현재 시각을 현재 구간의 끝과 비교하고, 넘었으면 그 자리에서 회전한다(한가했다면 두 번). 주기 타이머가 필요 없다.
  * 장부에서 회전은 포인터 교환뿐이다. 새 맵은 보조 스레드가 직전 구간의 항목 수로 크기를 잡아 미리 할당한다. 버린 맵의 해제도 보조 스레드가 한다. 장부는 큰 메모리를 초기화하거나 해제하며 멈추지 않는다.
* **해시.** 키는 신뢰할 수 없는 클라이언트가 정한다. 시드를 무작위로 둔 해시를 쓴다.
* **서버가 만드는 id.** `fresh_id`는 지금 활성 id만 피한다(`state/mod.rs:353`). 최근 키 맵도 피하게 한다.
* **메모리(설계식, 실측 아님).**
  * 항목 하나는 키 16 B + 행위 1 B + 제어 1 B, 채움률 7/8에서 약 20.6 B다. 실제 크기는 M7에서 잰다.
  * 최고 항목 수는 **2 × 활성 이탈률 × W**다(회전 직전 직전 구간 전체 + 현재 구간).

    | 이탈률 | W | 최고 항목 수 | 최고 메모리 |
    | --- | --- | --- | --- |
    | 10만/초 | 1시간 | 7.2억 | 약 14.8 GB |
    | 100만/초 | 1시간 | 72억 | 약 148 GB |
    | 25만/초 | 10분 | 3억 | 약 6.2 GB |
    | 100만/초 | 1분 | 1.2억 | 약 2.5 GB |
    | 10만/초 | 1분 | 1,200만 | 약 0.25 GB |

  * 그래서 W는 설정값이다. 원문의 1시간은 예시이고, 최고 처리량에서는 메모리를 크게 쓴다(E12).
  * 맵도 메모리 회계(2.5)에 들어간다. 직전 구간은 더 이상 바뀌지 않으므로, 압박 때 정렬 배열로 스왑에 내리고 메모리에는 필터만 둘 수 있다. 필터에 걸린 조회는 명시 착수처럼 주차된다(E12).
* **재기동.** 최근 키 맵은 저널에 적지 않는다. 그래서 재기동 직전에 끝난 이벤트의 재전송은 재기동 뒤 다시 등록될 수 있다(E13).
* **서버가 여럿일 때(0.5).** 최근 키 맵은 서버마다 따로 있다. 서버끼리 맵을 나누지 않는다(운송만 한다).
  * 같은 키의 재전송이 **같은 서버**로 가면 멱등이 그대로 지켜진다. 라우터·클라이언트가 이벤트 키의 해시로 서버를 고르면 된다.
  * 재전송이 **다른 서버**로 가면 두 서버에 하나씩 등록될 수 있다. 이것은 클라이언트·라우터 구성의 선택이고, 서버 계약은 "그 서버 안에서 창 동안 멱등"이다.
  * 착수·완료는 그 이벤트를 제안한 서버로만 간다. 후속은 완료를 받은 서버에 등록된다. 그래서 착수·완료의 멱등은 서버가 여럿이어도 그대로다.

**수신 확인 없음.**
* **등록·완료·삭제에 응답하지 않는다.** 지금의 `Registered`, `Accepted`, `Completed`, `Deleted` 응답이 사라진다. 클라이언트는 기다리지 않고 연속으로 보낸다.
* **착수 응답은 발송이다.** 착수는 본문을 받아야 실행할 수 있으므로 `Claimed`(본문 포함)는 남는다. 이것은 이벤트를 워커에게 보내는 1회성 발송이다. 잃어버리면 lease 회수로 다른 워커에게 간다. 같은 착수 요청이 다시 와도 응답을 다시 보내지 않는다.
* **구독 backlog**도 발송이다.
* **Strict의 의미가 바뀐다.** 지금은 커밋 뒤에 응답해서 등록자가 내구성을 알 수 있다(`state/mod.rs:448`). 응답이 없으면 공개 게이트만 남는다: 이벤트는 커밋 뒤에만 다른 연결에 보인다(통지·발송·제안). 등록자는 내구성을 모른다. 원문 1과 같다.
* **id는 클라이언트가 정한다(E15).** 응답이 없으므로 서버가 붙인 id를 클라이언트가 알 수 없다. nil id 등록은 재전송 때 두 번 등록된다. 그래서 최상위 등록과 삭제 `tag`는 id 필수다. 후속의 nil id는 허용한다. 완료 자체가 상태 기계로 멱등이므로 후속이 두 번 생기지 않는다.
* **거절 통보(E16).** 권한 없음, 형식 오류, 착수 경쟁 패배, 디스크 가득 같은 거절을 알릴지는 사용자 결정이다. 중복 무시는 거절이 아니므로 어느 경우에도 알리지 않는다.
* **클라이언트 API와 시험.** 등록·완료·삭제는 보내기만 하는 함수가 된다. `Err(Duplicate)`를 기대하는 지금 시험(`requirements.rs:145·146`, `state/tests.rs:130~141`)은 "조용히 무시하고 상태가 그대로"를 확인하는 시험으로 바뀐다. 1단계 계약 시험 목록에 넣는다.

**원자성.** 판정·상태 변경·맵 삽입이 장부 스텝 하나에서 일어난다. 완료라면 부모 제거, 후속 등록, 부모 id 삽입이 같은 스텝이다. 맵은 장부만 읽고 쓰므로 잠금이 없다. Strict에서 적용 뒤 커밋 전에 죽으면 상태 변경과 맵 항목이 함께 사라진다.

**처리량 효과.** 등록·완료·삭제마다 나가던 응답 프레임이 사라진다. 그만큼 장부 출력, 결과 링, 인코딩, 소켓 쓰기가 연산마다 한 건씩 줄어든다. 클라이언트는 응답을 기다리지 않으므로 유입이 응답 지연에 묶이지 않는다. 대신 장부는 활성이 아닌 키에 대해 조회 최대 두 번, 이탈할 때 삽입 한 번을 더 한다. 순효과는 M7에서 잰다.

| --- | --- | --- | --- | --- | --- |

## 3. 대용량 페이로드

### 3.1 지금의 한계

* 등록 하나는 프레임 하나(기본 16 MiB)를 넘을 수 없다.
* 대기 중인 착수용 이벤트는 엔진 메모리에 본문째 있고, 저널에도 본문째 적힌다.
* 발송 팬아웃은 연결마다 세 번 복사한다.

### 3.2 조각 시리즈

* 큰 페이로드는 조각 시리즈로 보낸다. 조각은 순서가 없고 다른 이벤트와 섞여도 된다. 조각 이벤트도 다른 이벤트처럼 하나씩 등록되고, 몰리면 언로드된다(2.5).
* 조각 워커는 조각을 **조각마다 개별 파일로** 쓰고 바로 완료한다. 순서를 기다리지 않으므로 조각 이벤트가 받는 즉시 비워진다.
* 병합은 순번대로 한 번 읽으면서 전체 해시를 함께 계산한다.

```text
part i ─► 조각 채널 ─► 제안 ─► part 워커:
              r = 저장소.put(series, gen, i, bytes)
              if r.sealed_now: complete(part, follow_ups=[assemble(id = A(series, gen))])
              else:            complete(part)
          assemble 워커: 저장소.begin_assemble → 임시 파일에 병합·해시 → 조건부 공개(ASSEMBLED)
              complete(assemble, follow_ups=[result(id = R(series, gen), 참조)])
```

**조각 저장소 계약(공유 상태는 저장소가 갖는다).**

| 연산 | 계약 |
| --- | --- |
| `open(manifest)` | 불변 manifest(세대, 조각 수, 조각 길이, 전체 길이·해시)를 조건부 생성. 다른 manifest면 충돌. 조각이 먼저 와도 되고, 조각마다 manifest 머리를 싣는다 |
| `put(i, bytes)` | 범위·길이·내용 식별자를 검증한다. **최종 이름이 없을 때만** 공개하고, 있으면 내용을 대조한다(같으면 성공, 다르면 `Conflict`). 파일의 내구성이 확보된 **뒤에** 세대별 **공유 비트맵**에 그 비트를 조건부로 세운다. 비트맵이 완성되는 순간을 만든 호출 하나만 `sealed_now`를 받고, 그 순간 `SEALED`와 "조립 의무"를 저장소에 남긴다 |
| `begin_assemble` | `SEALED`일 때만 진행. 이미 `ASSEMBLED`면 기존 결과 참조를 돌려준다(재실행은 발행만 재개) |
| `state` | `OPEN → SEALED → ASSEMBLED → PUBLISHED`, 또는 `ABORTED`, `FAILED`. 세대 단위, 조건부 갱신 |
| `read(range)` | 생산 중에는 **공개 완료된 연속 오프셋**까지만. 진행 통지를 놓쳐도 저장소에서 그 값을 다시 조회할 수 있다 |
| `abort`, `remove` | `abort`와 병합 공개는 같은 세대 상태를 조건부로 갱신한다. 완료·중단 뒤 `put`/`read`/`remove`의 결과를 고정한다. 읽는 중인 파일은 마지막 독자 뒤 정리한다. 세대 묘비를 보존 기간 동안 둔다 |

* **공유 비트맵이 필요한 이유(리뷰 반례).** N=2에서 두 프로세스가 빈 디렉터리를 보고 0번과 1번을 각각 쓰면, 프로세스별 계수로는 둘 다 1/2를 본다. 그러면 조립을 시작할 주체가 사라진다. 비트맵의 조건부 갱신은 정확히 한 호출만 완성을 보게 한다.
* **put 공개 뒤, 비트 반영 전에 죽으면.** 그 조각은 lease로 회수되어 재실행된다. `put`이 "파일은 있고 비트는 없음"을 보고 비트를 세운다.
* **sealed_now를 받은 뒤, 완료 전에 죽으면.** 그 조각이 재실행되면 `put`이 "이미 SEALED, 조립 의무 미발행"을 알려 준다. 워커는 `assemble` 후속을 다시 붙인다. 조립 의무는 `assemble` 착수 때 저장소에서 지운다.
* **결정적 id와 회수.**
  * `assemble`과 `result`는 별도 UUID 이름공간에서 유도한다.
  * `assemble(id=A)`가 회수되면 id가 바뀌어 A가 빈다(리뷰 반례). v3.3에서는 회수된 A가 최근 키 맵에 들어가므로(2.6), 창 안에 온 늦은 조각의 `assemble(A)` 후속은 건너뛰어진다. 창 밖에서 다시 등록된 조립은 `begin_assemble`에서 `ASSEMBLED`를 보거나, 진행 중인 조립의 조건부 갱신에 막힌다. 그래서 병합 파일을 두 번 공개하지 않는다.
* **중복 후속.** 이미 있는 id의 후속은 그 후속만 건너뛰고 완료는 적용된다(2.6). 그래서 v3.2의 "`Duplicate`면 후속을 빼고 재완료" 절차가 필요 없다.
* **결과 발행.**
  * 결과 이벤트는 착수용(영속)으로 보낸다. 발송용이면 당시 구독자에게만 간다.
  * 저장소는 `PUBLISHED`와 결과 참조를 보존해서, 결과 소비자가 다시 조회할 수 있게 한다.
  * 논리 결과는 id 하나다. 소비자는 결과 id로 멱등 처리한다.
* **서버 조인 카운터는 기각한다(D11).** 공유 비트맵은 저장소의 상태이지 엔진 규칙이 아니다.
* **조각이 여러 서버로 흩어져도 된다(0.5).** 완성 판정은 저장소의 공유 비트맵이 하므로, 조각이 어느 서버로 들어와 어느 워커가 받든 결과가 같다. 한 워커가 여러 서버에 붙든, 서버마다 다른 워커가 붙어 같은 저장소에 쓰든 마찬가지다.
* **객체 저장소(S3 계열).** S3 멀티파트 part는 마지막을 빼고 최소 5 MiB, 번호는 1~10,000이다(Amazon S3 사양. 호환 저장소는 백엔드마다 시험한다). 그래서 조각 하나를 part 하나에 대응시키지 않는다. 비트맵의 조건부 갱신은 조건부 쓰기(ETag 비교)로 구현한다.
* **시험.** 같은 시리즈를 두 **프로세스**에서 동시에 쓴다. 각 단계의 직전·직후에 죽인다. 조립자를 회수한 뒤 늦은 조각을 보낸다. 상충 중복, 해시 불일치, `abort`와 병합 공개의 경합을 넣는다.

### 3.3 큰 결과를 받는 쪽으로

* 큰 결과는 저장소에 쓰고, 결과 이벤트에는 참조만 싣는다. 프록시는 공개 완료된 오프셋까지 자기 속도로 읽는다.
* 작은 실시간 스트림(토큰 SSE)은 발송에 순번을 붙이고, 받는 쪽이 정렬한다. 생산자는 응답을 기다리지 않는 연속 등록 API로 보낸다.

### 3.4 채널 단위 저널 제외

* 엔진 설정 `volatile_channels: [패턴]`. 맞는 채널의 이벤트는 저널에 적지 않는다. 페이징은 채널 종류와 무관하게 똑같이 작동한다.
* 조합별 결과표를 시험으로 고정한다.
  * durable 부모 + volatile 후속: 부모 제거만 기록된다.
  * volatile 부모 + durable 후속: 후속은 기록된다.
  * 압축: volatile 제외.

## 4. 프록시

* **원 엔벨롭 스트림.** 허브가 `Arc<Envelope>`를 준다.
* **요청 교환 `Proxy::exchange(event)` 계약.**
  1. 연결 세대의 접두사 `<프록시 id>.<세대>.` 구독 표지를 확인한다.
  2. 요청 id(UUIDv7, 재사용하지 않음)의 대기자를 설치한다.
  3. 원 요청을 `reply = <접두사><요청 id>`로 등록한다.
* **대기자 종결.** 대기자는 (세대, 요청 id)에 귀속된다. 응답, 등록 실패, 취소, 연결 상실 중 먼저 온 것으로 끝난다. 세대가 바뀌면 옛 세대 대기자는 모두 연결 상실로 끝난다. 그 요청의 응답은 새 연결로 오지 않기 때문이다.
* **허브의 기존 불변식.** **신규 join**은 자기 구독 표지를 기다린다. 이미 활성인 같은 사용자의 재호출은 즉시 성공한다(`hub/channels/mod.rs:156`). 접두사 구독은 교환에만 쓴다.
* **장부의 접두사 구독.** 정확 이름은 해시 조회, 접두사는 `.` 경계 트라이 조회다. 겹쳐 받으면 연결 단위로 한 번만 보낸다.
  * 접두사 구독 권한은 하위 채널 범위 전체에 대해 검사한다.
  * 지금 권한 패턴은 문자열 `starts_with`다(`names/mod.rs:170`). 그래서 `.` 경계 트라이와의 차이를 시험한다.
* **앱 경로.** `Server::routes(Router<Proxy>)`.

## 6. 단계

각 단계는 테스트·문서·`cargo xtask verify`·커밋으로 끝내고, 측정이 있는 단계는 보고서를 남긴다.

1. **계약 시험 정의.** 이 문서의 계약과 리뷰 반례를 테스트 이름이 붙은 시험 목록으로 고정한다(`docs/testing.md` 지도). 정적 검사(`architecture.rs`)가 지금 코드 형태로 고정한 것도 새 구조의 같은 보장으로 바꿀 목록에 넣는다. 대상은 단일 엔진 소유, 저널 작성자 위치, `TIMERS`다. `Err(Duplicate)`와 응답을 기대하는 시험도 2.6의 계약으로 바꿀 목록에 넣는다.
2. **공통 기준선.** 지금 코드와 새 코드에 공통인 것만 잰다: TCP 등록~완료, 몰림 해소, 팬아웃, Strict. 응답 없는 경로는 3단계부터, 제안 전용 지표는 그 경로가 생기는 7단계부터 잰다.
3. **멱등과 수신 확인 없음.** 최근 키 맵(구간 회전, 보조 스레드 할당·해제), 활성에서 빠질 때 삽입, 조용한 무시, 후속 건너뛰기, 삭제 `tag`, `fresh_id`의 맵 회피, 등록·완료·삭제 무응답, id 필수. wire 버전을 여기서 2로 올린다.
   * 반례 시험: 완료 뒤 등록 재전송, 회수 뒤 옛 id의 등록·착수·완료 재전송, 오래 대기한 이벤트의 완료 직후 재전송, 같은 삭제 두 번, 구간 경계에 걸친 재전송, 한가한 뒤 첫 연산의 두 번 회전, 완료 재전송(후속이 한 번만 생김). M7.
4. **장부에서 본문 분리.** 장부는 본문 버퍼 참조만 넘기고, 수신은 이벤트 버퍼로 바로 읽는다. 저널은 지금 형식 그대로다. 기존 보장 시험이 다시 통과해야 한다.
5. **연결별 송신 순번과 코어 간 전달.** I/O 스레드, 쌍별 SPSC, 두 송신 부류, 벡터 쓰기, 저널 작성기를 장부 밖 스레드로. M0(장부 단독·링·hot TCP·Strict)와 M2.
6. **페이징과 메모리 회계.** 할당 전 회계, 스왑 스레드, 꼬리 구간 언로드, 스텁·스왑 구간 표지, 주차 연산, 미리 읽기, 느린 수신자 스왑 큐(G5 대체), 압축의 스왑 읽기, `volatile_channels`.
   * 저널 형식을 바꾸지 않으므로 저널 이전 절차는 없다. 스왑 영역은 재기동 때 버린다.
   * 반례 시험: 언로드 쓰기 중 삭제·착수, 스왑된 이벤트의 삭제·중복 id·명시 착수, 로드 중 같은 id 연산, 언로드 중 압축, 스왑 중 재기동(저널로만 복구). M0(cold TCP), M3, M5.
7. **원문 분배.** 머리 통지 `Offer`/`Accept`/`Decline`, 묶음 제안, 전달 창, 타이머 휠(재순회·응답 기한·lease), 무효화, v2 wire에 제안 프레임 추가. M1.
8. **조각 시리즈와 조각 저장소**(파일 시스템, 그다음 객체 저장소). M4.
9. **프록시.** M6.
10. **apibondrust**로 실제 적용 검증.

## 7. 기각한 대안

| 대안 | 기각 이유 |
| --- | --- |
| 메모리 예산 초과 시 `Busy` + `Room`(v2) | 사용자 결정: 송수신 거부 없음. 이벤트 언로드 |
| 저널 파일을 페이징에 재사용(v3, v3.1) | 사용자 결정: 페이징은 실행 중 메모리 기능이다. 저널과 묶으면 커밋 경계·압축 위치 변경·저널 이전이 복구 정확성에 끼어든다. 스왑 영역 분리, 이중 쓰기는 압박 때만 |
| 페이지를 이벤트의 저장·수명 단위로(v3.1) | 사용자 결정: 페이지는 로딩 묶음 단위일 뿐, 이벤트는 하나씩 등록된다. 예약·채택·폐기, 세대 핸들, 페이지 압축이 모두 필요 없어진다 |
| 느린 수신자 끊기(지금의 G5) | 송수신 거부 없음과 충돌. 미송신분을 스왑 큐로 |
| payload만 언로드 | 메타 N × m이 상한을 넘는다(리뷰). 이벤트 전체(메타+본문)를 언로드하고 스텁만 남긴다 |
| 본문 실은 `Offer` | 거절자에게 본문 전송, `Claim` 권한 경계 위반(리뷰). 원문대로 머리 통지 |
| 여유(credit) 기반 서버 배정(v2) | 원문의 제안·수락·거절 의미를 바꾼다 |
| 장부 분할 | 사용자 결정: 원자성은 한 스레드 |
| `ready`로 재순회 지연을 앞당김(v3 초안 E3) | 사용자가 정한 5·10·20 ms 최소 간격을 깨뜨린다(리뷰) |
| 프로세스별 조각 계수 | 다중 프로세스에서 완성을 놓친다(리뷰 반례). 저장소 공유 비트맵 |
| 링 FIFO만으로 연결 순서 | 경로가 여럿이면 합류 순서를 정하지 못한다(리뷰). 연결별 송신 순번 |
| 서버 조인 카운터 | 서버 규칙 추가(D11) |
| 저장소 배타 생성으로 조립 선출 | 선출 직후 사망 시 결과 유실(1회차 리뷰) |
| 결과 조각을 착수용으로 받는 창 | 역순 도착 교착(1회차 리뷰) |
| 끊기면 배정분 즉시 회수 | 원격 실행기 이중 실행. Q6(b) |
| 요청마다 정확 이름 구독 | 요청당 표지 왕복과 구독 표 변경 |
| 모든 수신에 응답(지금) | 사용자 결정: 수신 확인 없음. 응답 프레임 비용과 응답 대기가 유입을 묶는다 |
| 멱등을 기한 없이 보장 | 사용자 결정: 시간 창 보장. 기한 없는 키 기억은 메모리가 끝없이 는다 |
| 등록 순간 키를 맵에 넣기 | 오래 대기한 이벤트의 늦은 재전송이 창 밖이 된다. 활성에서 빠지는 순간에 넣는다 |
| 중복 후속이면 완료 전체 거절(지금) | 원문 2의 "이미 일어난 일로 보고 무시"와 다르다. 그 후속만 건너뛴다 |
| 구간 회전용 주기 타이머 | 연산 처리 때 현재 시각으로 회전하면 된다. 주기 타이머 금지 원칙(0.3) |

## 8. 결정 필요

| # | 질문 | 권장 |
| --- | --- | --- |
| E1 | 워커 순서 | 원문대로 참여 등록순, 매 이벤트 첫 워커부터 |

| E4 | 제안 응답 기한 | 기한 초과는 거절로 종결. 기본값은 M1 뒤 결정 |
| E5 | lease 회수 | 휠이 기한을 장부에 제출하고, 장부가 회수 결정. 외부 등록 없이도 진행 |

| E7 | 성능 목표 | 2단계 기준선 뒤 수치로 정한다. 장부 메타 연산 처리량, 코어 수에 따른 확장, 메모리 상한 준수가 합격 조건 |
| E8 | 조각 채널의 기본 영속 | 영속 |
| E9 | 큰 결과의 경로 | 저장소 + 참조 이벤트 + 오프셋 읽기 |
| E10 | 통지에 작은 본문 동봉 | 머리만이 기본. 동봉 문턱은 M1·M2로 정한다 |
| E11 | v1 wire 사용자 | "저장소 밖 사용자 없음"을 운영 전제로 확인하고, v1을 거절 |
| E12 | 멱등 창 W와 맵 메모리 | W는 설정값. 기본값은 M7의 실측 항목 크기와 목표 처리량으로 정한다. 1시간이면 10만/초에서 약 14.8 GB다(2.6 표). 압박 때 직전 구간을 스왑에 내리고 필터만 남기는 것을 함께 구현 |
| E13 | 재기동 뒤 멱등 유지 | **유지하지 않는다.** 원문 2("롱텀으로 보장하지 않는다")와 7(이상은 클라이언트 책임)에 맞춘다. 유지하려면 제거·회수 프레임에 id(16 B)를 싣고 압축이 창 안의 id를 보존해야 한다. 10만/초·1시간이면 압축마다 약 5.76 GB를 더 쓴다 |
| E14 | 착수·완료의 별도 맵 | **두지 않는다.** 상태 기계 + 등록 쪽 최근 키 맵으로 판정이 같다(2.6). 원문 2를 글자 그대로 따르려면 연산마다 조회·삽입이 하나씩 는다 |
| E15 | 최상위 등록의 nil id | **금지한다.** 응답이 없으므로 서버가 붙인 id를 알 수 없고, 재전송이 두 번 등록된다. 후속의 nil id는 허용 |
| E16 | 거절 통보 | 권한 없음·형식 오류·착수 경쟁 패배·디스크 가득을 짧은 오류 프레임으로 알릴지. **권장: 알린다.** 드물고 핫 경로가 아니며, 알리지 않으면 권한 설정 오류가 조용히 묻힌다. 수신 확인이 아니라 거절 사유다. 중복 무시는 어느 경우에도 알리지 않는다 |

## 9. 리뷰와 결정의 기록

### 9.1 코덱스 리뷰 1회차(v1 → v2)

리뷰 조건: gpt-6.2-astra, effort high, `c7a137a`, 472.6초. 보고서: 로컬 `codex-review/20261123-230112-gpt-6.2-astra-high/report.json`.

지적 12건(높음 9, 중간 3)에 모두 동의했다. v3에서의 처리는 다음과 같다.
* **유지:** 결정적 id 조립 선출, 저장소 + 오프셋 읽기, 교환 계약
* **대체:** 바이트 예산 → 페이지 언로드, credit → 원문 분배
* **해결:** 분할 문제(단일 장부)

### 9.2 사용자 결정(v2 → v3)

* **"거절 폭풍"(A3)은 과장이었다.** 한 바퀴는 워커마다 한 번이다. 실제 문제는 즉시 재순회했을 때 헛도는 것뿐이었다. 지수 지연 재순회로 정했다.
* **`Busy`/`Room`은 송수신 거부라서 버렸다.** 페이지 언로드로 바꿨다.
* **방향을 바꿨다.** v2는 지금 엔진 구조 안에서 고칠 곳만 찾았다. v3는 장부와 바이트를 분리하고 코어별 스레드로 옮겼다.

| 꼬리 페이지 미정의, 페이지보다 큰 입력(중간) | 동의 | 저장 등급 분리, 가장 이른 사용 예정, extent 목록(2.5) |
| 전달 창이 첫 워커 처리량 상한을 정함(중간) | 동의(설계식) | 네 단계 구분, 기한 기산점, 묶음 제안, M1에서 W₁/T₁ 실측(2.4) |
| 진행 중 읽기·교환 대기자 수명 미정(중간) | 동의 | 공개 완료 오프셋, 완료 뒤 연산 결과 고정, 대기자 종결(3.2, 4) |
| 기준선·단계 순서로 효과와 손실 구분 불가(중간) | 동의. `FileJournal::open`의 꼬리 절단을 `journal/file.rs:47·66`에서 확인 | 공통 기준선, 어댑터 단계, 이전 절차, 정적 검사 갱신(6) |

v3의 사실 주장 가운데 다음을 고쳤다(1장).
* 현 방식이 순차 제안보다 낭비가 크다는 단정: 근거불일치. 지금 통지에는 본문이 없다.
* Strict 요약: 부정확
* 중복 id 범위: 부정확. 한 완료 안의 후속끼리도 해당한다.
* v1 거절 지점: 부정확. `Welcome`이 아니라 `Hello`에 `Bye`로 답한다.
* 타이머 "첫 대상": 부정확. 이미 다섯 곳이 있다.
* 프록시 join 불변식: 부정확. 신규 join만 해당한다.
* 복사 라인 번호

**리뷰의 원문 대비 판정**은 "설계 방향 채택, 그대로의 구현 승인은 보완 후"였다. 보완 조건 넷은 v3.1에 반영했다.
* 메타까지 페이지화
* `ready`가 최소 지연을 깨지 않음
* 다중 프로세스·회수 뒤 조립 복구
* Strict 다중 파일 커밋과 연결별 공개 순서

위 표의 반영 칸은 v3.1 기준이다. v3.2에서 2.5의 처리가 바뀐 지적: 메모리 상한(메타 두 층 대신 이벤트 전체 언로드 + 스텁, 수신은 이벤트 버퍼로 직접 읽기), 느린 수신자(디스크 큐 대신 스왑 큐), 커밋 경계(저널 분리로 해당 없음), 페이지 재사용(이벤트별 버퍼 참조 계수로 해당 없음), 꼬리 페이지·큰 입력(스왑 페이지는 한 채널의 꼬리 구간, 큰 본문은 연속 슬롯), 기준선·단계(저널 이전 절차 불필요).

### 9.4 사용자 결정(v3.1 → v3.2)

* **페이징을 저널과 분리했다.** 페이징은 실행 중 메모리 기능이고, 저널은 영속·복구다. 스왑 영역은 재기동 때 버린다. 저널 형식과 원자성은 지금 그대로다.
* **관리 단위를 이벤트 하나로 되돌렸다.** 페이지는 언로드·로드의 묶음일 뿐이다. 로드된 이벤트는 하나씩 다시 장부에 들어간다.
* 결과로 v3.1의 다음 장치가 사라졌다: 페이지 예약·채택·폐기, 세대 핸들, 페이지 압축과 조건부 위치 변경, 데이터 페이지와 메타 로그의 커밋 경계, 저널 이전 절차.
* 새로 생긴 비용: 영속 이벤트를 언로드하면 스왑에 한 번 더 쓴다(압박 때만). 저널 압축이 스왑된 본문을 스왑에서 읽는다.

### 9.5 사용자 결정(v3.2 → v3.3)

* **등록·착수·완료를 멱등으로 했다.** 키는 (이벤트 고유키, 행위), 보장은 시간 창 안에서만 한다(0.4, 2.6).
* **수신 확인을 없앴다.** 등록·완료·삭제는 응답이 없다. 착수 응답은 발송으로 남는다. 이상 처리는 클라이언트 책임이다.
* 원문 4의 구간 회전은 그대로 받았다. 다만 회전을 타이머 없이 연산 처리 시점에 하고, 할당·해제를 보조 스레드로 뺐다.
* 원문에서 더 나간 것(사용자 확인 필요):
  * 맵에 넣는 시점을 "등록에 성공한 때"가 아니라 "활성에서 빠지는 때"로 했다. 오래 대기한 이벤트의 늦은 재전송 때문이다.
  * 착수·완료는 별도 맵 대신 상태 기계로 보장한다(E14).
  * 삭제도 `tag`로 멱등을 준다. 원문 목록에는 없다.
  * nil id 금지(E15), 거절 통보(E16).
* 맵 메모리가 원문 예시(1시간)에서는 최고 처리량에 크게 늘어난다. 그래서 W를 설정값으로 두고 E12로 남겼다.
* **서버는 운송만 한다(0.5).** 서버 사이 공유 상태를 요구하는 기능을 넣지 않는다는 원칙으로 받았다. 이 계획에서 그 원칙과 닿는 곳은 둘이다.
  * 최근 키 맵은 서버별이다. 여러 서버에서 멱등을 지키려면 재전송이 같은 서버로 가야 한다(키 해시 라우팅). 2.6에 적었다.
  * 조각 완성 판정은 이미 저장소의 공유 비트맵이라 서버 수와 무관하다. 3.2에 적었다.

v3.2와 v3.3은 아직 재리뷰를 받지 않았다.
