# 라이브러리 개편 계획: 장부와 바이트의 분리, 코어별 전달, 페이지 저장소

상태: **승인 대기 v3** (2026-11-24).
* v2는 코덱스 리뷰(gpt-6.2-astra, high)의 지적 12건을 반영했다(9장).
* v3는 사용자 결정(0.2)으로 구조를 다시 짰다. 바뀐 것은 세 가지다.
  * 바이트를 엔진 밖으로 뺀다.
  * 메모리 압박은 거부하지 않고 페이지 언로드로 푼다.
  * 전원 거절은 지수 지연 재순회로 푼다.
* 승인 전에는 코드를 바꾸지 않는다.

apibond 재구축([apibond-on-ruvent.md](apibond-on-ruvent.md))은 이 개편을 실제 적용에서 검증하는 프로젝트일 뿐이다. 본론은 라이브러리다.

## 0. 원문과 원칙

### 0.1 개편 요구

> apibond는 원래 라이브러리를 실적용하면서 일어나는 일을 검토하기 위한 프로젝트일뿐이야. 당연히 라이브러리를 전면개편하는게 더 중요하다.
> 대용량 파일 처리에 대한 의견도 부족하고 내가 제안한 기초적인 이벤트 워커 분배에 대해서도 보다 성능과 처리량, 동시성을 고려하여 설계적으로 보완점을 찾는 과정도 없었다.

분배 모델과 대용량 처리의 원문은 [apibond-on-ruvent.md](apibond-on-ruvent.md) 1장에 그대로 있다.

### 0.2 v3를 결정한 원문(2026-11-24)

> 등록 착수 완료는 하나의 쓰레드가 맞아. 그래야 원자성유지에 힘이 안들기 때문이야.
> 하지만 등록 후 쓰레드 통지는 별도의 쓰레드 풀이 처리하지. 그게 가장 큰 비용이 발생하는데 거기서는 문제가 없기 때문에 전체적으로는 여전히 고속일거야.

> 아무리 빠르게 몰려도 개별 이벤트를 워커가 신속하게 제거할거라서 서버 메모리는 빠르게 차지 않아. … 단일 파일핸들에 파일을 붙이는게 아니라 개별 파일 핸들을 통해 조각을 임시 저장하고 이후 병합 파일을 생성한다면 더욱 빨리 메모리를 비워줄 수 있지.

> 나는 초 고성능 이벤트 서버를 통해 이벤트가 들어차고 신속하게 비워지는걸 원해. 또한 이벤트서버의 메모리 제한이 가까워지면 오히려 메모리를 차지하는 이벤트를 페이지 단위로 영속화하여 언로드 했다가 다시 페이지단위로 로드하는 구조로 문제를 해결하지 이벤트 송수신 거부는 없다.

> 모든 워커서버가 거부한 경우 약간 딜레이를 줬다가 다시 순회시키는 로직이 적합하겠지. 처음엔 매우 작은 5ms정도의 딜레이로 시작해서 거부가 한바퀴돌때마다 2배씩 증가시키면 충분할거라 생각해

> 난 초고성능 이벤트 서버를 완성하고 거의 모든 서비스의 핵심 엔진으로 쓰려고 하고 있어.

### 0.3 지킬 원칙

* **이벤트 서버의 역할은 불변이다.** 등록, 발송, 착수 원자성, 완료 시 제거.
* **원자성은 한 스레드가 만든다.** 등록·착수·완료·삭제는 장부 스레드 하나만 바꾼다. 분할하지 않는다.
* **서버는 이벤트 송수신을 거부하지 않는다.** 메모리 압박은 페이지 언로드로 흡수한다. 처리량을 계속 넘는 부하는 워커를 늘려서 푼다. 라이브러리가 풀 문제가 아니다.
* **순서는 이벤트의 단락성(인과)으로 만든다.** 배정 순서는 보장하지 않는다.
* **이벤트 하나는 워커 하나가 가져간다.**
* **lease 회수(Q6(b)).** 원격 실행기는 연결이 끊겨도 일을 계속할 수 있으므로, 끊김으로 즉시 회수하지 않고 lease로 회수한다.
* **서버 규칙은 최소로 둔다(D11).**
* **타이머 원칙을 고친다.** 지금은 "주기 타이머 없음"이다. 이를 "선언된 일회성 타이머만"으로 바꾼다. 전원 거절 재순회 지연(사용자 결정)이 첫 선언 대상이다. 정적 검사 `TIMERS`에 그 위치를 등록한다. 폴링은 여전히 없다.

## 2. 구조: 장부, 페이지 저장소, 코어별 스레드

v2까지는 지금 엔진 안에서 고칠 곳을 찾았다. v3는 비용이 큰 일을 엔진 밖으로 빼고, 엔진에는 원자성에 필요한 최소 상태만 남긴다.

```text
           코어 0            코어 1            코어 n-1
        ┌──────────┐     ┌──────────┐      ┌──────────┐
 소켓 ─►│ I/O 스레드 │     │ I/O 스레드 │  …   │ I/O 스레드 │ ◄─ 연결은 한 스레드가 소유(읽기·쓰기 모두)
        │ 프레임 해석│     │          │      │          │
        │ payload → │     │ payload → │      │ payload → │ ◄─ 스레드마다 자기 열린 페이지에 덧붙임(잠금 없음)
        │ 자기 페이지│     │ 자기 페이지│      │ 자기 페이지│
        │ 전달 커서 │     │ 전달 커서 │      │ 전달 커서 │ ◄─ 채널마다 소유 스레드 하나: 순차 제안·거절·재순회 지연
        └────┬─────┘     └────┬─────┘      └────┬─────┘
             │ 메타 연산(SPSC 링, 묶음)          │
             ▼                                   ▼
        ┌─────────────────────────────────────────────┐
        │ 장부 스레드(단일 작성자)                      │
        │ id·채널·상태·착수 표지·재시도·payload 위치      │ ◄─ payload 바이트를 만지지 않는다. I/O 없음
        │ 등록 / 착수 / 완료+후속 / 삭제 / 회수           │
        └─────────────────────────────────────────────┘
             │ 결과·준비됨 알림(스레드별 SPSC 링, 장부 순서)
             ▼
        페이지 저장소: 메모리 페이지 ⇄ 디스크 페이지 파일(언로드·로드는 페이지 단위)
```

### 2.1 장부 스레드(원자성의 유일한 자리)

* 이벤트마다 쥐는 것: id, 채널, 타입, 상태(대기·착수 중), 착수 표지·lease, 재시도 수, **payload 위치**(페이지 번호, 오프셋, 길이).
* 하는 일: 등록, 착수, 완료+후속, 삭제, lease 회수. 지금의 의미(Q4(a), 활성 id 중복 거절, 착수 표지 대조)를 그대로 지킨다.
* 하지 않는 일: payload 읽기·복사·해시, 소켓 쓰기, 디스크 I/O, 워커 선택.
* 입력: 코어별 SPSC 링에서 메타 연산을 묶음으로 꺼낸다. 출력: 연산 결과와 "착수용 이벤트 준비됨"을 소유 스레드의 링에 장부 순서대로 넣는다. 그래서 연결별 순서가 잠금 없이 지켜진다.
* 페이지 하나에서 살아 있는 이벤트 수(참조 수)를 장부가 센다. 0이 되면 그 페이지를 해제 대상으로 알린다.

### 2.2 코어별 I/O 스레드(송수신과 전달)

* **연결 소유.** 연결 하나는 I/O 스레드 하나에 붙는다. 그 연결의 읽기·쓰기·인코딩은 그 스레드만 한다.
* **수신.** 프레임을 해석하면서 payload를 **자기 스레드의 열린 페이지**에 바로 덧붙인다. 장부에는 위치만 보낸다. 페이지에 넣는 것이 첫 복사이자 마지막 복사다. 작은 이벤트가 큰 수신 프레임을 붙잡는 문제(1장)도 사라진다.
* **송신.** 페이지에서 직접 벡터 쓰기로 내보낸다. 연결마다 일어나던 세 번 복사가 없어진다. 팬아웃 N이면 같은 페이지 구간을 N번 참조한다.
* **전달(사용자 원문의 "전달 풀").** 착수용 채널마다 소유 I/O 스레드가 하나 정해진다. 그 스레드가 그 채널의 워커 순서, 이벤트별 제안 커서, 재순회 지연을 쥔다. 제안을 받을 워커의 연결이 다른 스레드에 있으면, 그 스레드의 링으로 보낸다.
* 전달은 비동기다. 스레드가 제안 하나의 응답을 기다리며 서 있지 않는다. 한 스레드가 수천 개의 미결 제안을 동시에 들고 있을 수 있다. v2의 A2("전달자 P개 / RTT"로 막히는 상한)는 이 구조에서 생기지 않는다.

### 2.3 착수 분배: 원문 모델 그대로

```text
장부: 등록 → "준비됨(e)"를 채널 소유 스레드로
전달 스레드: e를 워커 순서(그 채널 참여 등록순)의 첫 워커부터 제안
  제안(Offer: 엔벨롭 + payload, 페이지에서 직접)
    ├─ 수락 = 착수 요청 → 장부가 원자적으로 대기→착수 중 → 성공 응답(착수 표지)
    │                          └ 이미 착수·삭제됐으면 실패 응답, 워커는 버린다
    ├─ 거절 → 다음 워커
    └─ 한 바퀴 전원 거절 → 지연 d 뒤 처음부터 다시. d = 5 ms × 2^(바퀴−1), 상한 D(E3)
```

* **한 이벤트는 한 시점에 한 워커에게만 제안된다.** 그래서 지금처럼 여러 워커가 같은 이벤트를 다투다 실패하는 낭비가 없다. 착수 실패는 명시 `claim` 도구와 겹칠 때만 생긴다.
* **수락이 곧 착수 요청이다.** 제안 → 수락 → 착수 응답이고, 별도의 착수 호출이 없다.
* **워커별 전달 창(원문 "전달 풀"의 크기).** 워커 하나에 동시에 나가 있는 미결 제안 수를 그 워커가 참여할 때 알린 창 크기로 묶는다. 창이 차 있으면 그 워커를 건너뛰지 않고, 창이 빌 때까지 그 워커 차례에서 기다린다.
  * 이것은 거부가 아니다. 이벤트는 대기 상태로 남는다(필요하면 언로드된다).
  * 창이 없으면 몰림 동안 대기 이벤트 전부가 첫 워커에게 한꺼번에 제안되고, 그 워커가 전부 거절하는 일이 생긴다. 창은 제안 수를 실제 처리 능력에 맞춘다.
* **재순회 지연.**
  * 지연 상태는 이벤트별이다. 이벤트가 착수되면 사라진다.
  * 구현은 전달 스레드마다 타이머 휠 하나다. 이벤트마다 OS 타이머를 두지 않는다.
  * 지연 중에 새 워커가 참여하거나 워커가 `ready`를 보내면, 지연을 끝내고 바로 다시 돈다(E3).
* **응답 없는 워커.** 제안에 응답 기한을 둔다. 기한이 지나면 거절로 본다. 같은 타이머 휠을 쓴다(E4).
* **lease 회수.** 회수된 이벤트는 다시 "준비됨"이 되어 같은 경로를 탄다. 회수 시점은 지금처럼 외부 등록 때다. 타이머 휠이 생기므로 lease 만료도 휠로 옮길 수 있다(E5).
* **명시 `claim`·관찰 `subscribe`.** 도구용으로 남긴다. 관찰 구독에는 착수용 본문이 가지 않는다.
* **발송용 이벤트.** 지금처럼 구독자 전원에게 간다. 페이지에서 직접 보내므로 팬아웃 복사가 없다.
* **wire.** 착수용 `Notice`와 경쟁 착수를 `Offer`/`Accept`/`Decline`으로 바꾼다. 프로토콜 버전을 2로 올리고 v1은 `Welcome`에서 거절한다(저장소 밖 사용자 없음).

### 2.4 페이지 저장소: 거부 대신 언로드

* **페이지.** 고정 크기 블록이다. 크기는 측정으로 정하고, 후보는 1~4 MiB다. I/O 스레드마다 열린 페이지가 하나 있고, 거기에 payload를 덧붙인다. 다 차면 닫고 새 페이지를 연다.
* **페이지 하나의 상태:** 메모리에 있음, 디스크에만 있음, 둘 다. 살아 있는 이벤트 수가 0이 되면 해제한다.
* **언로드.** 메모리의 payload 총량이 상한 위 문턱을 넘으면, 닫힌 페이지 중 **제안 커서에서 가장 먼 것(대기열 꼬리)** 부터 디스크로 내리고 메모리를 비운다. 아래 문턱 밑으로 내려가면 멈춘다. 이 판단은 페이지가 닫히거나 해제될 때만 한다. 주기 검사는 없다.
  * 몰림이 생기면 머리는 지금 제안 중이고 꼬리는 한참 뒤에 쓰인다. 그래서 LRU가 아니라 꼬리부터 내린다.
* **로드.** 전달 스레드가 제안 커서 앞쪽의 페이지를 미리 페이지 단위로 읽어 올린다. 장부 스레드는 디스크를 기다리지 않는다. 장부는 위치만 갖고, 언로드된 이벤트의 삭제·회수도 위치만 바꾸면 되기 때문이다.
* **영속 채널: 페이지 파일이 곧 저널이다.**
  * 영속 채널의 페이지는 닫힐 때(또는 Strict면 묶음 커밋 때) 디스크에 쓴다. 그래서 언로드할 때 추가 쓰기 없이 메모리만 버리면 된다.
  * 장부의 상태 변화(착수, 완료, 삭제, 위치 변경)는 작은 메타 로그에 따로 적는다.
  * 복구는 메타 로그를 다시 적용하고, 페이지 파일에서 위치를 찾는 것이다. 지금의 순변화 저널(본문 포함)을 "데이터 페이지 + 메타 로그"로 바꾸는 큰 변경이다(6장 4단계).
* **휘발 채널(`volatile_channels`).** 페이지를 별도 임시 파일에 내린다. 재기동하면 그 파일을 지운다. 내구성 약속은 없다.
* **조각난 페이지.** 살아 있는 이벤트가 조금만 남은 페이지는 저장소 스레드가 살아 있는 payload를 새 페이지로 옮긴다. 장부가 위치 변경을 원자적으로 반영한다. 옮기는 동안 진행 중인 송신은 옛 페이지 참조를 쥐고 있으므로 안전하다.
* **바닥.** 메모리는 상한을 넘지 않는다. 마지막 상한은 디스크다. 디스크가 차는 것은 흐름 제어가 아니라 운영 장애다. 이때 등록은 오류로 응답하고, 지표와 로그로 알린다.
* **장부 메모리.** 장부는 이벤트당 메타데이터만 쥔다. 대기열이 아주 길 때(수천만 건) 메타데이터까지 내리는 일은 이번 개편에서 하지 않는다(E6). 이벤트당 장부 크기는 측정해서 보고서에 적는다.

#### 상태 선언(키·범위·수명·상한·정리 주체)

| 상태 | 키 | 범위 | 수명 | 상한 | 정리 주체 |
| --- | --- | --- | --- | --- | --- |
| 장부 이벤트 | 이벤트 id(활성만) | 서버 | 등록 ~ 완료·삭제 | 대기 수(메타만, 측정) | 장부 스레드 |
| 페이지 참조 수 | 페이지 번호 | 서버 | 열림 ~ 0 도달 | 페이지 수 | 장부가 세고, 저장소 스레드가 해제 |
| 제안 커서·재순회 지연 | 이벤트 id | 채널 소유 I/O 스레드 | 준비됨 ~ 착수 | 대기 수 | 착수 결과를 받은 소유 스레드 |
| 미결 제안 | (연결, 이벤트 id) | 연결 소유 스레드 | 제안 ~ 응답·기한 | 워커 전달 창 | 응답·기한·끊김 처리 |

### 2.5 멀티코어에서 얻는 것

* 비용이 큰 일이 모두 코어별 스레드로 간다. 소켓 읽기·쓰기, 프레임 해석, 인코딩, payload 쓰기, 제안 왕복 관리, 페이지 로드가 그것이다.
* 장부 스레드는 짧은 메타 연산만 한다. 장부가 병목이 되는 지점은 측정으로 확인한다(M0). 목표 수치는 E7에서 정한다.
* 연결 소유가 한 스레드라서, 같은 연결의 순서를 지키는 데 잠금이 필요 없다. Strict의 "디스크에 닿기 전 공개 금지"는 장부가 결과를 링에 넣을 때 묶음 커밋 번호를 붙이고, I/O 스레드가 그 번호의 fsync 완료를 본 뒤 보내는 것으로 지킨다.

## 3. 대용량 페이로드

### 3.1 지금의 한계

* 등록 하나는 프레임 하나(기본 16 MiB)를 넘을 수 없다.
* 대기 중인 착수용 이벤트는 엔진 메모리에 본문째 있고, 저널에도 본문째 적힌다.
* 발송 팬아웃은 연결마다 payload를 세 번 복사한다.

### 3.2 조각 시리즈

큰 페이로드는 조각 시리즈로 보낸다. 조각은 순서가 보장되지 않고 다른 이벤트와 섞여도 된다. 서버 쪽에서 해결되는 것은 다음과 같다.
* 조각 이벤트는 2.4의 페이지에 들어간다. 몰리면 꼬리부터 언로드된다. 서버는 거부하지 않는다.
* 조각 워커는 조각을 **조각마다 개별 파일로 임시 저장**하고 바로 완료한다. 하나의 파일 핸들에 순서대로 붙이지 않으므로 순서를 기다리지 않는다. 그래서 조각 이벤트는 받는 즉시 비워진다.
* 다 모이면 병합 파일을 만든다.

```text
보내는 쪽(프록시 등)                         이벤트 서버          워커들(어느 워커든)
manifest: 시리즈 id·세대, 조각 수 N, 조각 길이, 전체 길이·해시, 결과 채널
part i (순서 무관) ─────────────────────► 조각 채널 ─► 제안 ─► part 워커: 저장소.put(series, gen, i, bytes) → 개별 임시 파일
                                                                if put이 "N개 모두 있음"을 돌려주면:
                                                                   complete(part, follow_ups=[assemble(id = f(series, gen))])
                                                                else: complete(part)
                                                         assemble 워커: 개별 파일을 순서대로 병합 → 병합 파일
                                                                complete(assemble, follow_ups=[result(id = g(series, gen))])
```

**조립 담당 선출은 엔진의 기존 규칙으로 한다.**
* "모두 있음"을 본 조각 워커는 자기 조각의 완료에 **결정적 id**(시리즈 id와 세대에서 유도)의 `assemble` 후속을 붙인다. 완료와 후속 등록은 장부에서 원자적이다(Q4(a)).
* 여러 워커가 동시에 "모두 있음"을 보면, 첫 완료만 `assemble`을 등록한다. 나머지는 후속 id 중복으로 거절된다. 클라이언트 라이브러리는 이 경우(`Duplicate` 거절 + 결정적 id 후속) 후속을 빼고 다시 완료한다.
* put 뒤 완료 전에 워커가 죽으면, 그 조각은 lease로 회수되어 다시 실행된다. put은 멱등이고 "모두 있음"을 다시 보므로 결과를 잃지 않는다.
* 보장 범위: **논리 결과는 id 하나다.** 결과가 이미 소비된 뒤 늦은 재실행이 같은 id로 다시 등록하는 경합은 막지 않는다. 결과 소비자는 결과 id로 멱등 처리한다.
* 서버 조인 카운터는 기각한다(D11; 저장소 상태를 서버가 알 수 없음).

**조각 저장소 계약.**

| 연산 | 계약 |
| --- | --- |
| `open(manifest)` | 불변 manifest를 고정한다. 같은 시리즈 id에 다른 manifest가 오면 충돌. 조각이 manifest보다 먼저 와도 된다. 조각마다 manifest 머리를 싣는다 |
| `put(i, bytes)` | 조각마다 **개별 파일**. 임시 이름에 쓰고 rename으로 공개한다. 같은 내용의 중복은 성공, 다른 내용은 `Conflict`. 돌려주는 것: 새로 들어갔는지, 지금 있는 조각 수 |
| `state` | `OPEN → SEALED(N개 모두 있음) → ASSEMBLED → PUBLISHED`, 또는 `ABORTED`, `FAILED(해시 불일치 등)`. 세대 단위 |
| `assemble` | 개별 조각 파일을 순서대로 이어 병합 파일을 만들고 전체 해시를 검사한다. 끝나면 조각 파일을 지운다 |
| `read(range)` | `ASSEMBLED` 이후 병합 파일에서 |
| `abort`, `remove` | `ABORTED` 뒤 put은 `Aborted`를 돌려주고 쓰지 않는다. 지운 뒤에도 세대 묘비를 보존 기간 동안 둔다 |

* **조각 수 세기.** `put`이 지금 개수를 돌려준다. 로컬 구현은 처음 접근 때 디렉터리를 세고, 이후 프로세스 안 원자 계수로 유지한다.
* **객체 저장소(S3 계열).** S3 멀티파트 part는 마지막을 빼고 최소 5 MiB이고, 번호는 1~10,000이다. 그래서 조각 하나를 part 하나에 대응시키지 않는다. 조각은 객체 하나씩 두고, 조립 때 합친다.
* **취소.** 보내는 쪽이 착수용 `abort`를 등록한다. 이후 put은 `Aborted`를 받는다.
* **정리.** 버려진 시리즈는 워커가 새 시리즈를 열 때 기한 지난 것을 지운다.

**조각 채널의 영속.** 기본은 영속이다. 2.4에 따라 영속 비용은 페이지 쓰기 한 번(순차)이다. 휘발 채널은 원본을 결과 확인 때까지 보존하는 생산자만 쓴다.

### 3.3 큰 결과를 받는 쪽으로

* 결과가 큰 경우 바이트를 이벤트로 흘리지 않는다. 생산자가 저장소에 결과를 쓰고, 결과 이벤트에는 참조(시리즈 id·세대·길이·해시)만 싣는다. 프록시는 저장소에서 오프셋 순서대로 자기 속도로 읽는다.
* 생산 중인 결과를 따라 읽어야 하면, 생산자가 진행 발송(`progress(series, 연속 오프셋)`)을 내고 프록시가 그 오프셋까지 읽는다.
* **작은 실시간 스트림(토큰 SSE).** 발송용 이벤트에 순번을 붙이고 받는 쪽이 정렬한다. 생산자는 응답을 기다리지 않는 연속 등록 API로 보낸다. 한 연결의 요청은 보낸 순서대로 장부에 들어가므로 순서가 유지된다.

### 3.4 채널 단위 저널 제외

* 엔진 설정 `volatile_channels: [패턴]`. 맞는 채널의 페이지와 메타 변화는 저널에 넣지 않는다.
* 조합별 결과표를 시험으로 고정한다.
  * durable 부모 + volatile 후속: 부모 제거만 기록된다.
  * volatile 부모 + durable 후속: 후속은 기록된다.
  * 압축·스냅샷: volatile 제외.

## 4. 프록시

* **원 엔벨롭 스트림.** 허브가 사용자에게 `Arc<Envelope>`를 준다. 내장 WS·HTTP가 텍스트로 그린다.
* **요청 교환 `Proxy::exchange(event)` 계약.**
  1. 프록시 연결 세대마다 접두사 `<프록시 id>.<세대>.` 구독의 표지를 확인한다.
  2. 재사용하지 않는 요청 id(UUIDv7)의 대기자를 설치한다.
  3. 원 요청을 `reply = <접두사><요청 id>`로 등록한다.
* 사용자 `subscribe`는 join마다 자기 표지를 기다린다(허브 불변식 유지). 접두사 구독은 교환에만 쓴다.
* **장부의 접두사 구독.** 정확 이름은 해시 조회, 접두사는 `.` 경계 트라이 조회로 둔다. 겹쳐 받으면 연결 단위로 한 번만 보낸다. 접두사 구독은 발송 수신 전용이다.
* **앱 경로.** `Server::routes(Router<Proxy>)`.

## 5. 측정 계획

변경 **전에** 지금 경로로 기준선을 남기고, 단계마다 같은 설정으로 다시 잰다. 보고서에는 버전·설정·호스트·코어 수·동시성·실제 작업 수·내구성 모드·반복 횟수를 적는다.

| # | 작업 부하 | 보는 것 |
| --- | --- | --- |
| M0 | TCP 등록→제안→수락→완료. W = 1, 4, 16, I/O 스레드 수 1~코어 수, payload 16 B ~ 64 KiB | 완료 처리량, 배정 대기 p50/p99, **장부 스레드 사용률**, I/O 스레드별 사용률, 이벤트당 장부 연산 수 |
| M1 | 몰림: 등록률이 처리율을 잠시 넘음, 전원 거절 후 재순회 | 대기 수, 제안·거절 수, 재순회 지연 분포, 몰림 해소 시간 |
| M2 | 발송 팬아웃 N = 1, 16, 256, payload 16 B ~ 1 MiB | 처리량, 복사 바이트·할당·시스템 호출 |
| M3 | 메모리 상한을 넘는 대기열. 상한의 2배·10배 | RSS가 상한 안에 머무는지, 언로드·로드 바이트, 로드로 인한 제안 지연 |
| M4 | 시리즈 64 MiB ~ 1 GiB, 조각 256 KiB ~ 4 MiB, 역순·누락·중복·중단 후 재개 | MB/s, RSS, 조각 이벤트 체류 시간, 병합 시간. 기준선은 같은 파일의 직접 전송 |
| M5 | Strict 묶음 커밋 | fsync 수 / 등록 수, 처리량, p99 |
| M6 | 요청 교환, 정확 이름과 접두사 | 요청당 지연 |

## 6. 단계

각 단계는 테스트·문서·`cargo xtask verify`·커밋으로 끝내고, 측정이 있는 단계는 보고서를 남긴다.

1. **계약 시험 정의.** 이 문서의 계약을 테스트 이름이 붙은 시험 목록으로 고정한다(`docs/testing.md` 지도).
2. **기준선 M0·M1·M2·M5.** 측정 예제를 TCP·다중 워커로 넓힌다.
3. **장부와 바이트 분리, 코어별 I/O 스레드.**
   * 엔진에서 payload를 빼고 위치만 남긴다.
   * 연결을 소유하는 I/O 스레드와 SPSC 링을 두고, 송신은 벡터 쓰기로 한다.
   * 기존 보장 시험이 다시 통과해야 한다. M0·M2를 재측정한다.
4. **페이지 저장소와 저널 교체.**
   * 데이터 페이지와 메타 로그, Strict 묶음 커밋, 언로드·로드, 조각 페이지 압축, `volatile_channels`를 만든다.
   * 반례 시험: 언로드된 이벤트의 삭제·회수, 로드 중 완료, 재기동 복구, 디스크 가득.
   * M3·M5를 측정한다.
5. **원문 분배.**
   * `Offer`/`Accept`/`Decline`, 워커별 전달 창, 재순회 지연(타이머 휠), 응답 기한, v2 wire를 만든다.

   * M0·M1을 재측정한다.
6. **조각 시리즈와 조각 저장소**(파일 시스템, 그다음 객체 저장소). 반례 시험: 선출 전·후 사망, 상충 중복, 해시 불일치, `abort` 경합. M4.
7. **프록시.** 원 엔벨롭, 접두사 구독, 교환 계약, 앱 경로. M6.
8. **apibondrust**로 실제 적용 검증.

### 9.2 사용자 결정(v2 → v3)
