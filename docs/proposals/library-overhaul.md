## 0. 목적, 원문, 원칙

### 0.1 목적

**거의 모든 서비스의 핵심 엔진으로 쓸 수 있는, 자원 효율이 극도로 높고 정상 운영에서 안정적인 단일 이벤트 서버.** 가용성과 용량은 독립 서버 여러 대로 얻는다.

"정상 운영"은 배포, 재시작, 재접속, 일시 과부하, 설정 실수, 워커 정지, 몰림이다. 이 문서의 모든 결정은 이 상황들에서 목적을 지키는지로 판단한다.

### 0.2 원문

> 나는 초 고성능 이벤트 서버를 통해 이벤트가 들어차고 신속하게 비워지는걸 원해.

> 난 초고성능 이벤트 서버를 완성하고 거의 모든 서비스의 핵심 엔진으로 쓰려고 하고 있어.

> 난 내 지시가 이뤄지길 바라지 않아. 보다 비판적으로 고가용성에서의 안정성있는 이벤트 기반 서버 구축에 맞는 아키텍쳐를 만들고 싶어. 내 의견외에도 기존에 참고할 수 있는 모든 공학적인 지식으로 충분히 비판적으로 검토하고 리뷰하길 원한다.

> 하지만 굳이 그런 병렬화된 이벤트서버의 필요성을 느끼진 않아. 이벤트 특성상 차라리 여러 독립된 이벤트 서버를 부하에 맞게 운영하는게 낫기 때문이야. 이벤트 서버가 굳이 트랜젝션 단위의 부하를 책임질 이유는 없고 부하분산 자체도 독립된 이벤트서버에게 알아서 할당하는 라우터는 별도 작성이라는 입장이다

> 중요한건 하나의 단일 이벤트서버가 엄청나게 자원효율적으로 이벤트를 처리하고 발송하는 것이다
> 유일한 약점인 발송부하는 프록시를 이용해 몇개의 프록시에게만 전가하는 것으로 갈음할 수 있기 때문이다

> 우리가 추구하는 목적을 잊지마. 부분적인 모순을 해결하는게 집중하면 안된다

그 이전 판의 원문은 9장에 있다.

### 0.3 원칙

**구조.**
* **서버 하나 = 장부 하나.** 등록·착수·완료·삭제·회수의 상태는 서버마다 단일 작성자 하나가 바꾼다. 서버 안에서 분할하거나 복제하지 않는다.
* **용량과 가용성은 독립 서버의 수로 얻는다.** 서버끼리는 상태를 나누지 않는다. 생산자의 서버 선택은 별도 라우터가 한다(범위 밖). 선례는 NSQ다(9.6).
* **목표는 단일 서버의 자원 효율이다.** 같은 일을 더 적은 CPU, 메모리, 디스크 쓰기, 시스템 호출, 프레임으로 한다. 판단이 갈리면 이 기준으로 고른다.
* **발송 팬아웃은 프록시가 진다.** 서버의 발송 비용은 프록시 수에 비례하게 만든다.
* **서버는 업무 payload를 해석하지 않는다.** 조립, 합산, 재시도 정책은 워커와 저장소의 몫이다. 서버가 아는 것은 엔벨롭 메타뿐이다.

**전달 의미.**
* **착수용 이벤트는 최소 1회 실행이다.** 정상 운영에서 재실행을 낳는 것은 lease 만료와 워커의 명시 반환뿐이다. **서버의 재기동과 재접속은 재실행을 낳지 않는다**: 커밋된 착수는 재기동을 넘어 유지된다(2.4). 비정상 종료와 서버 상실에서는 재실행이 남는다(2.4, 2.8). 그래서 워커의 업무 멱등은 여전히 필수다.
* **발송용 이벤트는 1회성이다.** 보내면 끝이다.
* **원자성.** 한 완료와 그 후속은 한 스텝에 적용되고, 한 영속 프레임 안에서 찢어지지 않는다.
* **순서는 이벤트의 인과(후속)로 만든다.** 배정 순서는 보장하지 않는다.

**응답과 부하.**
* **평상시 건별 응답은 없다.** 생산 연결은 누적 커밋 확인만 비동기로 받는다(2.3). 휘발 방송 전용 연결은 그것도 끈다.
* **과부하로 거절하지 않는다.**
  * 일시 몰림은 메모리와 디스크로 흡수한다.
  * 디스크나 관리 메모리가 고수위에 닿으면 생산 연결의 읽기를 늦춘다(TCP 흐름 제어, 2.6).
  * **한 수신자의 정체는 그 수신자에서 끝낸다.** 읽지 않는 연결 하나가 서버 전체의 자원을 쥘 수 없다(2.6).
* **설정·형식 오류는 연결마다 종류별 첫 1회만 알린다**(2.7).
* **이상 처리는 클라이언트 책임이고, 그 규칙은 SDK가 구현한다**(2.9). 서버가 부하를 클라이언트로 넘기는 설계이므로 SDK는 이 계획의 절반이다.

**정책과 시간.**
* **정책은 워커가 정하고, 서버는 시각과 횟수만 지킨다.** 서버가 지키는 것은 네 가지다: lease 기한, 가시 시각(`not_before`), 만료(`expires`), 실패 횟수 문턱(`isolate_after`). 몇 번, 얼마 뒤에 다시 할지는 워커가 정한다.
* **타이머는 선언된 일회성만 쓴다.**
  * 지금 `TIMERS`에 다섯 곳이 선언돼 있다(`tests/static/architecture.rs:95~101`).
  * 서버에 둘을 더한다: 기한 휠 하나(lease와 `not_before` 공용), 누적 확인의 시간 문턱.
  * SDK에 셋을 더한다: 재접속 백오프, 호출 기한, lease 자동 연장.
  * 모두 가장 이른 기한에만 깨고 비면 잠든다. 폴링과 주기 타이머는 없다.
* **서버의 시각은 단조 시계다.** 재기동하면 남은 시간을 알 수 없다. 그래서 lease, `not_before`, `expires`는 재기동 때 모두 원 길이로 다시 건다.

| 프록시 | 상향 연결 하나, 끊기면 back-off로 재접속한다. 사용자 join마다 상향 구독을 내고 표지를 기다린다. 인증 응답은 응답 채널 하나 + correlation으로 받는다. 느린 사용자는 끊는다 | `ruvent-proxy/src/hub/task.rs:208~229·233~241·330~336·358~363`, `ruvent-proxy/src/hub/channels/mod.rs:145~169` |

## 2. 구조

```text
 생산자 ──(라우터, 별도)──► 서버 A ◄── 워커(모든 서버에 직접)
                              │
                              └──► 프록시 몇 대 ──► 수많은 구독 클라이언트

 서버 하나의 안:
   ┌──────────────────────────────────────────────────────────────────┐
   │ 연결 소유자(I/O): 본문 직접 수신, 인코딩, 벡터 송신              │
   │   생산 연결            작업 연결              관찰 연결           │
   │   (등록·삭제)          (credit·완료·반환)     (구독·발송 수신)    │
   └───────┬──────────────────────▲──────────────────────────────────┘
           │ 연산(메타)            │ 결과 + 연결별 송신 순번
   ┌───────▼──────────────────────┴──────────────────────────────────┐
   │ 장부(단일 작성자): 메타만. 생산자 순번표, credit, 기한 휠, 회계  │
   └───────┬──────────────────────────────────────────▲──────────────┘
           │ 레코드 묶음                               │ 커밋 번호
   ┌───────▼──────────────────────────────────────────┴──────────────┐
   │ 세그먼트 로그(엔진 하나, 인스턴스 둘)                            │
   │   영속 로그: fsync, 재기동 뒤에도 남는다 + 체크포인터            │
   │   휘발 로그: 동기화 없음, 재기동 때 버린다(메모리 넘침용)        │
   │ 읽기 스레드: 캐시에 없는 본문을 세그먼트에서 읽어 온다           │
   └──────────────────────────────────────────────────────────────────┘
```

설계를 관통하는 선은 셋이다.

1. **본문은 한 번만 움직인다.** 소켓에서 본문 버퍼로 한 번, 영속이면 디스크에 한 번, 나갈 때 소켓으로 한 번. 장부는 메타만 쥔다.
2. **정상 운영의 사건은 일을 다시 만들지 않는다.** 재기동, 재접속, 배포는 재실행·유실·재시도 횟수 증가를 낳지 않는다.
3. **모든 자원에 주인과 상한이 있다.** 메모리, 디스크, 연결별 대기, credit이 모두 회계되고, 한 참여자의 정체가 다른 참여자에게 번지지 않는다.

### 2.1 장부

* **이벤트당 메타만 쥔다.** 논리 id, `WorkKey`, kind, 채널, 타입, 상태, 시도 표지, lease 길이와 기한, 실패 횟수, 착수 자격, `reply`·`correlation`, 가시 시각(`not_before`), 만료(`expires`), 필요 커밋 번호, 본문 위치(캐시 참조 또는 세그먼트 위치), 본문 다이제스트(길이 + CRC32).
* **식별자는 셋이고 역할이 다르다.**
  * **논리 id**는 이벤트의 이름이다. 회수해도 바뀌지 않는다. 명시 `claim(id)`, 삭제, 중복 판정, 결과 소비자의 멱등 키가 모두 이것을 쓴다.
  * **`WorkKey`**(세대, 도착 순번)는 서버가 붙이는 대기 순서다. 저널 레코드와 체크포인트의 키이기도 하다.
  * **착수 표지**(`ClaimToken`: 세대, 순번)는 시도 하나의 이름이다. 단조 증가하고, 워커에게 펜싱 토큰으로 내준다. 늦은 완료·연장·반환은 표지 불일치로 막는다.
  * 지금은 회수가 id를 새로 준다(`state/mod.rs:477`). 그래서 이벤트 고유키가 회수 때마다 바뀐다(비판 C3).
* **검사는 메타만으로 한다.** 권한, 타입, 후속 검증, 중복, 키 지정 삭제, 만료가 모두 그렇다. "내용이 같은가"는 본문 다이제스트로 판정한다. 다이제스트는 연결 소유자가 본문을 받으면서 계산한다. 영속 세그먼트의 무결성 검사에 어차피 필요한 값이라 추가 비용이 없다.
* **대기 순서는 (채널, 타입)별이다.** 워커는 타입을 골라 참여하므로(2.4), 채널 하나의 줄이면 머리의 미지원 타입이 뒤를 막는다.
* **출력은 값이다.** 인코딩은 연결 소유자가 한다.
* **자료구조.** 조밀한 슬롯 배열 + `id→slot` 인덱스 + 슬롯 세대 + (채널, 타입)별 대기 순서. 지금의 트리·맵 조합과 장부 단독으로 비교한다(M0, 2단계).
* **장부는 기다리지 않는다.** 소켓, 디스크, 타이머 어느 것도 기다리지 않는다. 지금과 같다(`engine/mod.rs:11`).

### 2.2 연결과 운송

**연결 역할(비판 C7).** `Hello`에서 역할을 밝힌다. 역할마다 흐름 제어가 다르다.

| 역할 | 들어오는 것 | 나가는 것 | 흐름 제어 |
| --- | --- | --- | --- |
| 생산 | 등록, 삭제 | 누적 확인, 오류 통보 | 고수위(디스크 또는 관리 메모리)에서 읽기를 늦춘다 |
| 작업 | 참여, credit, 완료(후속 포함), 연장, 반환, 명시 착수 | 배달, 굶음 신호, 누적 확인 | **읽기를 멈추지 않는다.** 메모리가 차면 들어오는 후속 본문을 디스크로 흘려 읽는다. 나가는 양은 credit의 바이트 한도로 묶인다 |
| 관찰 | 구독, 해지, 통계 요청 | 발송, 통지 | 들어오는 것은 작다. 나가는 것은 연결별 대기 상한으로 묶는다(2.6) |

* 한 TCP 줄에서 큰 등록 뒤의 완료는 앞 바이트를 다 읽어야 보인다. 메모리가 찬 순간에도 해제 경로(완료)를 살리려면 완료가 오는 연결을 멈추지 않아야 한다.
* 역할을 여럿 쓰는 앱은 연결을 여럿 연다. SDK가 감춘다(2.9).

**프레임(wire v2).** 레코드 하나가 머리와 본문으로 갈린다. 바깥 프레임은 없다.

```text
record = [tag u8][head_len u16][body_len u32][head …][body …]
```

* 머리를 읽으면 본문 길이를 안다. 할당 전에 메모리 회계를 거치고, 그 이벤트의 본문 버퍼에 소켓에서 바로 읽는다. 프레임 전체를 먼저 할당하지 않는다.
* 레코드 하나는 본문을 많아야 하나 싣는다. 후속이 여럿인 완료는 `Complete` 뒤에 `FollowUp` 레코드를 잇고, 마지막이 도착했을 때 한 연산으로 장부에 넘긴다.
* 묶음은 송신 쪽이 한 번의 벡터 쓰기에 여러 레코드를 싣는 것으로 한다.
* 레코드 목록은 2.11에 있다. 바이트 단위 레이아웃은 1단계에서 뒤 단계의 레코드까지 한 번에 고정한다. 단계마다 구현된 범위는 `Hello`·`Welcome`의 기능 비트로 알린다.

**수신과 송신.**
* **송신.** 연결별 머리와 공유 본문을 벡터 쓰기로 보낸다. 부분 쓰기는 남은 구간에서 잇는다. 본문은 연결마다 복사하지 않는다(지금 세 번, 1장). 작은 본문을 머리와 한 버퍼에 담는 문턱은 측정으로 정한다(8.2).
* **연결 하나의 읽기·쓰기·인코딩·이름 사전은 그 연결의 소유자만 다룬다.**
* **콜드 본문은 읽기 스레드가 읽는다.** 캐시에 없는 본문을 연결 소유자가 직접 디스크에서 읽으면 그 소유자의 모든 연결이 멈춘다. 연결 소유자는 준비된 버퍼만 쓴다.

**연결별 송신 순서.**
* 장부가 결정하는 순간 (연결, 연결별 송신 순번, 필요 커밋 번호)를 붙인다. 연결 소유자는 다음 순번이고, 커밋이 끝났고, 본문이 준비된 것만 내보낸다.
* 지금의 `route` 의미를 일반화한 것이다: 개별 게이트, 같은 연결의 선행 보류, 세대 전환 전체 게이트(`engine/mod.rs:361~373`).
* **발송 대상은 등록을 처리한 순간의 구독 집합**이다. 장부가 구독 집합 버전을 넘긴다.
* 시험: 지금의 A/B 순서 시험(`tests/runtime/durability.rs:44~73`)을 넓힌다. 장부와 연결 소유자가 다른 스레드, 본문이 세그먼트에만 있는 이벤트, 세대 전환이 낀 배치.

**스레드와 큐: 측정이 고른다.** 구조도의 "연결 소유자"와 "장부" 사이를 무엇으로 잇는지는 2단계의 M0가 정한다. 3·4단계의 기능을 그 위에 한 번만 쓰기 위해서다.

| 후보 | 내용 |
| --- | --- |
| (가) 지금 | tokio 태스크 + `mpsc` + `recv_many` 묶음(`engine/mod.rs:141·281`) |
| (나) | 코어별 I/O 스레드 + 다중 생산자 링 하나 |
| (다) | 코어별 I/O 스레드 + 쌍별 SPSC 링 |

* 판정: 같은 합성 부하에서 연산당 CPU 시간과 큐 체류 p99.9를 본다. 차이가 10% 미만이면 더 단순한 쪽((가) > (나) > (다))을 고른다.
* 어느 쪽이든 지키는 계약:
  * **대기 전략은 잠들기 + 묶음 깨우기다.** 소비자는 비었음을 표시하고 잠든다. 생산자는 그 표시가 서 있을 때만 깨운다. 깨우기는 "빔 → 비지 않음" 전이마다 한 번이다. 깬 소비자는 빌 때까지 꺼낸다(한 차례의 연산 수에 상한). 바쁜 대기와 주기 확인은 없다. 유휴 서버는 CPU를 쓰지 않는다.
  * 연결 소유자는 장부로 가는 큐가 차도 결과 소비, 쓰기 완료, 공간 반환을 계속 한다(막힘 분리).
  * 작업 연결의 연산은 예약된 큐 공간을 쓴다. 생산 연결의 몰림이 완료를 막지 않는다.

### 2.3 생산: 생산자 순번과 누적 커밋 확인 (비판 C2, C3)

```text
Hello{역할=생산, producer_id}   → Welcome{server_id, 세대, resume = 그 생산자의 마지막 적용 순번}
Register{seq = resume+1, …}  ─┐
Register{seq = resume+2, …}   ├─ 응답을 기다리지 않고 연속으로
Delete{seq = …}              ─┘
                              ← Committed{seq}   (N건마다 또는 T 뒤, 누적)
```

* **순번.** 생산 연결의 등록·삭제와 작업 연결의 완료에 연속 순번을 붙인다. 두 연결은 생산자 id가 다르다.
  * 순번이 마지막 적용 순번 이하면 재전송이다. 조용히 버린다.
  * 순번에 빈자리가 있으면 프로토콜 오류다. 첫 1회 통보(2.7) 뒤 연결을 닫는다.
* **생산자 id는 "재전송 버퍼 하나"의 이름이다.**
  * **기본: 프로세스가 뜰 때마다 SDK가 새로 만든다.** 재전송 버퍼가 메모리에만 있으므로, 프로세스가 죽으면 그 id로 다시 보낼 것이 없다. Kafka의 멱등 프로듀서와 같다.
  * 버퍼를 디스크에 두는 생산자(영속 outbox)만 id를 보존한다.
  * 이 규칙이 없으면 설정에 고정한 id를 복제본들이 함께 쓰게 되고, 한쪽의 이벤트가 다른 쪽의 순번에 가려 **조용히 버려진다.**
* **같은 id의 새 연결이 오면** 서버는 옛 연결에 `Bye{superseded}`를 보내고 닫는다. 옛 인스턴스의 늦은 쓰기를 막는다.
  * `Bye{superseded}`를 받은 SDK는 **그 id로 다시 붙지 않는다.** 앱에 오류로 올린다. 서로 끊기를 되풀이하지 않는다.
  * 새 연결의 `Welcome`은 "살아 있는 연결을 밀어냈음"을 알린다. id를 함께 쓰는 설정 실수가 양쪽에서 보인다.
* **`Welcome`의 `resume`은 마지막 적용 순번이다.** 서버는 그 생산자의 적용분이 모두 커밋된 뒤에 `Welcome`을 보낸다.
  * 버퍼가 있는 생산자는 `resume` 이하를 버리고 그 뒤를 다시 보낸다.
  * 커밋 순번을 주면, 적용됐지만 아직 커밋되지 않은 구간과 새 내용의 번호가 겹쳐 새 내용이 버려질 수 있다. 그래서 적용 순번을 준다.
  * 서버가 이 생산자의 기록을 잃었으면(`resume`이 버퍼의 첫 순번 − 1보다 작다) SDK는 버퍼를 `resume + 1`부터 다시 번호 매긴다(2.9).
* **누적 커밋 확인.**
  * `Committed{seq}`는 그 생산자의 seq까지 효과가 커밋됐다는 뜻이다. 생산자는 이것을 받아야 재전송 버퍼를 비울 수 있다.
  * **기준은 "버려도 되는가"다.** 저널이 있으면 Strict와 Scheduled 모두 그 순번의 레코드가 든 묶음의 fsync 완료다. 저널이 없으면 장부 적용이다.
    * 지금도 두 모드의 디스크 쓰기는 같다(1장). 두 모드의 차이는 **다른 연결에 보이는 시점**뿐이다(2.7).
    * 그래서 Scheduled에서도 확인받은 순번은 잃지 않는다. 확인 전에 서버가 죽으면 살아 있는 생산자가 다시 보낸다.
  * 수량 문턱 N과 시간 문턱 T 중 먼저 오는 것에서 보낸다. T는 미확인분이 생길 때 한 번 거는 일회성 기한이다.
  * 100만 건/초에 N = 256이면 확인 레코드는 약 3,906개/초, 건별 응답의 0.4%다(1,000,000 ÷ 256).
  * 확인이 필요 없는 휘발 방송 전용 연결은 `Hello`에서 끈다.
* **생산자 순번표(서버).** 생산자마다 (마지막 적용 순번, 마지막 커밋 순번, 살아 있는 연결)을 둔다.
  * 메모리는 생산자 수에 비례하고 처리량과 무관하다. 활성 생산자 10만 개 × 64 B ≈ 6.4 MB다(가정에 따른 계산).
  * 영속은 묶음마다 `Producer(id, seq)` 레코드 하나로 한다. 이벤트마다 기록하지 않는다. 체크포인트에 표 전체를 둔다. 재기동 뒤에도 멱등이 남는다.
  * 항목은 마지막 연결이 닫힌 뒤 보존 기간이 지나면 지운다(8.1). 영속 outbox 생산자는 `Hello`에서 더 긴 기간을 요청한다.
* **논리 id.**
  * nil이면 서버가 붙인다. 재전송은 순번으로 걸러지므로 서버가 붙인 id를 알릴 필요가 없다.
  * 같은 업무를 다시 낼 수 있는 생산자는 id를 직접 정한다. 활성 id와 겹치는 등록은 조용히 버린다(다이제스트가 같을 때). 다이제스트가 다르면 충돌이고 첫 1회 통보한다.
* **키 창(선택).** 활성에서 **빠진 뒤의** 재전송까지 막아야 하는 채널만 채널 설정 `dedup_window`로 켠다. 기본은 꺼짐이다.
  * 대상: 순번을 이어 갈 수 없는 경로(임시 HTTP 등록), 여러 독립 생산자가 같은 업무를 내는 채널.
  * 키는 활성에서 빠지는 순간 들어간다. 구간 두 개를 돌리고, 장부가 연산을 처리할 때 현재 시각으로 회전한다(타이머 없음).
  * 모든 채널에 켜면 메모리가 처리량에 비례한다: 2 × 이탈률 × W × 항목 = 10만/초 × 120초 × 2 × 40 B(가정) ≈ 1 GB. 그래서 기본이 꺼짐이다.
* **완료 안의 후속.** 후속 id가 활성이거나 창에 있을 때, 다이제스트까지 같으면 그 후속만 생략한다. 다르면 완료 전체를 적용하지 않고 충돌로 통보한다.

### 2.4 소비: credit, 기한, 반환, 격리 (비판 C6, C9)

```text
작업 연결:
  Join{채널, 타입들, lease}              → Joined | Refused        참여. Claim 권한을 여기서 검사한다
  Credit{채널, +n, 바이트 b}                                        미리 낸 수락
                                         ← Assign{엔벨롭 + 본문, 표지, 남은 lease, more}
  Complete{표지, 후속…, credit}  |  Extend{표지}  |  Release{표지, 지연, 실패, credit}
                                         ← Pending{채널}            credit이 0인데 일이 기다릴 때 한 번
  Credit{채널, 회수}                     → CreditReturned{n}        다른 서버로 옮길 때만
```

`Assign`은 v4의 `Delivery`다. 지금 코드에서 `Delivery`는 발송 전달의 이름이라 나눴다.

**credit은 미리 낸 수락이다.**
* 워커가 받을지 정한다는 원문의 의미가 그대로다. 거절은 credit을 내지 않는 것이다.
* 서버는 credit이 있는 참여자에게 본문까지 바로 보낸다. 배정, 착수, 배달이 하나다. 제안 → 수락 → 착수 왕복이 없다.
* 본문은 `Join`을 통과한 연결에만 간다.
* **워커 고르기.** 참여 등록순으로 credit이 남은 첫 참여자다. 원문의 "순서대로"를 지키면서 credit이 없는 워커는 건너뛴다. 채널 설정으로 가중 순환을 고를 수 있다(8.1).
* credit이 없으면 일은 대기열에서 새 credit을 기다린다. 재순회 타이머가 없다.

**여러 서버에서의 credit.** 워커는 모든 서버에 붙는다(2.8). credit은 서버별이므로, 실행 슬롯 P개를 서버들에 어떻게 두느냐가 정해져야 한다. 각 서버에 P를 내면 P × S건이 배정돼 lease를 태우고, P ÷ S씩 고정하면 부하가 몰린 서버에서 1/S만 쓴다.
* **불변식(SDK).** 모든 서버에 내놓은 미사용 credit + 착수 중인 수 ≤ P. 과배정이 없다.
* **평상시.** `Complete`의 credit 비트가 그 슬롯을 같은 서버에 되돌린다. 일이 이어지는 서버에서는 추가 프레임이 없다.
* **굶음 신호.** 서버는 "이 참여자가 받을 수 있는 일이 credit보다 많다"를, 그 참여자가 credit을 한 번 낼 때마다 많아야 한 번 알린다.
  * 그 참여자의 마지막 credit을 쓰는 `Assign`을 보낼 때 일이 더 기다리고 있으면 `more` 비트를 세운다(비용 1비트).
  * credit이 0인 참여자가 받을 수 있는 일이 새로 기다리게 되면 `Pending{채널}`을 보낸다.
  * 참여마다 통지 비트 하나로 관리한다. 둘 중 하나를 보내면 켜고, 그 참여자가 credit을 내면 끈다. 켜져 있는 동안은 다시 보내지 않는다. 포화 상태에서도 신호가 이벤트마다 나가지 않는다.
* **옮기기.** 워커는 빈 슬롯을 굶는 서버들에 돌아가며 준다. 빈 슬롯이 없으면 다른 서버에 주차된 미사용 credit을 `Credit{회수}`로 거둬 옮긴다. 서버는 실제로 남아 있던 수를 `CreditReturned{n}`으로 답한다. 회수와 엇갈려 이미 나간 `Assign`은 쓴 것으로 센다.
* 왕복은 부하가 서버 사이로 옮겨 갈 때만 생긴다. 타이머가 없다. 처음에는 슬롯을 서버들에 고르게 나눠 내므로, 부하가 낮을 때는 어느 서버든 바로 배정한다.
* 지금은 워커가 실행 직전에 가져가므로 이 문제가 없다(`worker/lane.rs:118~125`). push로 바꾸면서 함께 풀어야 한다.

**기한.**
* **lease는 장부가 배정한 순간부터 잰다.** 송신 대기가 lease에 들어간다. `Assign`은 쓰기를 시작하는 순간의 남은 시간을 싣는다.
  * 소켓에 다 쓴 순간부터 재면, credit을 낸 뒤 멈춘 워커(TCP는 살아 있음)에게 가던 큰 본문은 쓰기가 끝나지 않아 lease가 시작되지 않는다.
  * 회수 때 아직 쓰기를 시작하지 않은 `Assign`은 송신 큐에서 뺀다(그 송신 순번은 취소 표시로 메운다). 회수된 몫의 credit은 돌려주지 않는다. 멈춘 워커가 묶을 수 있는 것은 credit만큼, lease 동안뿐이다.
* **기한 휠 하나.** lease 기한과 `not_before`를 함께 쥔다. 가장 이른 기한에 (논리 id, 표지)를 장부에 내고 장부가 정한다. 외부 등록이 없어도 진행된다.
* **회수.** 같은 논리 id로 원래 순서 자리에 되돌리고, 실패 횟수를 올리고, 다음 배정에 새 표지를 준다.
* **연장.** 긴 작업은 `Extend`로 늘린다. SDK가 lease의 절반에서 자동으로 보낸다.
* 완료가 기한 뒤에 왔어도 회수 전이면 받는다. 지금과 같고, 계약에 적는다.

**재기동을 넘는 착수.**
* 저널의 `Claim` 레코드에 표지, lease 길이, 착수 자격을 넣는다. 복구는 착수 상태를 **그대로 복원**하고 기한을 "재기동 시각 + lease 길이"로 다시 건다.
* 워커는 실행을 계속하고, 다시 붙은 뒤 같은 표지로 `Complete`·`Extend`·`Release`를 보낸다. 귀속은 지금처럼 자격으로 검사한다(`state/mod.rs:561`).
* 실패 횟수는 재기동으로 오르지 않는다.
* 지금은 서버만 재시작해도 착수 중인 전량이 즉시 다시 풀리고 retry가 오른다(`state/mod.rs:182~190`). 워커는 살아서 실행 중인데 같은 일이 다른 워커에게 또 간다. 배포마다 생긴다.
* `Claim` 레코드가 디스크에 닿기 전에 서버가 죽으면 그 이벤트는 대기로 복원된다. 이 경우의 재실행은 최소 1회 계약 안이다.
* 연결이 끊긴 것만으로는 회수하지 않는다. 기한이 정한다.

**반환과 지연.**
* **`Release{표지, 지연, 실패}`.** 워커가 일을 돌려준다.
  * 실패 = 아니오: 실행하지 못했다(종료, credit 이동). 실패 횟수가 그대로다.
  * 실패 = 예: 시도했고 나중에 다시 하겠다(하류 503). 실패 횟수가 오른다.
  * 지연이 있으면 그 뒤에 다시 보인다(휠).
* **`Register{not_before}`.** 등록과 후속에 가시 시각을 줄 수 있다.
* 몇 번, 얼마 뒤인지는 워커가 정한다. 서버는 시각만 지킨다.
* 지금은 실패를 완료로 끝내거나 lease 만료까지 붙잡는 것 말고 방법이 없다(1장). 재시도 간격이 lease 길이가 된다.

**만료.**
* 등록에 `expires`(길이)를 줄 수 있다. 장부는 배정 직전과 명시 착수 때 시각만 비교하고, 지난 것은 지우고 센다. 타이머가 없다.
* 요청자가 이미 포기한 요청을 과부하가 끝난 뒤에 처리하지 않기 위한 것이다. 채널 설정으로 지우는 대신 격리할 수 있다.

**격리(DLQ).**
* **한도는 한 곳에 둔다.** 채널 설정 `isolate_after: n`. 실패 횟수(lease 만료 회수 + 실패 반환)가 n을 넘으면, 장부가 그 이벤트를 원본·횟수와 함께 격리 채널의 착수용 이벤트로 **한 스텝에** 옮긴다. 내구성은 원 채널과 같다.
* SDK의 `max_retries`와 "핸들러 없이 완료"(`worker/lane.rs:180`)는 없앤다. 한도가 두 곳이면 SDK 쪽이 먼저 걸려, 느린 작업이 흔적 없이 사라지고 격리에는 닿지 않는다.
* 이것은 서버 정책 최소화([event-server-redesign.md](event-server-redesign.md)의 D11)를 바꾸는 결정이다. 정책 단어 금지 시험(`tests/static/architecture.rs:212~222`)에는 걸리지 않지만, 그 시험의 설명과 `config.rs:1~2`의 문장을 "격리 문턱 하나가 예외"로 함께 고친다.

**개별 심사와 도구.**
* 내용을 보고 건별로 고르는 워커는 관찰 연결로 머리만 있는 `Notice`를 받고, 작업 연결로 `Claim{id}`를 낸다. 지금의 경로 그대로다.
* 명시 착수도 커밋 가시성과 만료를 따른다.
* v4의 Offer 모드는 뺐다(7장).

**펜싱.** 착수 표지를 워커 `Context`에 펜싱 토큰으로 내준다. 계약에는 "비가역 부작용은 업무 키의 유일 제약이나 하류 멱등 키로 보호, 덮어쓰기형 저장은 토큰으로 펜싱"을 적는다.

**발송용 이벤트.** 등록 순간의 구독자 전원에게 간다. 대개 그 구독자는 프록시다(4장).

### 2.5 저장: 세그먼트 로그 하나, 인스턴스 둘 (비판 C8, C13)

저장 엔진은 세그먼트 로그 하나다. 파일 형식, 위치 읽기, pin, 이주가 같다. 인스턴스가 둘이고 성격이 다르다.

| | 영속 로그 | 휘발 로그 |
| --- | --- | --- |
| 무엇을 담나 | 영속 채널의 본문과 모든 순변화 레코드 | 휘발 채널의 본문 가운데 메모리에서 넘친 것만 |
| 언제 쓰나 | 등록할 때 항상 | 관리 메모리가 문턱을 넘을 때만 |
| 동기화 | fsync | 하지 않는다 |
| 재기동 | 체크포인트 + 꼬리로 복구 | **디렉터리를 비운다** |

**휘발 로그는 영속 로그와 섞지 않는다.** 디렉터리가 다르고, 저널이 아니다. 실행 중에 메모리를 넓히는 수단일 뿐이다(사용자 원문 9.4: "페이징은 어디까지나 실행중 메모리 활용기능").

**본문의 자리.**
* 장부 메타가 본문 위치를 쥔다: 캐시 참조 또는 (로그, 세그먼트, 오프셋, 길이).
* **영속 채널.** 등록 때 세그먼트에 한 번 쓴다. 이것이 디스크의 유일한 사본이다. 곧 배달될 본문은 캐시에도 둔다. 메모리가 문턱을 넘으면 캐시에서 **놓기만** 한다. 쓰기가 없다.
* **휘발 채널.** 본문은 캐시에만 있다. 메모리가 문턱을 넘으면 가장 나중에 배달될 것부터 휘발 로그로 옮기고(`Relocate`) 캐시에서 놓는다. 메타는 장부에 그대로 있다.
  * v3.2의 스왑 페이지, 스텁, 복원 경로는 없다. 메타와 본문이 이미 갈라져 있으므로 스텁은 메타와 같은 것이다.
* **배달.** 캐시에 없으면 읽기 스레드가 세그먼트에서 위치 읽기를 한다(2.2).

**세그먼트의 수명.**
* 세그먼트는 크기 S에서 넘긴다(8.2).
* 세그먼트마다 살아 있는 이벤트 수를 센다. 0이 되고, 읽는 쪽의 pin이 풀리고, (영속이면) 체크포인트가 그 앞을 덮으면 통째로 지운다.
* 사용자 전제("들어차고 신속하게 비워진다")에서는 대부분의 세그먼트가 금방 빈다. 압축이 거의 필요 없다.
* **이주.** 오래 남은 소수 이벤트가 큰 세그먼트를 붙잡으면, 로그 작성기가 그 본문을 현재 세그먼트로 옮겨 쓰고 장부가 `Relocate`로 위치를 바꾼다.
* 세그먼트는 이름을 첫 사용 전에 스스로 정의한다. 지금 저널과 같다(`journal/codec.rs:46~57`). 사전의 크기는 세그먼트 하나로 묶인다.

**영속 로그의 레코드(저널 형식 3).** `Register`(메타 + 본문), `Claim`(key, 표지, lease 길이, 자격), `Remove`, `Reclaim`(key, 실패 횟수), `Release`(key, 실패 횟수, 지연), `Relocate`(key, 새 위치), `Producer`(id, seq), `Generation`, `Name`.
* **원자성.** 한 완료의 변화(부모 제거, 후속 등록, 생산자 순번)는 한 프레임에 든다.

**체크포인트: 장부를 멈추지 않는다.**
* 내용: 살아 있는 이벤트의 메타(착수 상태 포함), 생산자 순번표, 이름, 덮은 로그 위치. 본문은 위치로만 가리킨다.
* **체크포인터 스레드가 "이전 체크포인트 + 꼬리 레코드"로 만든다.** 장부의 메모리를 읽지 않는다.
  * 체크포인트는 `WorkKey` 순이다. 꼬리의 메타 레코드로 변경표를 만들고(크기는 꼬리 레코드 수에 비례), 이전 파일을 차례로 읽으며 합쳐 새 파일을 쓴다. 본문은 건너뛴다.
  * 지금은 엔진 태스크가 큐 전체를 복제한다(`engine/mod.rs:403~407`). 대기가 많을 때 장부가 멈춘다.
* 계기는 꼬리 레코드 수다. 지금의 압축 규칙을 잇는다(8.2). 주기 타이머는 쓰지 않는다.
* 정상 종료 때 꼬리를 접어 체크포인트를 쓴다. 배포 뒤의 재기동이 체크포인트 읽기만으로 끝난다.

**복구.**
* 휘발 로그 디렉터리를 비운다.
* 체크포인트를 읽고 그 뒤 꼬리만 **스트리밍으로** 재생한다. 본문은 건너뛰고 필요할 때 읽는다. 복구 메모리는 메타 크기로 한정된다. 지금은 파일 전체를 메모리에 올린다(`journal/file.rs:50`).
* 착수 상태를 복원한다(2.4). 기한, `not_before`, `expires`는 원 길이로 다시 건다.
* 마지막 프레임의 미완성 꼬리만 잘라 낸다. **중간 손상은 멈추고 보고한다.** 지금은 중간 손상 뒤의 정상 프레임까지 잘라 낸다.
* **이전.** 지금의 형식 2 저널은 첫 기동 때 한 번 읽어 형식 3(체크포인트 + 첫 세그먼트)으로 옮긴다. 옛 파일은 성공한 뒤에만 지운다.

**저널이 없는 서버.** 영속 로그가 없다. 휘발 로그는 데이터 디렉터리를 주었을 때만 쓴다. 없으면 메모리만 쓰고, 고수위에서 생산 읽기를 늦춘다.

### 2.6 자원 한계와 흐름 제어

과부하로 거절하지 않는다는 원칙은 "모든 자원에 상한이 있고, 닿으면 입구를 늦춘다"로 구현한다. 상한이 없는 자원이 하나라도 있으면 그 자원이 서버를 멈춘다.

**회계.** 할당 전에 바이트로 센다: 장부 메타, 본문 캐시, 큐, 연결 미송신, 로그 버퍼, 생산자 순번표, 키 창, 이름 사전. 합이 **관리 메모리**다.

**메타는 내리지 않는다.** 그래서 관리 메모리는 대기 이벤트 수에 비례하는 몫을 갖는다. 이 몫이 상한을 넘지 않게 하는 것은 입구의 흐름 제어다(아래 4번).
* 작은 본문에서는 메타 메모리가 디스크보다 먼저 찬다. 메타 180 B(가정, M3에서 잰다), RAM 64 GB, 디스크 1 TB면 평균 본문이 약 2.8 KB 아래일 때 그렇다(64 GB ÷ 180 B ≈ 3.6억 건, 1 TB ÷ 3.6억 ≈ 2.8 KB).
* 소비가 멈춘 채 10만 건/초가 들어오면 약 1시간 만에 닿는다. 디스크 고수위만 보면 그 전에 메모리가 넘친다.

**닿았을 때 하는 일(싼 것부터).**
1. **본문을 내린다.** 영속 본문은 캐시에서 놓는다. 휘발 본문은 휘발 로그로 옮긴다(2.5).
2. **관찰 연결의 대기를 디스크로 내린다.** 연결별 미송신이 메모리 몫을 넘으면 뒤쪽을 그 연결의 디스크 큐로 내리고, 쓸 수 있을 때 올린다. 영속 본문은 참조만 내린다.
3. **연결별 상한을 넘은 연결을 끊는다.** 디스크 큐가 상한(8.2)을 넘으면 `Bye{slow}`로 끊는다.
   * 발송은 1회성 계약이다(0.3). 프록시가 죽으면 잃는다는 계약(4장)보다 더 많이 보관할 이유가 없다.
   * 상한이 없으면 읽지 않는 프록시 한 대의 몫이 디스크를 채우고, 고수위가 서버 전체의 생산을 늦춘다. 발송 50 MB/s에서 여유 100 GB는 약 33분에 찬다(100 GB ÷ 50 MB/s).
   * 프록시는 이미 느린 사용자를 끊는다(`hub/task.rs:358~363`). 같은 격벽을 서버에도 둔다.
   * 작업 연결에는 이 큐가 필요 없다. 나가는 양이 credit의 바이트 한도로 묶이고, 배정된 몫은 lease가 지킨다.
4. **고수위에서 생산 연결의 읽기를 늦춘다.** 조건은 **디스크 또는 관리 메모리**다. 디스크 고수위에서는 그 전에 가장 큰 연결 디스크 큐부터 끊는다. 읽기는 저수위로 내려가면 다시 연다.
5. **작업 연결은 멈추지 않는다.** 완료의 후속 본문은 디스크로 흘려 읽는다. 완료·체크포인트·이주가 쓸 메모리, 큐, 디스크 공간을 예약해 둔다.
6. **저널 쓰기 실패는 엔진 정지다.** 지금과 같다(`engine/mod.rs:285~289`).

**재기동도 상한 안에 있다.** 복구 중 최고 메모리가 상한을 넘으면 서버가 다시 뜨지 못한다. 이것을 합격 기준으로 둔다(M3).

### 2.7 커밋 가시성과 오류 통보 (비판 C10, C4)

**커밋 가시성.**
* Strict에서 영속 채널 이벤트는 **등록이 커밋되기 전에는 어떤 경로로도 다른 연결에 보이지 않는다.** 배달, 통지, 구독 backlog, 명시 착수가 모두 그렇다.
* 슬롯에 필요 커밋 번호를 둔다. 배정과 backlog는 미커밋을 거르고, 명시 착수는 커밋까지 주차한다.
* 지금은 backlog와 착수 응답이 게이트를 우회한다(1장).
* Scheduled는 보이는 것을 디스크 뒤로 미루지 않는다. 그것이 두 모드의 유일한 차이다(2.3).
* 시험: 파일 쓰기를 막고, 미커밋 id에 backlog·명시 착수·배달을 시도한다. 아무것도 보이지 않아야 한다.

**오류 통보.**
* 과부하로는 거절하지 않는다.
* 권한은 가능한 한 앞에서 검사한다. 작업 연결은 `Join`, 관찰 연결은 `Subscribe`가 답을 받는다. 생산 연결은 `Hello`에 쓸 채널을 선언하면 `Welcome` 전에 검사받는다.
* 그 밖의 설정·형식·충돌 오류는 **(연결, 종류)마다 첫 1회만** 짧은 `Fault`로 알린다. 이후는 서버 계수기로 센다.
* 종류: 권한 없음, 형식 오류, id 형식, id 충돌(같은 id 다른 내용), 후속 충돌, 순번 빈자리.
* 재전송 무시, 늦은 완료(표지 불일치), 만료 삭제는 정상이므로 알리지 않고 센다.
* 근거: 정상 상태에서는 0건이라 비용이 없다. 설정 실수 때는 통보 한 번이 성공 확률 0인 재발송 루프 전체를 없앤다.

### 2.8 여러 서버 운영

* **서버 사이 상태 공유는 없다.**
* **라우터(별도 작성)는 생산 경로에만 둔다.** 같은 생산자는 같은 서버로 보내야 순번이 이어진다. 서버를 바꾸면 그 서버에서 새 순번으로 시작한다.
* **워커와 프록시는 모든 서버에 직접 붙는다**(NSQ 소비자 방식). 착수, 완료, 재접속이 같은 서버로 간다.
* **서버 목록.** SDK는 서버 목록 공급자(현재 목록 + 변경 알림)를 받는다(2.9). 구현(정적 설정, 라우터 연동)은 범위 밖이다. 목록이 바뀌면 SDK가 붙고 뗀다. 서버를 늘렸는데 워커가 모르면 그 서버의 일은 아무도 가져가지 않는다.
* **결과 경로.** 결과는 요청을 처리한 서버에서 나온다. 완료의 후속이 그 서버에 등록되기 때문이다.
  * **응답 채널은 요청자 인스턴스마다 하나다.** 요청자는 그 채널을 서버마다 접속 때 한 번 구독하고, 요청에 `reply`(그 채널)와 `correlation`을 싣는다. 결과와 스트림 조각은 `correlation`으로 가른다.
  * 요청마다 채널을 만들면 요청당 구독·해지가 서버 수만큼 생긴다. 요청 5만/초, 서버 4대면 구독 연산이 40만/초(5만 × 4 × 2)이고, 실제 일(등록·착수·완료 15만 전이/초)보다 많다. 이름 사전도 요청마다 새 항목을 받는다.
  * 프록시의 인증 응답이 이미 이 방식이다(`hub/task.rs:330~336`).
* **부하 신호.** 관찰 연결의 `Stats` 요청에 서버가 값을 복사해 답한다: 대기 수, 가장 오래된 대기의 나이, 착수 중 수, 디스크·메모리 수위, 계수기. 라우터와 운영자가 쓴다. 주기 보고는 없다.
* **서버를 내릴 때(drain).** 운영 명령으로 drain 상태에 들어간다. 생산 연결을 `Bye{draining}`으로 닫고 새 생산 연결을 받지 않는다. 배달과 완료는 계속한다. 대기와 착수가 0이면 종료해도 잃는 것이 없다. `Stats`로 확인한다.
* **서버를 잃을 때(사용자 결정의 대가).**
  * 대기 이벤트는 재기동까지 기다린다. 디스크를 잃으면 잃는다.
  * 클라이언트는 시간 초과 뒤 다른 서버로 같은 논리 id로 보낸다. 죽었던 서버가 재기동하면 옛 이벤트가 다시 실행될 수 있다.
  * 그래서 워커 업무 멱등이 필수다. NSQ도 같은 계약을 문서화한다.

### 2.9 클라이언트 SDK 계약

지금 클라이언트는 연결 하나에 재접속도 버퍼도 없다(`ruvent-client/src/remote/mod.rs:63~136`). 아래가 `ruvent-client`의 새 계약이다. SDK를 쓰지 않는 클라이언트도 같은 계약을 지켜야 한다.

**공통.**
* 서버 목록 공급자를 받아 서버마다 역할별 연결을 연다.
* 재접속은 지수 백오프 + full jitter다.
* `Welcome`의 서버 id·세대가 바뀌었으면 재기동이다. 아래 규칙대로 잇는다.

**생산자.**
* 서버마다 생산 연결 하나. 생산자 id는 기동 때마다 새로 만든다(영속 outbox가 있을 때만 보존).
* **미확인 버퍼.** 보낸 것을 `Committed`가 올 때까지 쥔다. 상한은 바이트다(8.2). 가득이면 `send`가 **기다린다.** 거절이 아니라 호출자에게 가는 흐름 제어다.
* **재접속.** `Welcome.resume` 이하를 버리고 그 뒤를 같은 번호로 다시 보낸다. 서버가 기록을 잃었으면(2.3) `resume + 1`부터 다시 번호 매긴다.
* `Bye{superseded}`는 다시 붙지 않고 오류로 올린다.
* **재시도 계약.**
  * 같은 업무는 **같은 논리 id**로 다시 보낸다.
  * 재시도 예산을 둔다(정상 요청 대비 비율 상한, 8.2).
  * 업무 결과의 기한과 등록 커밋의 기한을 분리한다. 커밋은 누적 확인으로 안다.
  * 결과 기한이 있는 요청은 등록에 `expires`를 싣는다. 기한을 넘기면 `Delete`로 취소를 시도한다.

**워커.**
* 서버마다 작업 연결 하나. 채널에 `Join`한다.
* **슬롯과 credit.** 2.4의 불변식과 옮기기 규칙을 구현한다. 서버별 (미사용 credit, 착수 중, 굶음 표시)를 쥔다.
* **핸들러의 끝.**
  * 성공: `Complete`(후속 포함).
  * 나중에 다시: `Release{지연, 실패 = 예}`. 핸들러가 지연을 정한다.
  * 영구 실패: 실패 후속과 함께 `Complete`. 지금과 같다(`worker/lane.rs:195`).
  * 횟수 한도는 서버의 `isolate_after`가 정한다. SDK는 횟수를 판단하지 않는다.
* **lease.** 절반에서 `Extend`를 자동으로 보낸다. 핸들러에는 표지를 펜싱 토큰으로 준다.
* **종료.** credit을 회수하고, 아직 실행하지 않은 것은 `Release{실패 = 아니오}`로 돌려주고, 실행 중인 것은 끝까지 한다.
* **서버 재기동.** 실행을 계속한다. 완료는 미확인 버퍼에 두었다가 다시 붙은 뒤 같은 표지로 보낸다.

**요청자(요청–응답).**
* 인스턴스마다 응답 채널 하나를 만들고 서버마다 한 번 구독한다(2.8).
* 대기자 표(`correlation` → 대기자)를 쥔다. 응답, 취소, 기한, 연결 상실 중 먼저 온 것으로 끝난다.

## 3. 대용량 페이로드 (비판 C15)

* 큰 페이로드는 조각 시리즈로 보낸다. 조각은 순서가 없고, **여러 서버로 흩어져 도착해도 된다.** 조각 워커는 조각마다 개별 파일로 쓰고 바로 완료한다.
* 조각 채널의 워커는 credit의 바이트 한도로 받을 양을 정한다. 조각 하나가 16 MiB(본문 상한)를 넘지 않는다.
* **완성 판정은 저장소가 한다.** `put`은 파일 내구성이 확보된 뒤 공유 비트맵의 비트를 조건부로 세운다. 완성을 만든 호출 하나만 `sealed_now`를 받는다.
* **비트맵 분할.** 큰 시리즈(1 GiB ÷ 256 KiB = 4,096조각)는 비트맵을 블록(예: 1,024비트)으로 나눈다. 블록이 찰 때만 완성 계수를 조건부 갱신하므로, 경합이 블록 수만큼으로 준다. S3 조건부 쓰기는 객체 하나 단위이기 때문이다.
* **의무를 상태와 함께 남긴다(outbox).**
  * `SEALED + 조립 의무`를 저장소의 한 원자적 변경으로 남긴다.
  * `ASSEMBLED + 결과 발행 의무`도 한 원자적 변경으로 남긴다.
  * 독립 발행자(별도 프로세스)가 남은 의무를 읽어 결과 R을 **불변 논리 id**로 등록하고, 커밋 확인(2.3)을 받은 뒤 의무를 지운다. 알림을 놓쳐도 미완 의무를 다시 찾을 수 있다.
  * R이 두 번 등록돼도 논리 id가 같으므로 소비자는 id로 멱등 처리한다. 논리 id는 회수로 바뀌지 않는다(2.1).
* **조립 시도.** 만료·인계·펜싱을 둔다. 임시 객체는 세대별로 정리한다.
* **저장소 계약**(v3.2 3.2 유지): `open(manifest)`, 조건부 `put`, `begin_assemble`, 상태 `OPEN → SEALED → ASSEMBLED → PUBLISHED`(또는 `ABORTED`, `FAILED`), 공개 완료 오프셋까지의 `read`, `abort`·`remove`와 세대 묘비.
* **S3 계열.** multipart part는 마지막을 빼고 최소 5 MiB, 번호는 1~10,000이다. 조각 하나를 part 하나에 대응시키지 않는다.
* **큰 결과.** 저장소에 쓰고 결과 이벤트에는 참조만 싣는다. 받는 쪽은 공개 완료 오프셋까지 자기 속도로 읽는다.
* **채널 단위 저널 제외.** `volatile_channels: [패턴]`. 영속 부모 + 휘발 후속, 휘발 부모 + 영속 후속의 결과표를 시험으로 고정한다.

## 4. 프록시

* **역할: 발송 팬아웃 계층.** 프록시는 맡은 채널을 서버마다 한 번 구독하고, 받은 엔벨롭을 자기 클라이언트들에게 나눈다. 서버의 발송 비용은 프록시 수에 비례한다.
* **상향 연결은 서버마다 하나다.** 지금 허브는 상향 연결이 하나다(`hub/task.rs:208~229`). 서버 목록 공급자를 받아 모든 서버에 붙도록 넓힌다(2.8).
* **느린 클라이언트는 프록시가 끊는다.** 지금과 같다(`hub/task.rs:358~363`). 서버는 프록시 연결 하나만 본다.
* **프록시가 느려지면** 서버는 그 연결의 대기를 디스크 큐로 받아 주고, 상한을 넘으면 끊는다(2.6). 프록시는 다시 붙는다. 그사이의 발송은 잃는다.
* **프록시가 죽으면** 그 프록시로 가던 발송은 잃는다. 발송은 1회성이다. 클라이언트는 다른 프록시에 다시 붙는다.
* **원 엔벨롭 스트림.** 허브가 `Arc<Envelope>`를 나눈다. 바이트 payload를 JSON 텍스트로 바꾸지 않는 경로를 둔다.
* **요청 교환 `Proxy::exchange(event)`.**
  * 프록시는 2.9의 생산자이자 요청자다. 요청을 순번과 함께 등록하고, 커밋 확인으로 등록 성공을 안다.
  * 응답은 프록시 인스턴스의 응답 채널 하나로 받는다(2.8). 요청마다 구독하지 않는다. 지금의 인증 응답 경로(`hub/task.rs:330~336`)를 일반화한다.
  * 대기자는 (연결 세대, `correlation`)에 귀속된다. 응답, 취소, 전체 기한, 연결 상실 중 먼저 온 것으로 끝난다.
  * 기한이 지난 요청은 `expires`로 서버의 대기열에서도 사라진다. 이미 착수된 요청은 끝까지 간다. 그래서 기한 뒤에도 같은 논리 id로 결과를 다시 조회할 수 있어야 한다.
* **사용자 구독의 불변식.** 신규 join은 자기 구독 표지를 기다리고, 이미 활성인 같은 사용자의 재호출은 즉시 성공한다(`hub/channels/mod.rs:156~169`).
* **접두사 구독(서버).** 서버의 구독 집합이 정확 이름과 접두사를 받는다. 정확 이름은 해시, 접두사는 `.` 경계 트라이로 찾는다. 프록시는 사용자 채널 묶음을 접두사 하나로 구독할 수 있다. 지금 권한 패턴의 `starts_with`(`names/mod.rs:172`)와의 차이를 시험한다.

| M3 | 메모리 상한의 2배·10배 대기열, 본문 64 B와 4 KiB. 재기동 | 관리 바이트 최고치, 이벤트당 메타 크기, 어느 고수위가 먼저 걸리는지, 복구 시간과 **복구 중 최고 메모리**(지금 방식 대 체크포인트 + 꼬리), 체크포인트 중 장부 지연 |
| M4 | 조각 시리즈 64 MiB ~ 1 GiB, 조각 256 KiB ~ 4 MiB, 다중 프로세스·다중 서버 | 수신 → 내구성 → 완료 시간, 비트맵 경합, 병합 바이트 |
| M5 | 영속: 세그먼트 크기별, 오래 남는 이벤트 비율 0·1·10 %. 휘발 넘침 | 유효 레코드 바이트 대비 디스크 쓰기 바이트(이주 포함), 세그먼트 삭제 지연, 체크포인트 비용, 휘발 `Relocate` 쓰기량 |
| M6 | 요청 교환 | 요청당 지연, **요청당 서버 제어 연산 수** |
| M7 | 확인: 확인 끔, 누적 확인 N = 64·256·1,024, 지금의 건별 응답. 과부하에서 같은 id 재전송과 새 id 재발송, `expires` 유무 | 서버 CPU·프레임 수, 클라이언트 미확인 버퍼 최고치, 과부하 제거 뒤 정상 처리율 회복 시간 |
| M8 | 장애 시험 | 아래 일곱 가지 |

M8 장애 시험:
1. 등록 append 전, 커밋 후 확인 전, 완료 커밋 후 결과 전달 전에 서버를 죽이고 재기동한다. 확인된 생산자 순번 유실 0(Strict와 Scheduled 모두), 같은 순번의 이중 적용 0, 복구 시간을 본다.
2. 워커 정지. 첫 워커가 TCP 읽기를 영구히 멈춘 상태에서 다른 워커가 대기 건을 처리하는지 본다. **credit을 낸 뒤 멈춘 워커**(본문 1 MiB)에 배정된 몫이 lease 뒤에 다른 워커로 가는지 본다. 생산 연결을 막아도 작업 연결의 완료가 진행되는지 본다.
3. 파일 쓰기를 막고 미커밋 id의 backlog·명시 착수·배달을 시도한다(2.7).
4. 세그먼트 이주·삭제와 배달 읽기, 휘발 `Relocate`와 체크포인트를 겹친다.
5. 조각의 마지막 비트, 조립 공개, R 커밋, 의무 삭제 각각의 직전·직후에 죽인다.
6. **착수 중에 서버를 정상 재시작한다.** 워커는 살아 있다. 다시 배정된 수 0, 실패 횟수 변화 0, 원래 워커의 완료가 받아들여지는지 본다.
7. **같은 producer_id로 두 인스턴스를 띄운다.** 조용히 버려진 등록 0, 양쪽이 사유를 받는지, 서로 끊기를 되풀이하지 않는지 본다.

## 6. 단계

각 단계는 테스트·문서·`cargo xtask verify`·커밋으로 끝낸다. 측정이 있는 단계는 보고서를 남기고, 보고서에 합격 기준과의 비교를 적는다. 모든 단계에 **회귀 금지선**(8.2)이 걸린다.

순서의 원칙: **명세 → 측정으로 구조 선택 → 운송 → 의미 → 저장 → 분배.** 운송을 먼저 바꾸고 그 위에 기능을 한 번만 쓴다.

## 7. 기각한 대안

| 대안 | 기각 이유 |
| --- | --- |
| 서버 안 파티션·복제(비판 K1·K8) | 사용자 결정: 독립 서버를 부하에 맞게 여러 대. 대가(서버 상실 시 대기 이벤트 대기·유실)는 계약에 적는다(2.8) |
| 순차 제안 + 지수 재순회(v3) | 첫 워커가 읽지 않으면 뒤 워커가 많아도 멈춘다. 재순회는 워커 상태를 모른 채 묻는 폴링이고 상한이 없다. credit으로 대체(2.4) |
| Offer 모드(v4) | 개별 심사는 `Notice` + `Claim{id}`로 이미 된다. Accept/Decline 왕복, 응답 기한 타이머, 거절 집합 상태를 따로 둘 이유가 없다 |
| 서버마다 credit을 고정 분할하거나 전부 내기 | 고정 분할은 부하가 몰린 서버에서 1/S만 쓴다. 전부 내면 P × S건이 배정돼 lease를 태운다. 굶음 신호 + 옮기기(2.4) |
| credit을 주기적으로 다시 나누기(NSQ 클라이언트 방식, 확인 필요) | 주기 타이머다. 부하가 옮겨 갈 때만 움직이면 된다 |
| lease를 소켓에 다 쓴 순간부터 재기(v4) | 멈춘 워커에게 가던 큰 본문은 lease가 시작되지 않아 묶인다. 배정 시점부터 잰다 |
| 재기동 때 착수 중인 것을 모두 회수(지금, v4) | 서버 배포마다 살아 있는 워커의 일이 다시 풀리고 실패 횟수가 오른다. 착수 상태를 복원한다 |
| 끊기면 배정분 즉시 회수 | 원격 실행기 이중 실행. 기한이 정한다 |
| 재시도 한도를 SDK와 서버 두 곳에(v4) | SDK 쪽이 먼저 걸려 격리에 닿지 않고, 느린 작업이 흔적 없이 사라진다. `isolate_after` 한 곳 |
| 수신 확인 전면 제거(v3.3) | 클라이언트가 보낸 것을 언제 버려도 되는지 영원히 모른다. 누적 확인은 건별 응답의 0.4%다(2.3). 휘발 방송 연결은 끈다 |
| 재접속 때만 순번 하나 알림(비판 초안) | 연결이 살아 있는 동안 재전송 버퍼를 비울 수 없다 |
| 생산자 id를 기본으로 영구 보존(v4) | 버퍼가 메모리뿐이면 보존할 이유가 없고, 설정에 고정한 id를 복제본이 함께 쓰면 조용히 버려진다. 기동마다 새로 |
| `Welcome`에 커밋 순번 주기(v4) | 적용됐지만 미커밋인 구간과 번호가 겹친다. 적용 순번을 커밋 뒤에 준다 |
| 1시간 시간 창 키 맵을 주 멱등 수단으로(v3.3) | 메모리가 처리량 × 창에 비례(100만/초·1시간 약 148 GB). 재기동·서버 변경에 무력. 생산자 순번이 주, 키 창은 채널이 켤 때만 |
| 중복 후속은 건너뛰고 완료 적용(v3.3) | 내용이 다른 필요한 일을 영구히 빠뜨린다. 같은 내용만 생략, 다르면 충돌 |
| 거절 전부 생략(v3.3 E16) | 설정 실수 때 성공 확률 0인 재발송이 끝없이 이어진다. 첫 1회 통보 |
| 영속 채널도 메모리 우선 + 스왑(v3.2) | 본문이 이미 디스크에 있는데 다시 쓴다. 재기동이 전체 재적재다. 세그먼트 로그 |
| 휘발 채널 스왑 페이지 + 스텁(v3.2, v4) | 저장 엔진이 하나 더 생긴다. 메타와 본문이 갈라진 장부에서는 넘친 본문을 휘발 로그로 옮기면 끝난다 |
| 저널 파일을 휘발 페이징에 재사용(v3, v3.1) | 휘발 본문은 재기동 때 버리는 것이 맞다. 휘발 로그는 영속 로그와 디렉터리도 수명도 다르다 |
| 장부 메모리에서 체크포인트 뜨기(지금의 압축) | 대기가 많을 때 장부가 멈춘다. 체크포인터가 이전 체크포인트 + 꼬리로 만든다 |
| 연결 소유자가 콜드 본문을 직접 읽기(v4) | 그 소유자의 모든 연결이 멈춘다. 읽기 스레드 |
| 회수 때 id 교체(지금) | 이벤트 고유키가 바뀌어 멱등과 결과 소비자 규칙이 깨진다. 시도 표지로 구분 |
| 혼합 연결 하나 + TCP 흐름 제어(v3) | 메모리가 차면 완료도 못 읽는다. 연결 역할 분리 |
| 느린 수신자를 버퍼가 차는 즉시 끊기(G5) | 순간 정지에도 끊긴다. 디스크 큐로 받아 준다 |
| 느린 수신자 디스크 큐에 상한 없음(v4) | 한 프록시의 정지가 디스크를 채워 서버 전체의 생산을 늦춘다. 연결별 상한 |

### 9.1 코덱스 리뷰 1회차(v1 → v2)

### 9.2 사용자 결정(v2 → v3)

> 등록 착수 완료는 하나의 쓰레드가 맞아. 그래야 원자성유지에 힘이 안들기 때문이야. 하지만 등록 후 쓰레드 통지는 별도의 쓰레드 풀이 처리하지.

> … 단일 파일핸들에 파일을 붙이는게 아니라 개별 파일 핸들을 통해 조각을 임시 저장하고 이후 병합 파일을 생성한다면 더욱 빨리 메모리를 비워줄 수 있지.

> … 이벤트서버의 메모리 제한이 가까워지면 오히려 메모리를 차지하는 이벤트를 페이지 단위로 영속화하여 언로드 했다가 다시 페이지단위로 로드하는 구조로 문제를 해결하지 이벤트 송수신 거부는 없다.

> 모든 워커서버가 거부한 경우 약간 딜레이를 줬다가 다시 순회시키는 로직이 적합하겠지. 처음엔 매우 작은 5ms정도의 딜레이로 시작해서 거부가 한바퀴돌때마다 2배씩 증가시키면 충분할거라 생각해

지금 남은 것: 단일 장부, 장부 밖 I/O, 조각별 파일과 병합, 과부하 거절 없음, 휘발 본문을 디스크로 내렸다 올리기. 지수 재순회는 credit으로 대체했다(7장).

### 9.3 코덱스 리뷰 2회차(v3 → v3.1)

### 9.5 사용자 결정(v3.2 → v3.3)

> 1. 이벤트 등록은 멱등을 제공해야해. 멱등의 근간은 이벤트 고유키와 행위의 조합이다. … 헌데 고성능 이벤트서버는 모든 이벤트 수신에 대해 수신완료 반송을 하지 않는다.
> 2. 이벤트 서버 입장에서의 멱등은 롱텀으로 보장하지 않는다. …
> 6. 하지만 등록, 착수, 완료는 멱등을 보장해야한다.
> 7. 여러 이벤트 송수신의 이상점은 클라이언트가 알아서 책임진다.

> 거절은 안보내. 그런것들은 전부 부하를 일으켜 … 모든 부하를 클라이언트로 옮겨야 서버가 고가용상태가 된다.

지금 남은 것: 등록·착수·완료의 멱등(생산자 순번 + 상태 기계 + 선택 키 창), 평상시 건별 응답 없음, 이상 처리의 클라이언트 책임(SDK 계약으로 구현), 서버 사이 상태 공유 없음. 바뀐 것: 영속 경로의 누적 확인, 설정 오류 첫 1회 통보. 비판 검토에서 반증했고, 사용자가 v4 작성을 승인했다(9.6).

1. "연산 하나 = 프레임 하나"가 지금의 원자성: 부정확. append 프레임 하나에 여러 호출이 든다.
2. "이벤트는 커밋 뒤에만 다른 연결에 보인다": 부정확. backlog와 착수 응답이 게이트를 우회한다.
3. "모든 호출이 `Reply`를 받고 등록은 Strict 커밋 뒤": 부정확. 생성만 하고 도달은 보장하지 않으며, 발송용은 비게이트다.
4. "같은 완료 안의 같은 id는 형식 오류": 부정확. `Duplicate`다.
5. "Strict에서 적용 뒤 커밋 전에 죽으면 상태와 키가 함께 사라진다": 부정확. 프레임이 디스크에 남은 뒤 통지 전에 죽을 수 있다.
6. "응답 제거로 연산마다 프레임·소켓 쓰기가 하나씩 준다": 근거불일치. writer가 이미 묶어 쓴다.
7. "저널 작성기를 장부 밖으로 옮긴다"가 새 변화: 근거불일치. 이미 별도 태스크다.

### 9.7 Fable 리뷰 1회차(v4 → v4.1)

* 리뷰 조건: Fable 5.2, effort xhigh, 대상 `f92f89b`. 독립 리뷰이고, 기준은 0.1의 목적과 "근거는 정상 운영에서 일어나는 상황만"이다.
* **판정: 조건부.** 뼈대(단일 장부, 메타·본문 분리, 세그먼트 로그, 누적 확인, credit, 프록시 팬아웃)는 목적에 맞다. 그대로 구현하면 정상 운영에서 목적을 깨는 곳이 여덟 군데 남는다.
* **목적 수준 지적 8건(높음). 모두 반영했다.**

| # | 지적 | 반영 |
| --- | --- | --- |
| G1 | 여러 서버에서 워커 credit을 어떻게 나누는지 없다 | 굶음 신호 + 옮기기(2.4), SDK 불변식(2.9) |
| G2 | 서버 재기동이 착수 중 작업을 전부 회수한다 | 착수 상태 복원(2.4, 2.5) |

| G4 | 느린 수신자 디스크 큐에 상한이 없다 | 연결별 상한(2.6) |
| G5 | 메타 메모리가 찰 때의 조치가 없다 | 고수위 = 디스크 또는 관리 메모리(2.6) |
