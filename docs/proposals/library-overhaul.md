# 라이브러리 개편 계획: 착수 분배, 대용량 페이로드, 프록시 교환

상태: **승인 대기 v2** (2026-11-23). 코덱스 리뷰(gpt-6.2-astra, high)의 지적 12건을 코드로 확인하고 반영했다(9장). 승인 전에는 코드를 바꾸지 않는다.

apibond 재구축([apibond-on-ruvent.md](apibond-on-ruvent.md))은 이 개편을 실제 적용에서 검증하는 프로젝트일 뿐이다. 본론은 라이브러리다.

## 0. 원문과 지킬 원칙

> apibond는 원래 라이브러리를 실적용하면서 일어나는 일을 검토하기 위한 프로젝트일뿐이야. 당연히 라이브러리를 전면개편하는게 더 중요하다.
> 대용량 파일 처리에 대한 의견도 부족하고 내가 제안한 기초적인 이벤트 워커 분배에 대해서도 보다 성능과 처리량, 동시성을 고려하여 설계적으로 보완점을 찾는 과정도 없었다.

분배 모델과 대용량 처리의 원문은 [apibond-on-ruvent.md](apibond-on-ruvent.md) 1장에 그대로 있다. 요지는 다섯 가지다.
* 서버 안 전달 풀이 이벤트마다 전달자를 배정한다.
* 워커 서버에 등록순으로 순차 통지하고, 거절하면 다음 워커로, 모두 거절하면 처음부터 다시 통지한다.
* 순서는 이벤트의 단락성(인과)으로 만든다.
* 큰 페이로드는 순번 조각 시리즈로 보낸다. 어느 워커든 조각을 처리하고, 다 맞춘 쪽이 결과 이벤트를 낸다.
* 서버의 역할(등록, 발송, 착수 원자성, 완료 시 제거)은 불변이다.

함께 지킬 원칙은 다음과 같다.
* 서버 규칙은 최소로 둔다(제안서 D11). 새 규칙을 더하지 않고 기존 규칙(같은 id 거절, 착수 표지 대조, 완료·후속 원자성, 기한 회수, 발송)만으로 해결한다.
* 라이브러리는 폴링하지 않고, 주기 타이머를 쓰지 않는다. 타이머는 선언된 곳에만 있다.
* 영속은 최소로 하고, 채널 단위로 저널을 제외할 수 있어야 한다.
* 이벤트 하나는 워커 하나가 가져간다.
* 원격 실행기는 연결이 끊겨도 일을 계속할 수 있으므로 Q6(b)를 택했다(끊김으로 즉시 회수하지 않고 lease로 회수).

## 2. 착수 분배

### 2.1 원문 모델을 그대로 구현했을 때의 문제

원문 모델: 전달자가 이벤트 하나를 맡아 등록순 워커에 제안 → 수락이면 끝, 거절이면 다음 → 모두 거절하면 처음부터.

| # | 문제 | 크기와 조건 |
| --- | --- | --- |
| A1 | 제안마다 왕복이 붙는다 | 거절 k번이면 네트워크 지연이 (k+1)·RTT다. 대기·처리 시간은 별도다. 포화 때 단계 수가 얼마나 되는지는 측정할 일이다 |
| A2 | 전달 풀이 왕복을 기다리며 묶인다 | 전달자 P개가 미결 제안을 하나씩 들고 있으면 처리량 상한은 P / (평균 단계 수 × RTT)다(리틀의 법칙). P=64, RTT=0.5 ms, 1단계면 128,000건/초다. 이 수치를 1장의 25만/초와 비교해 병목을 판정할 수는 없다(그 25만은 TCP 분배 용량이 아니다) |
| A3 | 포화 때 거절 폭풍 | 한 바퀴에 제안 W번과 거절 W번, 이벤트당 논리 메시지 2W개. R바퀴면 2WR개. 일을 못 하는 순간에 부하가 가장 크다 |
| A4 | "처음부터 다시"의 시점이 없으면 헛돈다 | 즉시 다시 돌면 바쁜 대기, 시간으로 돌면 주기 타이머가 된다 |
| A5 | 멈춘 워커가 전달자를 붙잡는다 | 응답 기한이 없으면 무한 대기, 있으면 타이머 하나와 그 기한만큼의 점유 |
| A6 | 등록순 우선은 부하를 앞쪽에 몰아준다 | 지역성에는 좋고, 뒤쪽 워커는 앞쪽이 찰 때까지 논다. 의도된 선택인지 명시해야 한다 |
| A7 | 공유 전달 풀을 한 채널이 점유한다 | 뜨거운 채널의 적체가 전달자를 모두 차지하면, 한가한 워커가 있는 다른 채널도 배정받지 못한다 |
| A8 | 수락 왕복의 비용 | 제안 → 수락 → 착수 응답 3메시지다. 다만 수락에는 "이 이벤트를 맡을지 워커가 판단한다"는 의미가 있다. 이 의미는 지켜야 한다(2.3 반환) |

### 2.2 보완 설계: 여유분(credit) 기반 배정과 이벤트별 반환

워커가 거절하려고 제안을 기다리게 하지 말고, **받을 수 있는 수를 미리 알리게** 한다(AMQP prefetch, HTTP/2 흐름 제어 창과 같은 방식). 판단이 필요한 이벤트만 워커가 돌려준다.

```text
워커: take(channel, 여유 c, 처리 타입, 워커 태그, lease)   ── 배정 참여 등록. 관찰 구독(subscribe)과 별개
등록 ─► 엔진(단일 작성자)
          ├─ 그 채널의 참여자 중 여유 > 0인 후보를 정책 순으로 고른다(타입이 맞고, 이번 라운드에 반환하지 않은 후보)
          ├─ 원자적으로 착수 표지를 찍고 그 후보의 여유 −1(슬롯은 이 배정에 묶인다)
          └─ Assign(완전한 엔벨롭 + 착수 표지)을 그 연결 송신 순서대로      ── 메시지 1개, 왕복 0
          후보가 없으면 대기 표에 둔다(보류)
워커: 시작 전에 반환 release(id, token, 이유) ─► 표지를 풀고 다음 후보로. 한 바퀴를 다 돌면 보류
워커: 완료(complete) ─► 그 배정의 슬롯을 한 번만 복원 ─► 그 채널의 보류분을 같은 규칙으로 배정
```

원문과의 대응:

| 원문 | 보완 설계 |
| --- | --- |
| 등록순 순차 통지 | 후보 순서는 `take` 순서. 정책 `priority`(원문대로 앞에서부터)가 기본. `rotate`는 채널 설정 |
| 1차 워커가 모두 일하는 중이면 다음 워커 | 서버가 여유 0을 알고 있으므로 묻지 않고 건너뛴다(A1, A3 제거) |
| 여러 이유로 거부하면 다음 워커 | 처리 타입처럼 미리 알 수 있는 조건은 배정 전에 거른다. 본문을 봐야 알 수 있는 조건(세션 소유 등)은 시작 전 `release`로 돌려준다. 왕복은 이 드문 경로에만 생긴다(A8의 의미 보존) |
| 모두 거부하면 처음부터 | 보류했다가 2.3의 "다음 라운드를 여는 사건"에서 처음부터 다시 배정한다. 시간이 아니라 사건이다(A4 제거) |
| 전달 풀, 다 바쁘면 기다림 | 배정 결정은 엔진 안의 상태 변경이라 네트워크를 기다리지 않는다(A2, A5 제거). 원문의 풀은 미결 전달 수를 제한하고, 여유는 워커의 실행 여유를 표현한다. 둘은 제한하는 자원이 다르므로 둘 다 둔다(2.3 송신 상한) |
| 순서는 단락성으로 | 그대로. 배정 순서는 보장하지 않는다 |
| 착수 마킹의 원자성 | 엔진이 배정과 동시에 찍는다. 반환·완료·lease 만료로만 풀린다. 한 시점에 유효한 착수는 하나(G1). 원격 부작용의 생애 전체 1회 실행은 G1의 범위 밖이다 |

메시지 수(이벤트 하나, 논리 메시지, 반환 없음, 구독·사전 정의·여유 보충 제외):

| | 지금(알림+경쟁) | 원문 그대로(제안) | 보완(여유 배정) |
| --- | --- | --- | --- |
| 일반식 | 4 + W + 2a (a = 실제 착수 시도 연결 수) | 7 + 2k (k = 거절 수) | 5 (+ 반환 r번이면 2r) |
| W=8, a=8, k=0 | 28 | 7 | 5 |

### 2.3 세부 규칙

**참여와 관찰의 분리.**
* `subscribe`는 지금처럼 관찰이다(발송용 이벤트 수신, 대기 목록 조회).
* 배정 참여는 새 호출 `take(channel, credit, types, worker, lease)`다. 엔진은 `Claim` 권한을 이때 검사한다.
* 관찰만 하는 연결에는 착수용 본문과 토큰이 가지 않는다.
* `subscribe`의 대기 목록과 명시 `claim(id)`는 도구용으로 남긴다. 명시 착수는 여유 슬롯을 쓰지 않는다. 같은 대기 이벤트를 자동 배정과 명시 착수가 다퉈도 유효 토큰은 하나다.

**여유 회계: 슬롯은 배정에 묶인다.**
* 여유는 (참여 세대, 채널) 단위다. `take`가 새 참여 세대를 연다. 재접속이나 다시 `take`하면 새 세대가 되고, 옛 세대의 슬롯을 새 세대에 더하지 않는다. 워커는 재접속 때 실제 가용량을 다시 알린다.
* 배정 하나는 (세대, 작업 키, 착수 토큰)에 슬롯 하나를 묶는다. 그 배정에서 **첫 유효 전이 한 번만** 슬롯을 복원한다. 유효 전이는 완료, 반환, 조기 반환(`credit_back(id, token)`: 실행기로 넘긴 뒤 lane 허가를 일찍 돌려줄 때) 셋이다.
* 다음 경우에는 복원하지 않는다.
  * 완료 응답 재전송
  * 잘못된 표지
  * 다른 연결에서 온 완료: 같은 자격의 완료는 받아들이되, 슬롯은 배정한 세대가 살아 있을 때만 그 세대에 돌려준다
  * 명시 `claim`의 완료
* lease 만료 회수는 작업을 다시 배정할 수 있게 할 뿐, 옛 실행기의 물리 슬롯이 비었다고 보지 않는다. 회수된 배정의 슬롯은 그 세대에 돌려주지 않는다(옛 실행기가 아직 돌 수 있다).
* 워커 쪽 규칙: lane 허가 하나 = 여유 하나다. 지금 lane은 허가를 완료 전에 돌려준다(`Released`). 새 lane은 허가 반환을 `credit_back` 한 번으로만 알리고, 완료는 슬롯 복원에 쓰지 않도록 `complete(…, credited=true)`로 표시한다. 이중 증가가 없다.
* 여러 채널이 한 실행 슬롯을 공유하는 워커(공유 실행기)는 채널마다 따로 여유를 알리면 초과 배정된다. 그래서 `take`에 **공유 풀 이름**을 줄 수 있고, 같은 풀의 채널들은 하나의 여유를 나눠 쓴다.

**반환과 라운드.**
* 반환 `release(id, token, 이유)`는 현재 토큰·자격을 검사한다. 반환은 `retry`를 올리지 않는다(실행하지 않았으므로). 표지를 풀고 그 배정의 슬롯을 복원한다.
* 이벤트마다 라운드 상태(이번 라운드에 반환한 후보 집합)를 둔다. 크기는 후보 수 W로 제한된다. 반환한 후보는 같은 라운드에서 그 이벤트의 후보가 아니다. 반환으로 복원된 슬롯은 **다른 이벤트**나 **다른 후보**에게는 여유가 되지만, 같은 이벤트를 같은 후보에게 다시 여는 사건은 아니다. 그래서 `A→B→A` 무한 순환이 없다.
* 모든 후보가 반환하면 이벤트는 보류되고 라운드 상태는 유지된다. 다음 라운드를 여는 사건은 다음 넷이다.
  * 새 참여(`take`), 새 세대
  * 워커의 명시 `ready(channel)`: 거절 사유가 풀렸다는 신호
  * 처리 타입·능력 변경
  * 보류 이벤트가 반환 외의 이유로 다시 대기 표에 들어옴(회수)

  이때 라운드 상태를 비우고 처음부터 배정한다.

**보류분이 깨어나는 사건(빠짐없이).**
* 그 채널 참여자의 슬롯 복원
* 새 참여·새 세대·`ready`
* 대기 표에 일이 생기는 모든 경로: 등록, 회수, 재기동 복구, 삭제 취소

회수는 회수된 이벤트의 **원래 채널**을 배정 대상으로 올린다. X 채널 등록이 일으킨 Y 채널 회수가 Y의 배정을 깨운다.

**진행 조건(문서화).** 회수는 Q6(b)대로 외부 등록 때 일어난다. 외부 등록이 영원히 없으면 만료된 착수도 회수되지 않는다. 타이머 없는 설계의 대가로 명시한다.

**공정성과 비용.**
* 채널마다 "여유 > 0인 참여자"를 정책 순으로 정렬한 색인을 둔다. 후보 찾기는 O(log W), 반환 제외는 라운드 집합 검사다.
* 엔진 한 차례에서 채널 하나가 배정할 건수·바이트에 상한을 둔다. 남은 일은 다음 차례에 잇는다. 큰 `+n`과 긴 대기가 겹쳐도 다른 채널의 p99를 밀어내지 않는다.
* `priority`의 뒤쪽 굶주림은 원문 의미(등록순)의 의도된 결과로 명시한다. 고른 분배는 `rotate`로 측정한다.

**송신 상한(원문 "전달 풀"의 역할).**
* 한 연결에 나가 있는 미시작 `Assign`의 수는 그 연결의 여유 합이다. 엔진은 여유 합이 연결 송신 버퍼 용량(`outbound`)을 넘지 않도록 `take`의 여유를 깎는다. 그래서 배정 때문에 송신 버퍼가 차서 끊기는 일이 없다.
* `Assign`은 다른 송신과 같은 연결 순서를 탄다. Strict에서는 그 이벤트의 등록이 디스크에 닿기 전에 공개되지 않는다(지금의 알림과 같은 게이트).
* lease 기산점은 `Assign`을 송신 버퍼에 넘긴 순간이다. Strict 대기나 송신 대기 중에는 lease가 흐르지 않는다.

**끊긴 워커.** Q6(b)를 유지한다. 끊기면 그 세대의 여유는 사라지고, 배정된 이벤트는 lease로 회수한다. 엔진이 **송신 버퍼에 넣지 못한** `Assign`(끊김과 동시에 남은 것)은 전달되지 않은 것이 확실하므로 즉시 대기 표로 돌린다. 이미 넣은 것은 전달됐을 수 있으므로 lease로 회수한다.

**발송용 이벤트.** 지금처럼 구독자 전원에게 즉시 간다. 불변.

**wire 전환.**
* 프로토콜 버전을 2로 올린다. v2는 `take`, `Assign`, `release`, `credit_back`, `ready`를 갖고 착수용 `Notice`를 보내지 않는다. v1 연결은 `Welcome` 단계에서 거절한다. 이 저장소 밖 사용자가 없어 이중 지원은 두지 않는다.
* 워커 프레임워크는 lane을 만들고 inbox 소비를 시작한 **뒤에** `take`로 여유를 연다. 그래서 초기 `Assign`이 inbox를 채워 다른 응답을 막는 일이 없다.

### 2.4 동시성과 멀티코어

* **엔진은 단일 작성자로 남는다.** 배정은 착수 표지·여유·라운드 상태를 바꾸는 엔진 전이다. 엔진 밖 전달 태스크로 빼면 두 작성자가 생긴다.
* **엔진 분할은 이번 개편에서 하지 않는다.** 지금 계약(Q4(a): 후속 전체 사전 검증 뒤 부모 제거, 전역 id 중복 거절, 작업 키 고유성, 연결별 송신 순서, Strict 공개 경계)을 지키면서 분할하려면 다음이 먼저 설계돼야 한다.
  * 전역 id 예약·라우팅
  * 충돌 없는 작업 키
  * 조각을 넘는 후속의 사전 검증과 커밋 경계
  * 영속 수신 영수증
  * 조각 간 인과 장벽

  단순 아웃박스는 대상 조각 거절 때 부모를 보존하지 못하고, 완료 뒤 사라진 id로는 재전달을 막지 못한다(리뷰 지적, `admit`이 활성 id만 본다). 측정이 엔진 CPU 포화를 보이면 별도 제안서로 다룬다.
* **송신 복사 제거.** 인코더가 머리(연결별 사전으로 인코딩)와 payload(`Bytes` 공유)를 따로 두고, 작성기가 벡터 쓰기로 내보낸다. 문턱 아래 작은 payload는 지금처럼 복사가 싸다. 문턱은 측정으로 정한다.
* **수신 프레임 고정 해소.** 대기 표에 오래 머무는 착수용 이벤트의 payload가 프레임 크기보다 훨씬 작으면, 대기 표에 넣을 때 그 payload만 떼어 복사한다. 작은 이벤트 하나가 큰 프레임을 붙잡지 않는다.
* **발송 등록의 파이프라이닝.** 발송 등록은 지금 `Accepted` 왕복을 기다린다. 토큰 스트림처럼 작은 발송이 많은 경우를 위해, 클라이언트에 응답을 기다리지 않고 연속 등록하는 API를 둔다. 한 연결의 요청은 보낸 순서대로 엔진에 들어가므로 순서는 유지된다. 실패는 다음 응답에서 모아 알린다.

## 3. 대용량 페이로드

### 3.1 지금의 한계

* 등록 하나는 프레임 하나(기본 16 MiB, 머리와 이름 정의 포함)를 넘을 수 없다. 그보다 큰 페이로드는 TCP로 등록할 수 없다. 프로세스 안 연결은 이 상한을 거치지 않는다.
* 대기 중인 착수용 이벤트는 엔진 메모리에 있고 저널에 본문째 적힌다.
* 발송에는 수신자 흐름 제어가 없다.
* 발송 팬아웃은 연결마다 payload를 세 번 복사한다.

### 3.2 설계: 조각 시리즈 + 조각 저장소 + 엔진 규칙에 기댄 조립

```text
보내는 쪽(프록시 등)                     이벤트 서버                          워커들(어느 워커든)
manifest: 시리즈 id·세대, 조각 수 N, 조각 길이, 전체 길이·해시, 결과 채널
part i (순서 무관, 다른 이벤트와 섞임) ─► 조각 채널 ─► 여유 기반 배정
                                                            part 워커: 저장소.put(series, gen, i, bytes)  (길이·해시 검증, 멱등)
                                                                       if put이 "모두 있음"을 돌려주면:
                                                                          complete(part, follow_ups=[assemble(id = f(series, gen))])
                                                                       else: complete(part)
                                                            assemble 워커: 저장소 상태 확인 → 순서대로 읽어 처리
                                                                       complete(assemble, follow_ups=[result(id = g(series, gen))])
```

**조립 담당 선출을 엔진의 기존 규칙으로 한다.** 저장소의 배타 생성을 쓰지 않는다.
* "모두 있음"을 본 조각 워커는 자기 조각의 완료에 **결정적 id**(시리즈 id와 세대에서 유도)의 `assemble` 착수용 후속을 붙인다. 완료와 후속 등록은 엔진에서 원자적이다(Q4(a)).
* 여러 워커가 동시에 "모두 있음"을 보면, 첫 완료만 `assemble`을 등록한다. 나머지 완료는 후속 id 중복으로 거절된다(부모는 남는다). 이 경우 워커는 후속 없이 다시 완료한다. 클라이언트 라이브러리가 이 규칙을 감춘다: `Duplicate` 거절이고 그 후속이 결정적 id면, 후속을 빼고 재완료한다.
* 조각 워커가 put 뒤 완료 전에 죽으면, 그 조각은 lease로 회수되어 다시 실행된다. put은 멱등이고 "모두 있음"을 다시 보므로 `assemble`이 다시 시도된다. **선출 직후 사망으로 결과를 잃는 구멍이 없다.** 선출과 후속 등록이 한 엔진 전이이기 때문이다.
* `assemble`과 `result`도 같은 방식(결정적 id 후속)으로 이어진다. 보장 범위:
  * **논리 결과는 id 하나다.** 결과 등록이 성공하고 응답만 잃어 다시 등록하면, 결과가 아직 대기 중일 때는 중복으로 거절된다.
  * 결과가 이미 소비된 뒤에 늦은 재실행이 같은 id로 다시 등록할 수 있다. 저장소 상태를 `SEALED → ASSEMBLED → PUBLISHED`로 남겨 assemble 워커가 이미 끝난 시리즈를 건너뛴다. 이 확인과 등록 사이의 경합까지 막지는 않는다. 그래서 결과 소비자는 결과 id로 멱등 처리한다. 이것이 약속의 경계다.
* 서버에 조인 카운터를 두는 대안은 기각한다. 저장소의 조각이 읽을 수 있는 상태인지, 해시가 맞는지, 결과가 이미 소비됐는지는 카운터가 알 수 없다. 이 상태는 저장소와 처리 라이브러리가 갖는 편이 D11에 맞다(리뷰 동의).

**저장소 계약.**

| 연산 | 계약 |
| --- | --- |
| `open(manifest)` | 불변 manifest를 고정한다: 세대, 조각 수, 조각 길이, 전체 길이·해시. 같은 시리즈 id에 다른 manifest가 오면 충돌. 조각이 manifest보다 먼저 와도 된다. 조각마다 manifest 머리를 싣는다 |
| `put(i, bytes)` | 길이(그리고 조각 해시가 있으면 해시)를 검증한 뒤, 완성된 조각을 원자적으로 공개한다(임시 이름에 쓰고 rename). 같은 내용의 중복은 성공, 다른 내용은 `Conflict`다. 돌려주는 것: 새로 들어갔는지, 지금 있는 조각 수 |
| `state` | `OPEN → SEALED(N개 모두 있음) → ASSEMBLED → PUBLISHED`, 또는 `ABORTED`, `FAILED(해시 불일치 등)`. 세대 단위다 |
| `read(range)` | `SEALED` 이후에만 |
| `abort`, `remove` | 실행 중 put과의 경합: `ABORTED` 뒤 put은 `Aborted`를 돌려주고 쓰지 않는다. 지운 시리즈를 늦은 재전송이 되살리지 않도록, 지운 뒤에도 세대 묘비를 보존 기간 동안 둔다 |

* **조각 수 세기를 O(1)로.** "모두 있음"을 조각마다 N개 전수 확인하면 시리즈당 O(N²)이다(리뷰 지적). `put`이 지금 개수를 돌려주게 하고, 구현이 개수를 싸게 유지한다. 로컬 파일 시스템 구현은 시리즈 디렉터리의 개수를 처음 접근 때 목록으로 세고, 이후 프로세스 안 원자 계수로 유지한다.
* **구현:**
  * 로컬 파일 시스템: 워커 서버 하나 또는 공유 디렉터리.
  * 객체 저장소: S3 계열. **S3 멀티파트 part는 마지막을 빼고 최소 5 MiB, 번호 1~10,000이다.** 그래서 조각 하나를 part 하나에 대응시키지 않는다. 조각은 객체 하나씩 두고, 조립 때 합치거나 5 MiB 이상으로 모아 멀티파트로 올린다.
  * 백엔드마다 충돌·부분 실패를 시험으로 검증한다.
* **무결성:** 조각 길이 검사, 조립 때 전체 해시 검사. 불일치는 `FAILED`와 실패 이벤트.
* **정리:** `PUBLISHED`된 시리즈는 결과 소비자가 다 읽었다고 알린 뒤 지운다(`remove`). 버려진 시리즈는 저장소에 마지막 활동 시각을 적고, 워커가 새 시리즈를 열 때 기한 지난 것을 지운다. 주기 타이머는 없다.
* **취소:** 보내는 쪽이 `abort`를 등록한다. 이 등록은 발송이 아니라 저장소 상태를 바꾸는 착수용 이벤트다. 발송이면 그때 오프라인인 워커가 놓친다. 이후 조각 워커는 `put`에서 `Aborted`를 받고 그냥 완료한다.

**조각 채널의 영속.**
* 기본은 **저널 대상(영속)**이다.
* 저널 제외는 "서버가 죽으면 보내는 쪽이 시리즈를 처음부터 다시 보낼 수 있는" 생산자만 쓴다. 원본을 결과 확인 때까지 보존하는 생산자다. 원본 스트림을 이미 소진한 생산자(예: 받은 HTTP 업로드를 흘려보낸 프록시)는 영속 채널을 써야 한다. 그렇지 않으면 서버 재기동 뒤 그 시리즈는 되살릴 수 없다.

**보내는 쪽 흐름 제어: 즉시 거절 + 자리 알림.** 응답을 늦추는 방식은 쓰지 않는다. 리뷰가 보인 교착 때문이다. 같은 연결이 뒤 조각 응답을 기다리며 앞 조각 완료를 못 보내는 경우가 그 예다.
* 엔진에 채널별·전체 **대기 payload 바이트 예산**을 둔다. 예산을 넘는 등록은 즉시 `Busy`로 거절한다. 엔진도 연결 reader도 멈추지 않는다.
* 예산이 풀리는 사건(그 채널 이벤트의 완료·삭제)이 생기면, 그 채널에서 `Busy`를 받은 연결에 `Room(channel)` 발송을 한 번 보낸다. 받기 전까지 같은 채널의 추가 `Room`은 합친다. 보내는 쪽은 `Room`을 받고 다시 보낸다.
* 제어 호출(완료, 반환, 삭제, `abort`, `ready`)은 예산 대상이 아니다. 그래서 데이터가 포화돼도 예산을 푸는 호출은 항상 도달한다.
* 완료와 후속은 순증분(후속 바이트 − 부모 바이트)으로 계산한다.
* 예산보다 큰 단일 조각은 영구 거절한다(`TooLarge`). 조각 크기는 예산보다 작아야 한다.
* 예산이 세는 것은 엔진이 쥔 대기·착수 중 payload다. 수신 프레임 버퍼와 Strict 보류분은 연결 수 × 프레임 상한으로 따로 묶인다.

**받는 쪽 흐름 제어(큰 결과를 프록시로).**
* 결과가 큰 경우 바이트는 이벤트로 흘리지 않는다. 생산자가 **같은 조각 저장소**에 결과 시리즈를 쓰고, 결과 이벤트에는 참조(시리즈 id·세대·길이·해시)만 싣는다. 프록시는 저장소에서 자기 속도로 오프셋 순서대로 읽어 클라이언트에 쓴다.
  * 역순 도착 교착(리뷰 지적: 창 2에 `1, 2, 0` 순서)이 생기지 않는다.
  * HTTP에 쓴 뒤 완료 응답 유실로 같은 조각을 두 번 쓰는 문제도 오프셋으로 막는다.
* 생산이 진행 중인 결과를 따라 읽어야 하면, 생산자가 조각마다 작은 진행 발송(`progress(series, 연속 오프셋)`)을 내고, 프록시는 그 오프셋까지 읽는다. 진행 발송을 놓쳐도 다음 진행 발송이 더 큰 오프셋을 알리므로 손실이 아니다.
* **작은 실시간 스트림(토큰 SSE)** 은 발송용 이벤트에 순번을 붙여 보내고, 받는 쪽이 정렬한다. 순서 맞추기 버퍼는 요청마다 상한이 있다. 넘치면 그 요청을 끊는다(손실 신호). 생산자는 2.4의 파이프라이닝 등록으로 조각마다 왕복을 기다리지 않는다.
* HTTP 클라이언트에 정확히 한 번 쓰는 것은 약속하지 않는다. 오프셋·순번으로 프록시 안 중복은 막고, 클라이언트 연결이 끊기면 그 요청은 실패다.

### 3.3 채널 단위 저널 제외

* 엔진 설정 `volatile_channels: [패턴]`. 맞는 채널의 착수용 이벤트는 저널과 복구 스냅샷에 넣지 않는다. 재기동하면 사라진다.
* 계약은 "volatile 등록 **자체**는 디스크 쓰기를 요구하지 않는다"로 좁힌다. 같은 연결에서 앞선 게이트 송신이 있으면 volatile 등록의 응답도 그 뒤에 나간다(연결별 순서 우선).
* 조합별 결과표를 문서와 시험으로 고정한다.
  * durable 부모의 완료 + volatile 후속: 부모 제거는 기록되고 후속은 기록되지 않는다. 재기동하면 둘 다 없다. 허용하되 명시한다.
  * volatile 부모 + durable 후속: 후속은 기록된다.
  * volatile 이벤트의 착수·회수·제거: 기록하지 않는다.
  * 압축 재작성·운영 스냅샷: volatile 제외.
  * 디스크 실패: 혼합 배치에서 먼저 공개된 `Assign`·후속·성공 응답 수.

## 4. 프록시

* **원 엔벨롭 스트림:** 허브가 사용자에게 `Arc<Envelope>`를 준다. 내장 WS·HTTP가 텍스트로 그린다(이벤트당 한 번 그리는 성질 유지).
* **요청 교환 `Proxy::exchange(event)` 계약.**
  1. 프록시 연결 세대마다 접두사 `<프록시 id>.<세대>.` 구독의 표지를 확인한다.
  2. **재사용하지 않는** 요청 id(UUIDv7)의 대기자를 설치한다.
  3. 원 요청을 `reply = <접두사><요청 id>`로 등록한다.

  이 순서면 빠른 워커의 첫 응답도 잃지 않는다. 옛 세대·끝난 요청 id로 온 늦은 응답은 버린다. 응답 채널 발행 권한은 grant의 채널 패턴으로 워커에게만 준다.
* 사용자 `subscribe`는 지금처럼 join마다 자기 표지를 기다린다(허브 불변식 유지). 접두사 구독은 교환에만 쓴다.
* **엔진의 접두사 구독:**
  * 정확 이름 경로는 지금처럼 해시 조회다. 접두사는 구분자(`.`) 경계의 트라이 조회로 따로 둔다.
  * 한 연결이 정확 이름과 접두사로 같은 발송을 겹쳐 받으면 연결 단위로 한 번만 보낸다.
  * 접두사 구독은 발송용 수신 전용이다. 배정 참여(`take`)는 정확 이름만이다.
  * 활성 접두사 수·매칭 수를 따로 늘려 측정한다.
* **앱 경로:** `Server::routes(Router<Proxy>)`. 내장 프로토콜 feature를 끄면 앱 경로와 `/health`만 남는다.

## 5. 측정 계획

변경 **전에** 지금 경로로 잴 수 있는 것을 모두 기준선으로 남기고, 단계마다 같은 설정으로 다시 잰다. 보고서에는 다음을 적는다.
* 버전·설정·호스트·동시성·실제 작업 수·내구성 모드
* 반복 측정 횟수

기존 단건 보고서의 수치를 TCP 개선율의 분모로 쓰지 않는다.

| # | 작업 부하 | 보는 것 | 전후 비교 |
| --- | --- | --- | --- |
| M0 | TCP 등록→착수→완료. W = 1, 4, 16에서 **총 허가 고정**과 **워커당 허가 고정**을 따로. 부하율·RTT·타입 불일치·반환율·Strict를 바꾼다 | 완료 처리량, 배정 대기 p50/p99, 채널별 p99, 워커별 점유율, 이벤트당 wire `claim` 수와 엔진 배정 전이 수, 반환 순회 수, 논리 메시지·실제 프레임·바이트 | 전·후 |
| M1 | 포화(등록률 > 처리율), 전원 거절 후 `ready` | 보류 수, 메시지 수(거절 폭풍), 엔진 메모리, 재개까지의 메시지 | 전·후 |
| M2 | 발송 팬아웃 N = 1, 16, 256, payload 16 B ~ 1 MiB, 느린 구독자 포함 | 처리량, 복사 바이트·할당·시스템 호출, 엔진·작성기·저널 코어 사용률 분리 | 전·후 |
| M3 | 시리즈 64 MiB ~ 1 GiB, 조각 256 KiB ~ 4 MiB. 역순·누락·상충 중복·예산 초과 조각·느린 송수신자·같은 연결 완료·중단 후 재개 | MB/s, RSS, 엔진 대기 바이트, inbox·Strict 보류 바이트, 저장소 요청 수, 재전송 바이트, 논리 결과 수 | 기준선은 같은 파일의 직접 전송 |
| M4 | 요청 교환: 요청/초, 응답 조각 수. 정확 이름 구독 방식과 접두사 방식 | 요청당 지연, 엔진 구독 표 변경 수 | 정확 이름 방식이 기준선 |

## 6. 단계

각 단계는 테스트·문서·`cargo xtask verify`·커밋으로 끝내고, 측정이 있는 단계는 보고서를 남긴다.

1. **계약과 실패 시험 정의.** 이 문서의 계약을 테스트 이름이 붙은 시험 목록으로 고정한다(`docs/testing.md` 지도). 2.3, 3.2, 3.3, 4의 각 규칙과 리뷰가 든 반례가 대상이다.
2. **기준선 M0·M1·M2·M4(정확 이름).** 지금 경로로 측정 예제를 TCP·다중 워커로 넓힌다.
3. **여유 기반 배정(v2 wire).** 상태 기계, 프로토콜, 워커 프레임워크. 기존 보장(G1~)과 인수 테스트 재통과. 반례 시험:
   * `A→B→A` 반환 순환 없음
   * 전원 반환 후 정지 → `ready` 한 번 → 한 라운드
   * X 등록 → Y 회수 → Y 재배정
   * 완료 응답 재전송·다른 연결 완료·명시 착수에서 여유 불변
   * 공유 풀 초과 배정 없음
   * Strict에서 `Assign` 공개 시점

   M0·M1 재측정.
4. **채널 단위 저널 제외와 대기 바이트 예산**(`Busy`/`Room`). 조합 결과표 시험. 같은 연결 완료 진행, 예산 초과 조각 거절.
5. **송신 벡터 쓰기, 수신 프레임 고정 해소, 발송 파이프라이닝.** M2 재측정.
6. **시리즈와 조각 저장소**(파일 시스템, 그다음 객체 저장소). 반례 시험: 선출 전·후 사망, 결과 등록 직후 응답 유실, 결과 소비 뒤 재전송, 상충 중복, 해시 불일치, `abort` 경합, 묘비. M3.
7. **프록시: 원 엔벨롭, 접두사 구독, 교환 계약, 앱 경로.** 반례 시험: 등록 직후 즉시 응답, 상위 재접속 세대, 옛 응답과 새 요청 교차. M4.
8. **apibondrust**로 실제 적용 검증.
