# 제안: ruvent 위의 apibond, 그리고 그에 필요한 라이브러리 변경

상태: **구현·실증됨** (2026-11-25). 라이브러리 부분(옛 3장 L1~L3)은 [library-overhaul.md](library-overhaul.md) v4.6으로 대체되어 구현됐고, apibond는 그 위에 `F:\dev\apibondrust`로 다시 세워 실제 프로세스로 실증했다. 3장 이후는 실제 구현과 결과다. 1장의 원문 인용은 그대로 유효하다. 2장은 개편 전 ruvent와 원문의 차이를 적은 기록으로 남긴다.

`F:\dev\apibond`(Rust, 약 2,300줄)는 OpenAI·Anthropic·Responses·Embeddings 요청을 여러 추론 서버로 나누는
중계기다. 공개 모델 별칭 하나, 세션 고정, 부하 기반 배정, 스트리밍 중계, Responses·파일 ID 소유 추적을 한다.
이 제안은 apibond를 ruvent 위에 **프록시 파트와 워커 파트로 분해해** 다시 세우고(새 저장소 `F:\dev\apibondrust`),
그 과정에서 드러난 ruvent 라이브러리의 부족분을 라이브러리 쪽에서 고친다.

## 1. 사용자 원문

> 결국 apibond는 분해되어야해. 프록시 서버 파트와 워커파트겠지. 예를들어 클라이언트가 api콜을 하면 프록시 서버는 그걸 이벤트로 바꿔서 이벤트서버에 등록하겠지. 그때 세션id가 있거나 없거나 할테고 최초요청에 기존 세션id가 없다고 하면 프록시 서버는 신규 id를 발급했을 것이다.
> 이런 정보 자체가 이벤트 페이로드에 들어있을 것이다.
> 또한 개별 요청은 개별 채널로 등록되면서 동시에 이벤트서버에게 프록시는 그 채널을 수신하다고 보고해야겠지.
> 그렇게 등록된 이벤트는 워커가 가져간다. 워커는 이벤트를 착수하면서 요청id와 실 서버를 매핑하는 라우팅을 실시하여 적절한 api서버를 중계하면서 끝낼 것이다.
> 실제 api서버를 처리하는 쓰레드 혹은 프로세스는 인퍼런스 내내 중계하면서 이벤트서버에 스트리밍 응답 조각을 요청에 맞는 채널의 이벤트로 등록하거나 실패 메세지등을 이벤트로 등록할 것이고 그것은 다시 이벤트서버에서 수신채널로 프록시에게 보내면 프록시는 최종적으로 클라이언트들에게 쏴주는 식이 될것이다.

> 앞서 설명한 것처럼 고가용성 이벤트 서버의 역할은 어떤 경우라도 불변이다. 이벤트서버는 이벤트를 등록하고 이벤트채널 수신자들에게 발송전용 이벤트가 등록되는 순간 발송한다.
> 워커가 착수하면 동시성을 관리하여 착수마킹의 아토믹을 보장하고 완료보고시 큐에서 제거한다.
> 오히려 지금 시점에 명확하지 않은 것은 워커가 이벤트서버의 큐에 있는 이벤트를 가져가는 방식이다.
> 이는 상시 감시로 처리하기엔 자원이 비효율적이다. 최대 성능을 낼려면 각 워커는 이벤트서버에 착수용 이벤트 큐에서 자신이 착수하는 이벤트 타입 또는 이벤트 채널을 등록하여 해당 이벤트가 들어오면 그 워커서버 혹은 내장 워커풀은 이벤트가 도착했다는 통지를 받는다. 워커서버들은 등록순으로 순차적으로 통지받는다. 1차워커서버가 모든 워커가 일하는 중이거나 여러 이유로 그 이벤트 착수를 거부하면 다음 워커에게 통지되는 식으로 동작하기 때문에 이벤트 서버입장에서 이벤트 착수의 동시성 제어는 사실상 필요없다.
> 만약 모든 워커풀이 착수를 거부한 이벤트는 다시 처음부터 통지한다.
> 이런 이벤트 등록시 개별 이벤트를 워커에게 돌아가면서 전달하는 책임은 이벤트 서버내의 전달 쓰레드풀이 담당한다. 이벤트가 등록되는 즉시 워커쓰레드 풀에서 워커가 하나 배정되어 워커서버에게 전달하는 책임을 지는 것이다. 전달이 끝나면 워커는 다시 풀로 돌아온다. 만약 이벤트 서버의 모든 이벤트 전달 워커풀이 동작중이면 워커가 풀려날까지 기다렸다가 이벤트에 워커가 배정된다. 사실상 큐라고 하지만 이 시스템은 이벤트를 큐처럼 관리하는 것은 아니다.
> 모든 이벤트간의 순서는 도착이나 착수의 순서가 아니라 이벤트가 단락적이라는 점을 이용한다.
> 즉 순서를 보장하고 싶다면 1번이벤트를 처리한 워커가 2번 이벤트를 등록하기 때문에 2번 이벤트를 착수하게 되는 식의 순서가 성립하는 것이다.

> 그런 일은 좀처럼 일어나지 않는다. 그 일이 일어나는 경우는 실 api서버가 503을 토하는 경우일테다. 대부분 인퍼런스 api서버들은 503을 토하지 않고 작업큐에 넣는 방식이다.

> 그건 또다른 도전을 의미한다. 대규모파일 등을 어떻게 이벤트서버가 처리할까는 이미 정답이 나와있다. 왜냐면 페이로드를 잘게 분해해서 시리즈로 보내는 것이기 때문이다.
> 각 분절된 이벤트는 전체 페이로드중 몇번이다라는 식으로 정보가 있어서 이를 처리하는 워커는 어떤 워커가 와도 그런 조각만 정리하고 부분처리하게 구현되어야한다. 모든 파일이 이벤트로 등록되고 워커가 모든 조각을 맞췄다면 그 결과를 이벤트로 등록하고 이를 수신한 클라이언트가 후속작업을 할 것이다. 조각은 순서대로 온다는 보장이 없고 하나의 시리즈를 보내는 동안 다른 이벤트를 안보낼 이유도 없다.

> 단지 apibond의 문제가 아니라 라이브러리 수준의 수정이 필요하다면 그것 역시 전개하라

(사용자, 2026-11-23)

## 2. 지금 ruvent와 원문의 차이

| 항목 | 지금 구현 | 원문 |
| --- | --- | --- |
| 착수용 이벤트를 워커에 알리는 방식 | 등록되면 그 채널 구독자 **전원**에게 `Notice`를 보낸다(`engine/state/mod.rs` `announce`). 워커들은 받은 알림으로 `claim`을 다투고, 엔진이 하나만 받아들인다 | 서버 안 **전달 풀**의 전달자 하나가 이벤트를 맡아, 등록 순서대로 워커 서버에 **하나씩 제안**한다. 거절하면 다음 워커로, 모두 거절하면 처음부터 |
| 착수 동시성 | 엔진의 원자 착수가 경쟁을 가른다. 워커 N개면 실패하는 `claim`이 N−1번 | 한 번에 한 워커에게만 제안하므로 경쟁이 없다. 원자성은 엔진이 그대로 보장 |
| 바쁜 워커 | 알림을 받고 허가가 없으면 `pending`에 쌓아 두었다가 나중에 착수 시도(`lane.rs`) | 그 자리에서 거절, 다음 워커가 받는다 |
| 큰 페이로드 | 프레임 상한 16 MiB(`ruvent-protocol` `MAX_FRAME`)를 넘으면 등록 불가 | 조각 시리즈로 나눠 등록하고, 어느 워커든 조각을 맡아 정리하고, 마지막 조각을 맞춘 쪽이 결과 이벤트를 낸다 |
| 프록시의 사용자 스트림 | 이벤트를 JSON 텍스트로 바꿔 준다(`message::event_text`). 바이트 payload는 손실 변환 | 요청마다 개별 채널, 응답 조각을 원 바이트 그대로 받아 클라이언트 프로토콜로 내보내야 한다 |
| 프록시 서버 경로 | 내장 프로토콜(`ws`, `http`)만 서비스. 앱 경로는 `router`를 따로 합쳐야 함 | apibond 게이트웨이는 OpenAI·Anthropic HTTP 경로 자체가 프로토콜이다 |

## 3. 원문 개념이 된 것 (v4.8)

| 원문의 개념 | 구현(apibondrust, ruvent v4.8) |
| --- | --- |
| 프록시가 API 콜을 이벤트로 등록, 세션 id가 없으면 발급해 payload에 넣음 | 게이트웨이(SDK `Producer`)가 세션 id를 원본 우선순위로 읽고, 없으면 `apibond-<UUIDv7>`을 발급해 `CallHead.session`에 넣고 응답 헤더 `x-apibond-session-id`로 돌려준다. 요청 머리 + 본문이 `apibond.call`의 착수용 이벤트가 된다. `expires` = 답이 시작될 때까지의 한도(`call_deadline_ms`) |
| 개별 요청은 개별 채널, 프록시는 그 채널을 수신 | 원문대로 됐다(v4.8). 요청마다 응답 채널 `apibond.answer.<UUIDv7>` 하나. 게이트웨이는 그 채널을 팬아웃 구성원 하나로 구독한 뒤 호출을 등록하고(`CallHead.answer`), 오는 것을 HTTP로 바꿔 쓴다. 이벤트 서버가 채널로 나누므로 게이트웨이에는 분배가 없다. v4.6~v4.7은 인스턴스 응답 채널 `reply.<id>` + `correlation`이었다(계획 9.13) |
| 워커가 착수하며 요청 id ↔ 실서버 라우팅 | 제안·거절 대신 창(계획 2.4): 워커의 `apibond.call` 창 = 백엔드 용량의 합. 배정 = 착수이고, 그 순간 세션 표·부하·상태 소유로 백엔드를 고른다 |
| 모두 거절하면 처음부터 다시 | 창이 다 차면 서버가 배정하지 않고 대기열에 둔다(보류, 타이머 없음). 세션이 고정된 백엔드만 가득이면 워커 안에서 용량 반납·건강 회복 통지를 기다린다(503 대신) |
| 스트리밍 응답 조각을 이벤트로 | 머리 = 조각 0, 본문 = 조각 1..: 요청의 응답 채널로 내는 실행 중 방출(`Context::emit_now`, 타입 `fragment`). 종결 = 같은 채널의 발송 후속(`Context::emit_dispatch`, 타입 `outcome`), 완료와 한 스텝. 조각 → 결과 순서는 연결 하나가 지킨다. 결과도 발송이라 그 순간 구독이 없으면 사라진다(재시작 직후 등) |
| 실패 메시지도 이벤트로 | 종결 결과 `Outcome::Fail{status, message}`, 스트림 중단은 `Outcome::Abort`. 게이트웨이는 원본과 같은 상태(502/504 등)와 봉투로 답한다. 실패도 결과이므로 호출은 한 번 완료되고 다시 실행되지 않는다 |
| 대용량은 조각 시리즈 | 원본이 64 MiB JSON, 512 MiB 업로드를 받으므로 범위에 들었다. 8 MiB를 넘는 본문은 4 MiB 조각(`apibond.part`, 착수용, 각 조각에 시리즈 id·순번·전체 수·전체 길이)으로 나뉜다. 워커는 조각을 로컬 파일 저장소에 순서 없이 저장하고, 마지막을 맞춘 저장이 `complete`를 배타 생성해 기다리는 호출을 깨운다. 서버 쪽 조건은 계획 3장의 넷뿐이다 |
| 서버는 운송만, 독립 서버 여럿 | 게이트웨이와 워커는 서버 목록(`events.servers`)의 모든 서버에 붙는다. 서버 사이 상태 공유는 없다 |

클라이언트가 끊으면 게이트웨이가 `apibond.cancel`에 발송 이벤트(payload = 그 요청의 응답 채널)를 내고, 워커는 그 채널을 관찰 연결로 구독해 중계를 끊고 용량을 돌려준다. (v4.9에서 바뀌었다: 7.2.)

## 5. 원본 apibond와 달라진 것

* 백엔드 용량이 차도 즉시 503을 내지 않는다(위 3장). 호출 기한까지 자리가 없으면 503이다. 실 서버의 503은 그대로 간다.
* 세션 표와 소유 표의 주인은 워커다. 게이트웨이는 상태가 없다. 워커는 라우팅 권한 하나를 전제한다(옛 D3).
* 세션 id가 없는 첫 요청에 게이트웨이가 id를 발급한다. 그 세션도 표에 들어가므로 세션 수로 동점을 가르는 분배가 원본과 다를 수 있다.
* `/status`는 워커에 묻는 이벤트다(타입 `STATUS`, 묻기마다 채널 하나, 호출과 다른 창. 같은 창이면 호출이 슬롯을 다 쥐었을 때 상태 조회가 굶는다).
* 원본 시험 중 기대가 바뀐 것은 넷이고, 바뀐 이유와 함께 `apibondrust/docs/testing.md`에 있다.

## 7.1 요청별 응답 채널로 바꾼 뒤 (v4.8, 2026-11-26)

사용자 지시: 각 요청은 개별 이벤트 스트림이므로 독립 채널이어야 하고, 게이트웨이는 그 채널로 온 것을 프로토콜만 바꿔 기계적으로 보내야 한다. 그렇게 바꿨다(계획 9.13).

* 게이트웨이의 요청자·`correlation` 분배·중계 태스크가 사라졌다. 요청 하나 = 팬아웃 구성원 하나 = 응답 채널 하나다. 느린 클라이언트는 골조가 구성원을 떼어 내는 것(`fragment_backlog` = 구성원 버퍼)으로 끊긴다.
* 시험 68개 통과, 실패 0(`apibondrust/tests/reports/unit/20261126_141011.txt`). 인수 7/7(`apibondrust/tests/reports/acceptance/20261126_135521`).
* 이벤트 서버 정상 재시작 시나리오의 판정을 "결과 유실 0, 재실행 0"에서 "재실행 0"으로 바꿨다. 결과 보존은 워커의 일이라는 사용자 결정 때문이다. 관찰값: 진행 중 20건 중 200 17건, 결과 유실 3건, 재실행 0. 잃은 요청은 게이트웨이 호출 기한(600초) 무렵까지 기다렸다.

## 7.2 타입 라우팅과 UUIDv7 채널로 바꾼 뒤 (v4.9, 2026-11-26)

사용자 지시: 타입은 서버가 워커에게 배정할 때 쓸 때만 정당하고(2바이트 정수), 워커는 채널·타입·조합으로 참여하며, 채널은 이름 없이 UUIDv7 형식만 받는다(계획 9.14). apibond는 원문의 흐름 그대로 됐다.

* **요청 = 채널.** 게이트웨이가 요청마다 `Channel::new()`를 정해 구독하고, 같은 채널에 타입 `CALL`로 호출을 등록한다. `CallHead.answer`(채널 이름 문자열)는 없어졌다. 워커는 `cx.channel()`로 같은 채널에 `FRAGMENT`·`OUTCOME`을 낸다.
* **워커는 타입으로만 참여한다.** `Service::typed().on(CALL)`, `on(STATUS)`, `on(PART)`: 채널을 미리 알 필요가 없다. 창은 그대로 용량 합이다.
* **타입 번호.** 1–99 착수용(`CALL` 1, `STATUS` 2, `PART` 3), 100–199 발송(`CANCEL` 100, `FRAGMENT` 101, `OUTCOME` 102). 이벤트 서버 자격은 `"types": ["1-3", "100-102"]`이고 채널은 설정 어디에도 없다.
* **큰 본문.** 시리즈 하나가 채널 하나다. 시리즈 id는 그 채널의 글이다(조각 저장소의 이름).
* **취소.** 고정 채널 `apibond.cancel`이 없어졌다. 게이트웨이는 요청 채널에 `CANCEL`을 발송하고, 호출이 아직 대기 중이면 그 호출을 삭제한다(삭제된 호출은 돌지 않는다: v4.8의 "먼저 온 취소" 표가 하던 일). 워커는 돌리는 호출의 채널을 호출 동안 구독해 `CANCEL`을 받는다. 대가: 그 구독은 워커 자신의 조각·결과도 돌려받고(버린다), 배정 뒤 구독이 서기 전(한 왕복)에 온 취소는 보이지 않아 그 중계가 끝까지 돈다.
* **실증.** 시험 68개 통과, 실패 0(`apibondrust/tests/reports/unit/20261126_200054.txt`). 인수 7/7(`apibondrust/tests/reports/acceptance/20261126_200310.md`). 이벤트 서버 정상 재시작 시나리오의 관찰값: 진행 중 20건 모두 200, 결과 유실 0, 백엔드 실행 20회(재실행 0), 재시작 직후 새 요청 1 ms. v4.8 실행(결과 유실 3)과 다른 것은 이번 실행의 관찰일 뿐이다: 결과가 발송이라는 계약은 그대로이고, 재구독보다 먼저 끝난 결과는 여전히 잃을 수 있다.

## 7.3 최소 서버로 바꾼 뒤 (v5, 2026-11-26)

사용자 지시: 서버의 할 일을 줄일수록 범용성이 높아지고, 엔벨롭에는 서버의 기본 동작에 필요한 것만 남긴다(계획 9.15). apibond에서 바뀐 것은 둘이다.

* **만료가 없다.** 호출·조각·상태 묻기에 걸던 `expires`(호출 기한)를 뺐다. 게이트웨이는 호출 기한을 넘기면 504로 답하고, 그때 `CancelGuard`가 대기 중인 호출을 삭제한다(v4.9부터 있던 경로). 조각은 워커가 타입 참여로 늘 가져가므로 서버에 남지 않는다.
* **이벤트 서버 설정이 메서드 권한뿐이다.** 자격의 `types`와 타입 규칙(`isolate_after`)이 없어졌다. 서버는 실패를 세기만 하고 격리하지 않는다. 워커의 중계는 실패를 결과(`Outcome::Fail`)로 내고 완료하므로 다시 실행되지 않는다. 그래도 실패가 쌓이는 호출(패닉이나 lease 만료로 끊긴 실행)은 워커가 직접 끝낸다: 실패 횟수가 `events.max_failures`(기본 5)에 닿으면 다시 돌리지 않고 502 결과로 완료한다. 한도는 서버가 아니라 워커의 설정값이다.
* **실증.** 시험 68개 통과, 실패 0(`apibondrust/tests/reports/unit/20261126_203952.txt`). 바로 앞 실행(`20261126_203519`)에서는 느린 클라이언트 시험 1건이 타이밍 경합으로 실패했고, 다시 돌리면 통과했다. 인수 7/7(`apibondrust/tests/reports/acceptance/20261126_204140.md`).
* **재시작 시나리오의 관찰값: 결과 유실 20/20, 재실행 0.** v5의 퇴행인지 따져 봤고, 아니었다.
  * 서버는 1633 ms에 멈추고 3178 ms에 다시 올라왔다. 백엔드 지연(2500 ms)이 그 사이에 끝나, 모든 실행이 서버가 내려가 있는 동안 완료됐다.
  * 워커의 완료는 다시 붙자마자 적용됐다. 게이트웨이의 재구독은 그보다 늦어 결과가 아무에게도 가지 않았다.
  * 같은 흐름을 재현한 시험(실제 서버 재시작, 팬아웃 구성원, 타입 참여 워커, 서버를 2초 내려 둠)은 v4.9 커밋(4dbecdc)에서도 결과를 잃었다.
  * v4.9 인수 실행에서 유실이 0이었던 것은 서버가 2453 ms에 올라와 실행보다 먼저 돌아왔기 때문이다.
  * 결과를 지킬지는 워커의 일이라는 계약(9.13)은 그대로다.

## 8. 남은 범위

* 워커 서버 여러 대가 세션 표를 나눠 갖는 것(옛 D3의 다음 단계)과 공유 조각 저장소(네트워크 파일 시스템의 배타 생성)는 하지 않았다.
* 원본의 설치·배포 스크립트, 혼합 부하(4 × 60 MiB 이미지)와 느린 클라이언트 측정 행은 옮기지 않았다.
* 큰 본문 경로의 단계별 비용 측정과 개선은 다음 일이다.
