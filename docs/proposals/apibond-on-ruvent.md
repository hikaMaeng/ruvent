# 제안: ruvent 위의 apibond, 그리고 그에 필요한 라이브러리 변경

상태: **라이브러리 부분(3장 L1~L3)은 [library-overhaul.md](library-overhaul.md)로 대체됨** (2026-11-23). 사용자 지시에 따라 apibond는 라이브러리 개편을 실제 적용에서 검증하는 프로젝트로 두고, 4장 이후는 개편이 끝난 뒤 그 계획에 맞춰 다시 쓴다. 1장의 원문 인용은 유효하다.

`F:\dev\apibond`(Rust, 약 2,300줄)는 OpenAI·Anthropic·Responses·Embeddings 요청을 여러 추론 서버로 나누는
중계기다. 공개 모델 별칭 하나, 세션 고정, 부하 기반 배정, 스트리밍 중계, Responses·파일 ID 소유 추적을 한다.
이 제안은 apibond를 ruvent 위에 **프록시 파트와 워커 파트로 분해해** 다시 세우고(새 저장소 `F:\dev\apibondrust`),
그 과정에서 드러난 ruvent 라이브러리의 부족분을 라이브러리 쪽에서 고친다.

## 1. 사용자 원문

> 결국 apibond는 분해되어야해. 프록시 서버 파트와 워커파트겠지. 예를들어 클라이언트가 api콜을 하면 프록시 서버는 그걸 이벤트로 바꿔서 이벤트서버에 등록하겠지. 그때 세션id가 있거나 없거나 할테고 최초요청에 기존 세션id가 없다고 하면 프록시 서버는 신규 id를 발급했을 것이다.
> 이런 정보 자체가 이벤트 페이로드에 들어있을 것이다.
> 또한 개별 요청은 개별 채널로 등록되면서 동시에 이벤트서버에게 프록시는 그 채널을 수신하다고 보고해야겠지.
> 그렇게 등록된 이벤트는 워커가 가져간다. 워커는 이벤트를 착수하면서 요청id와 실 서버를 매핑하는 라우팅을 실시하여 적절한 api서버를 중계하면서 끝낼 것이다.
> 실제 api서버를 처리하는 쓰레드 혹은 프로세스는 인퍼런스 내내 중계하면서 이벤트서버에 스트리밍 응답 조각을 요청에 맞는 채널의 이벤트로 등록하거나 실패 메세지등을 이벤트로 등록할 것이고 그것은 다시 이벤트서버에서 수신채널로 프록시에게 보내면 프록시는 최종적으로 클라이언트들에게 쏴주는 식이 될것이다.

> 앞서 설명한 것처럼 고가용성 이벤트 서버의 역할은 어떤 경우라도 불변이다. 이벤트서버는 이벤트를 등록하고 이벤트채널 수신자들에게 발송전용 이벤트가 등록되는 순간 발송한다.
> 워커가 착수하면 동시성을 관리하여 착수마킹의 아토믹을 보장하고 완료보고시 큐에서 제거한다.
> 오히려 지금 시점에 명확하지 않은 것은 워커가 이벤트서버의 큐에 있는 이벤트를 가져가는 방식이다.
> 이는 상시 감시로 처리하기엔 자원이 비효율적이다. 최대 성능을 낼려면 각 워커는 이벤트서버에 착수용 이벤트 큐에서 자신이 착수하는 이벤트 타입 또는 이벤트 채널을 등록하여 해당 이벤트가 들어오면 그 워커서버 혹은 내장 워커풀은 이벤트가 도착했다는 통지를 받는다. 워커서버들은 등록순으로 순차적으로 통지받는다. 1차워커서버가 모든 워커가 일하는 중이거나 여러 이유로 그 이벤트 착수를 거부하면 다음 워커에게 통지되는 식으로 동작하기 때문에 이벤트 서버입장에서 이벤트 착수의 동시성 제어는 사실상 필요없다.
> 만약 모든 워커풀이 착수를 거부한 이벤트는 다시 처음부터 통지한다.
> 이런 이벤트 등록시 개별 이벤트를 워커에게 돌아가면서 전달하는 책임은 이벤트 서버내의 전달 쓰레드풀이 담당한다. 이벤트가 등록되는 즉시 워커쓰레드 풀에서 워커가 하나 배정되어 워커서버에게 전달하는 책임을 지는 것이다. 전달이 끝나면 워커는 다시 풀로 돌아온다. 만약 이벤트 서버의 모든 이벤트 전달 워커풀이 동작중이면 워커가 풀려날까지 기다렸다가 이벤트에 워커가 배정된다. 사실상 큐라고 하지만 이 시스템은 이벤트를 큐처럼 관리하는 것은 아니다.
> 모든 이벤트간의 순서는 도착이나 착수의 순서가 아니라 이벤트가 단락적이라는 점을 이용한다.
> 즉 순서를 보장하고 싶다면 1번이벤트를 처리한 워커가 2번 이벤트를 등록하기 때문에 2번 이벤트를 착수하게 되는 식의 순서가 성립하는 것이다.

> 그런 일은 좀처럼 일어나지 않는다. 그 일이 일어나는 경우는 실 api서버가 503을 토하는 경우일테다. 대부분 인퍼런스 api서버들은 503을 토하지 않고 작업큐에 넣는 방식이다.

> 그건 또다른 도전을 의미한다. 대규모파일 등을 어떻게 이벤트서버가 처리할까는 이미 정답이 나와있다. 왜냐면 페이로드를 잘게 분해해서 시리즈로 보내는 것이기 때문이다.
> 각 분절된 이벤트는 전체 페이로드중 몇번이다라는 식으로 정보가 있어서 이를 처리하는 워커는 어떤 워커가 와도 그런 조각만 정리하고 부분처리하게 구현되어야한다. 모든 파일이 이벤트로 등록되고 워커가 모든 조각을 맞췄다면 그 결과를 이벤트로 등록하고 이를 수신한 클라이언트가 후속작업을 할 것이다. 조각은 순서대로 온다는 보장이 없고 하나의 시리즈를 보내는 동안 다른 이벤트를 안보낼 이유도 없다.

> 단지 apibond의 문제가 아니라 라이브러리 수준의 수정이 필요하다면 그것 역시 전개하라

(사용자, 2026-11-23)

## 2. 지금 ruvent와 원문의 차이

| 항목 | 지금 구현 | 원문 |
| --- | --- | --- |
| 착수용 이벤트를 워커에 알리는 방식 | 등록되면 그 채널 구독자 **전원**에게 `Notice`를 보낸다(`engine/state/mod.rs` `announce`). 워커들은 받은 알림으로 `claim`을 다투고, 엔진이 하나만 받아들인다 | 서버 안 **전달 풀**의 전달자 하나가 이벤트를 맡아, 등록 순서대로 워커 서버에 **하나씩 제안**한다. 거절하면 다음 워커로, 모두 거절하면 처음부터 |
| 착수 동시성 | 엔진의 원자 착수가 경쟁을 가른다. 워커 N개면 실패하는 `claim`이 N−1번 | 한 번에 한 워커에게만 제안하므로 경쟁이 없다. 원자성은 엔진이 그대로 보장 |
| 바쁜 워커 | 알림을 받고 허가가 없으면 `pending`에 쌓아 두었다가 나중에 착수 시도(`lane.rs`) | 그 자리에서 거절, 다음 워커가 받는다 |
| 큰 페이로드 | 프레임 상한 16 MiB(`ruvent-protocol` `MAX_FRAME`)를 넘으면 등록 불가 | 조각 시리즈로 나눠 등록하고, 어느 워커든 조각을 맡아 정리하고, 마지막 조각을 맞춘 쪽이 결과 이벤트를 낸다 |
| 프록시의 사용자 스트림 | 이벤트를 JSON 텍스트로 바꿔 준다(`message::event_text`). 바이트 payload는 손실 변환 | 요청마다 개별 채널, 응답 조각을 원 바이트 그대로 받아 클라이언트 프로토콜로 내보내야 한다 |
| 프록시 서버 경로 | 내장 프로토콜(`ws`, `http`)만 서비스. 앱 경로는 `router`를 따로 합쳐야 함 | apibond 게이트웨이는 OpenAI·Anthropic HTTP 경로 자체가 프로토콜이다 |

## 3. 라이브러리 변경

### L1. 제안식 착수 전달 (코어·프로토콜·워커 프레임워크)

```text
등록 ─► 엔진(단일 작성자: 대기 표·착수 원자성·완료 제거) ─► 전달 풀(전달자 P개)
                                                           │ 전달자 하나가 이벤트 하나를 맡는다
                                                           ▼
                        워커 서버 1 ──Offer──► 수락? ──예──► 엔진에서 착수(원자) → 전달자는 풀로
                                               └─아니오─► 워커 서버 2 ─► … ─► 모두 거절 → 보류
                        보류된 이벤트: 그 채널의 워커가 여유를 알리면(완료 또는 Ready) 처음부터 다시 제안
```

* **수신 등록:** 워커는 지금처럼 채널을 구독한다. 착수용 이벤트에 대해서는 이것이 "제안 순번에 줄을 선다"는 뜻이 된다. 순번은 구독한 순서다. 발송용 이벤트는 지금처럼 구독자 전원에게 즉시 간다(불변).
* **제안(Offer):** 전달자가 이벤트 전체 엔벨롭과 제안 표지를 워커 한 곳에 보낸다. 워커는 즉시 **수락**하거나 **거절**한다. 수락은 곧 착수다: 엔진이 원자적으로 착수 표지를 찍고 lease를 시작한다. 지금의 `claim(id)` 왕복이 사라진다.
* **거절과 순환:** 거절, 연결 끊김, 응답 기한 초과는 모두 "다음 워커로"다. 순번 끝까지 모두 거절하면 그 이벤트는 **보류**된다. 보류는 시간으로 재시도하지 않는다. 그 채널의 워커가 여유를 알릴 때(착수한 이벤트의 완료 보고, 또는 새 `Ready` 신호) 보류된 이벤트를 처음부터 다시 제안한다. 타이머 없이 "모두 거절하면 처음부터"를 지킨다.
* **전달 풀:** 동시에 진행 중인 제안 라운드는 최대 P개(설정, 기본 64)다. 모두 바쁘면 새 등록은 전달자가 풀려날 때까지 기다린다. 대기 표는 엔진이 지금처럼 가지고 있으므로 이것은 큐가 아니라 "배정 대기"다. 순서는 보장하지 않는다. 순서가 필요하면 원문대로 1번을 처리한 워커가 2번을 등록한다.
* **회수:** lease 만료 회수는 지금과 같다(다음 등록 때 일괄 회수). 회수된 이벤트는 다시 제안 대상이 된다.
* **명시 착수 유지:** `claim(id)`는 남긴다(대기분 목록을 보고 고르는 도구, 테스트). 7개 메서드의 의미는 유지하고, 제안 수락은 착수의 다른 입구로 둔다.
* **워커 프레임워크:** lane은 제안을 받으면 허가가 있으면 수락하고 없으면 거절한다. `pending` 보관과 대기분 재조회(`Refilled`)는 필요 없어져 지운다. 허가가 돌아오면 `Ready`를 보낸다.
* **보장 재검증:** G1(정확히 하나의 착수) 등 제안서 5장의 보장과 인수 테스트를 새 경로로 다시 통과시킨다. 경쟁이 없어지는 것을 측정으로 보인다(워커 N개에서 이벤트당 착수 시도 수 = 1).

### L2. 프록시: 요청 교환과 앱 경로 (`ruvent-proxy`)

* **원 엔벨롭 스트림:** 허브가 사용자에게 주는 것을 JSON 텍스트가 아니라 `Arc<Envelope>`로 바꾸고, 내장 WS·HTTP 프로토콜이 텍스트로 그린다. 텍스트 변환은 이벤트마다 한 번만 한다는 지금 성질은 프로토콜 쪽 캐시로 유지한다.
* **요청 교환 `Proxy::exchange(event)`:** 요청 하나에 개별 응답 채널 `<prefix>.<요청 id>`를 만들고, 먼저 그 채널을 구독해 효력을 확인한 뒤(표지), 착수용 이벤트를 `reply = 그 채널`로 등록한다. 돌려주는 것은 그 채널의 엔벨롭 스트림이다. 드롭하면 구독을 푼다. 원문의 "개별 요청은 개별 채널로 등록되면서 동시에 프록시는 그 채널을 수신한다고 보고"를 라이브러리 기능으로 만든다.
* **앱 경로:** `Server::routes(Router<Proxy>)`로 앱의 경로를 같은 리스너에 얹는다. 내장 프로토콜 feature를 끄면 앱 경로와 `/health`만 서비스한다.

### L3. 조각 시리즈 (`ruvent`의 순수 부분 + `ruvent-client`의 조립)

* **나누기(순수):** 페이로드를 `chunk` 바이트(기본 1 MiB) 조각으로 나눠 엔벨롭 N개를 만든다. 조각마다 시리즈 id, 순번, 전체 조각 수, 전체 길이, 전체 해시를 담는다(작은 고정 머리 + 원 바이트). 시리즈를 보내는 동안 다른 이벤트를 보내도 된다.
* **조립(어느 워커든):** 조각 하나를 맡은 워커는 그 조각을 조립 저장소에 순번 이름으로 저장하고 끝낸다. 저장 뒤 모든 순번이 있으면 **완성 표지를 원자적으로 만든 한 워커만**(배타 생성) 전체를 맞춰 해시를 확인하고 결과 이벤트를 등록한다. 조각은 순서 없이, 중복으로 와도 된다(같은 순번 재저장은 무해).
* **저장소:** 트레이트 하나와 파일 시스템 구현. 워커 서버가 여럿이면 공유 디렉터리를 쓴다. 끝난 시리즈와 일정 시간 미완성인 시리즈는 정리한다(정리 시점은 결정 필요, 6장 D4).
* **순서 맞추기(순수):** 받는 쪽이 순번으로 다시 줄 세우는 유한 버퍼. 스트리밍 응답 조각에도 쓴다.

## 4. apibondrust

```text
client ──HTTP(OpenAI·Anthropic·Responses·Embeddings·Files)──► apibond-gateway (ruvent-proxy, 앱 경로)
   │  인증·모델 확인·세션 id(없으면 발급, 응답 헤더로 돌려줌)·본문 수용
   │  exchange: apibond.r.<요청id> 구독 → apibond.call 착수용 등록(payload: 요청 머리 + 본문 또는 시리즈 참조)
   ▼
ruvent-server (불변: 등록·발송·제안·착수·완료)
   ▼ 제안
apibond-worker (ruvent-client)
   call 서비스: 수락 = 세션 표·부하·상태 소유로 백엔드 선택. 고른 백엔드에 자리가 없으면 거절(다음 워커 서버 → 보류)
                중계 실행기에 넘기고 즉시 완료(워커는 풀로 돌아온다)
   중계 실행기: 백엔드에 원 요청 그대로 → head / chunk(순번) / end / fail 를 apibond.r.<요청id>에 발송용으로 등록
                Responses·파일 ID를 스트림에서 관측해 소유 표 갱신
   upload 서비스: 조각 시리즈 조립 → 완성되면 업로드 call 등록
   cancel 수신: 게이트웨이가 클라이언트 끊김을 알리면 그 요청의 중계를 끊는다
   ▲
gateway: apibond.r.<요청id>의 조각을 순번대로 클라이언트에 쓴다(SSE든 일반 본문이든 원 바이트)
```

| 크레이트 | 내용 | 원본에서 옮기는 것 |
| --- | --- | --- |
| `apibond-wire` | 이벤트 이름과 payload 형식: call(요청 머리 + 본문/시리즈 참조), head, chunk, end, fail, cancel. 순수 | — |
| `apibond-gateway` | 게이트웨이 프로그램. ruvent-proxy의 훅(인증)과 앱 경로. 경로표·오류 봉투·헤더 거르기·본문 수용·세션 id 추출과 발급 | `proxy.rs`의 HTTP 표면, `config.rs`의 수신 쪽 |
| `apibond-worker` | 워커 프로그램. 라우팅(세션 표·용량·상태 소유), 중계 실행기, 조립 | `routing.rs`, `inspect.rs`(관측기), `proxy.rs`의 상위 호출, `config.rs`의 백엔드 쪽 |

* **세션 id:** 원본의 헤더 우선순위를 그대로 읽고, 없으면 게이트웨이가 새 id를 발급해 payload에 넣고 응답 헤더 `x-apibond-session-id`로 돌려준다(원문).
* **라우팅은 착수 시점에 워커가 한다(원문).** 세션 표와 소유 표는 워커 서버 메모리에 있다. 고른 백엔드가 가득이면 거절해 다음 워커 서버로 넘긴다. 원문대로 용량 초과는 드물다고 보고 별도 503 대기열을 두지 않는다. 실 서버가 503을 내면 그 응답이 그대로 클라이언트에 간다.
* **실패:** 연결 실패·타임아웃·워커 내부 오류는 `fail` 이벤트 하나로 관측되고(P6 합격 조건), 게이트웨이는 원본과 같은 상태(502/504 등)와 봉투로 답한다. 다음 요청 처리는 계속된다.
* **큰 본문:** 게이트웨이는 문턱(기본 8 MiB)을 넘는 본문과 모든 파일 업로드를 시리즈로 보낸다. 파일 내용 다운로드처럼 큰 응답도 조각 이벤트로 돌아온다.

## 5. 원본 apibond와 달라지는 것

* 백엔드 용량이 모두 차도 즉시 503을 내지 않는다. 제안이 보류되고, 자리가 나면 다시 제안된다. 실 서버의 503은 그대로 전달한다.
* 세션 표의 주인은 게이트웨이가 아니라 워커 서버다. 게이트웨이는 여러 대여도 앞단 고정이 필요 없다.
* 세션 id가 없는 첫 요청에 게이트웨이가 id를 발급해 돌려준다. 원본은 id 없이 부하로만 골랐다.
* 응답은 이벤트 서버를 거친다. 조각마다 한 단계가 더 붙는다. 지연은 측정해 보고한다(원본 성능 보고서와 같은 부하 형태).

## 6. 결정 필요 (권장안을 적었다)

| # | 질문 | 권장 |
| --- | --- | --- |
| D1 | 제안에 답이 없는 워커(살아 있으나 멈춘 연결)를 어떻게 넘기나 | 제안 응답 기한(기본 2초) 타이머 하나를 선언해 넘기면 거절로 본다. 끊김은 즉시 거절 |
| D2 | 모두 거절한 이벤트를 "처음부터 다시" 언제 | 시간 재시도 없이, 그 채널 워커의 완료 보고·`Ready` 신호가 올 때 |
| D3 | 워커 서버가 여럿일 때 세션 고정 | 1차는 라우팅 권한 워커 서버 하나(나머지는 순번 뒤의 대기). 여러 대가 세션 표를 나눠 갖는 것은 다음 단계 |
| D4 | 미완성 시리즈 정리 | 조립 저장소에 마지막 조각 도착 시각을 적고, 워커가 새 시리즈를 받을 때 기한 지난 것을 함께 지운다(타이머 없음) |
| D5 | 이벤트 타입 단위 수신 등록(원문 "이벤트 타입 또는 이벤트 채널") | 1차는 채널 단위. 타입 단위는 채널 이름에 타입을 넣어 같은 효과를 낸다 |

## 7. 순서와 검증

각 단계는 테스트·문서·`cargo xtask verify`·커밋으로 끝낸다.

1. **L1 제안식 전달.** 엔진 상태 기계 단위 테스트(순번, 거절 순환, 보류와 재제안, 끊김, 회수 후 재제안), 프로토콜 왕복, 워커 프레임워크, 기존 보장(G1 등)과 인수 테스트 재통과. 경쟁 제거를 측정.
2. **L2 프록시 교환과 앱 경로.** 교환의 구독 선행(표지 뒤에만 응답), 드롭 시 구독 해제, 원 바이트 보존.
3. **L3 시리즈.** 순서 섞임·중복·동시 조립에서 정확히 한 번 결과 등록, 해시 불일치 거절, 정리.
4. **apibondrust 추론 API.** Chat·Messages·Responses·Embeddings, 스트리밍과 비스트리밍, 세션 고정, 상태 소유 409, 실패 이벤트. 가짜 추론 서버로 원본의 계약 테스트를 옮기고, 실제 프로세스 셋(이벤트 서버·게이트웨이·워커)으로 인수.
5. **apibondrust Files.** 시리즈 업로드, 큰 응답 다운로드.
6. **측정과 리뷰.** 원본과 같은 부하 형태로 지연·처리량 비교, 코덱스리뷰.

## 8. 위험

* L1은 코어의 착수 경로를 바꾼다. 지금까지 쌓은 보장 테스트가 안전망이지만, 상태 기계·프로토콜·워커 세 층을 함께 바꾸므로 범위가 크다.
* 응답 조각이 모두 이벤트 서버를 지나므로 서버의 발송 처리량이 곧 apibond의 토큰 처리량 상한이 된다.
* 공유 디렉터리 조립 저장소의 배타 생성은 일부 네트워크 파일 시스템에서 원자적이지 않다. 1차는 로컬 디스크(워커 서버 하나)를 전제로 한다.
