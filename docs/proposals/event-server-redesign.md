# 이벤트 서버 재설계 제안

> 상태: **승인·구현됨 (2026-11-23).** 단계별 계획(8장)은 사용자 지시로 파기하고 한 번에 구현했다. 구현에서 달라진 점은 14장.
> 기준 커밋: `f5a1439` (2026-11-22). 개정: 3차(사용자 지시로 두 큐·7개 메서드 모델) + 3·4·5회차 리뷰 반영 + 단일 엔벨롭(사용자 지시). 리뷰 이력은 12장.

## 0. 요약

지금의 ruvent는 엔진·워커·게이트웨이가 **한 프로세스** 안에 있고, 서버가 재시도 상한·dead letter·리액션 표·
보존 로그 같은 정책까지 갖고 있다. 목표는 그 반대다.

* **이벤트 서버는 일곱 개의 메서드만 제공한다.** 착수용 등록, 발송용 등록, 착수 마킹, 완료 보고, 삭제, 구독, 구독 취소.
* **이벤트는 두 종류, 큐도 두 개다.** 착수용 이벤트는 완료 보고로 지워지고, 발송용 이벤트는 발송하는 순간 지워진다.
* **엔벨롭은 하나다.** id, 채널, 재시도 카운트, 착수 여부, 착수 정보를 담는 한 가지 이진 형식을 두 종류가 함께 쓴다. 고정 머리 27바이트(6.0).
* **정책은 워커가 갖는다.** 재시도 상한, 실패 처리, 후속 이벤트, 실패 보고는 모두 이벤트를 처리하는 워커의 로직이다.
* **저널링은 메서드가 아니다.** 재기동 때 미처리 이벤트를 다시 올리는 것이 최우선 목적이고, 설정에 따라 특정 채널·이벤트를 모아 스냅샷으로 남긴다.

```text
일반 클라이언트들 ──► 프록시 서버(ruvent-proxy로 빌드, JSON 설정·훅) ─┐
                                                               ├──► 이벤트 서버 (메서드 7개, 단일 작성자)
                      워커 서버(여러 워커풀, 작업 실행기) ─────┘      ├ 착수용 큐: 완료 보고로 제거
                      내장 워커 = 같은 메서드를 함수로 호출            └ 발송용 큐: 발송 즉시 제거
```

## 2. 사용자가 정한 것 (원문)

판정 기준은 이 원문이다. 설계는 이것을 구현하는 방법이며, 원문과 충돌하면 원문이 이긴다.

**이벤트 서버의 메서드**

> 1. 착수가능한 이벤트 등록
> 2. 발송전용 이벤트 등록
> 3. 특정 이벤트 착수 마킹
> 4. 특정 이벤트 완료보고
> 5. 이벤트 삭제(아직 대기열에 있어야함) 이미 발송되거나 착수되면 발송용 삭제 실패 이벤트 등록. 성공시에도 발송용 성공이벤트 등록
> 6. 특정 채널 구독 등록
> 7. 특정 채널 구독 취소

**착수용 이벤트의 라이프사이클**

> 1. 이벤트 등록
> 2. 착수마킹(이벤트 자체에 상태를 직접 변경):가져간 워커정보를 비롯한 착수정보 기록. 착수시에 타임아웃이 일어날 시간을 워커가 마킹함
> 3. 완료보고(큐에서 지움)
> 4. 지연확인 -> 재시도 카운트 증가 후 대기 상태로 전환. 이때 이벤트 ID는 재발급된다.
> 5. 워커의 실패시 이벤트는 완료처리됨. 이후 처리를 위한 것은 새로운 이벤트로 등록됨
> 6. 재시도 카운트가 늘어난 대기 이벤트의 처리 역시 워커가 착수하고 처리함. 일정 재시도 횟수가 넘어가면 그냥 완료처리하고 새로운 이벤트를 등록할지 실패용 이벤트보고를 할지 말지도 전부 해당 이벤트를 처리할 워커 내부로직으로 해결

**이벤트 형식**

> 기본적인 이벤트 엔벨롭 구조도 문서에 빠져있어. 이벤트 자체의 포멧도 최적화시켜 최대 효율을 갖도록

> 엔벨롭은 적어도 ID, 채널명, 재시도카운트, 착수여부, 착수관련 정보 를 내포할 수 있어야한다.
> 발송전용 이벤트도 이벤트 자체는 한가지 타입의 엔벨롭만 사용한다.

> 특히 서버나 클라이언트를 특정하지 않기 때문에 큰 내용은 필요없다

**이벤트 id**

> ID가 같은 이벤트는 등록될 수 없고 ID는 영원히 고유하지 않아도 충분하지만 비용이 저렴한 UUID7 등을 쓰는 것이 성능에 문제가 없다면 사용한다.

**발송 전용 이벤트**

> 이벤트에는 발송 전용 이벤트와 워커가 접수할 이벤트가 다르다. 발송전용 이벤트는 발송을 통해 큐에서 제거되어야하기 때문이다. 아니면 언제 큐에서 제거할지 판단하기 어렵다.
> 발송 전용큐를 운영하는것도 방법이다. 접수해서 처리할 이벤트큐와 발송전용큐를 따로 운영한다면 발송큐에 있는건 그 시점에 발송해줘야할 연결된 클라이언트(직접 혹은 프록시) 등에게 발송하는 것으로 큐에서 지워질것이다.

**저널링**

> 저널링은 메소드가 아니다. 서버는 저널링을 유지하고 비정상적, 정상적 종료 후 다시 재기동할 때 미처리 이벤트를 메모리에 로드하기 위한 목적을 최우선으로 저널링을 운영한다. 그외에는 서버 설정에 따라 특정 채널이나 이벤트를 일정 단위로 모아 스냅샷화하여 저장한다. 이런 기능은 메소드가 아니다.

**착수 기한**

> 착수이벤트의 타임아웃은 일반적으로 스케줄러가 필요없어.
> 활성화된 이벤트서버는 지속적으로 이벤트가 수신되기 때문에 이벤트 등록시점에 착수이벤트 중 시간이 초과된것을 일괄 미착수 상태로 돌리기만 하면 되기 때문이야. 단 이 때 이벤트 고유번호를 업데이트한다.
> 그러면 타임아웃 이후에 워커가 완료보고해도 그 이벤트 번호에 해당되는 이벤트는 존재하지 않기 때문에 무시하면 된다.

**고가용성과 워커**

> 모든 워커는 재빨리 워커풀로 돌아와야해. 따라서 장기실행을 이벤트용 워커가 들고 있을 수는 없어.
> 꼭 프로세스를 만들지는 않아도 괜찮아. 단지 이벤트용 워커풀이 처리할 수는 없다는거지.

> 고가용성이 젤 중요한 이유는 이것만 확보되면 대부분의 로직은 전부 이벤트 발급을 많이 하는것으로 해결되기 때문이다.

> 아까 APIBOND시나리오에서 실제 API가 실패를 보고하는 것조차 실패이벤트를 등록해버리면 되기 때문이다

**구현 태도**

> 매우 섬세하게 사이사이 사소한 로직도 귀찮다고 가장 안전하고 무거운 구현을 하면 안된다.
> 내가 바라는 이벤트 서버는 엄청 고가용성을 원하고 있어

> 이벤트의 불변성도 그렇게 중요하지 않아. 논리적으로 동시성에서 안전하기만 하면 된다.

**역할과 배치**

> 근데 말야..아주 엄밀하게 워커서버란 존재하지 않아. 왜냐면 이벤트 서버입장에서는 딱히 클라이언트와 워커서버를 구분할 이유가 없단말이지.
> 그저 메소드로 이벤트 등록, 채널 수신, 이벤트착수, 이벤트 완료 라는 기능을 제공해줄 뿐이고 다 자기에게 달라붙은 클라이언트일뿐이야. 인프로세스 워커조차 메소드로 호출하고 통신층을 안거칠 뿐인거지

> 이벤트 서버는 초 고가용성이라서 성능이 엄청나게 좋을텐데 그저 소켓연결이 많아지는 것으로 금방 한계에 봉착할거잖아

> 내가 그리는 그림은 일반 클라이언트는 프록시에 붙고 이벤트서버는 프록시서버와 워커서버와는 직접 연결된 상태로 보는거지

> 이벤트 서버 자체는 여러 프로토콜을 받아줄 수 있다. 프록시 서버는 프로토콜별로 확정 구현으로 존재한다. 프록시서버는 바이너리로 배포되며 프록시서버용 설정은 JSON으로 한다.
> 이벤트서버는 종합적인 API를 제공하며 딱히 워커인지 프록시인지 클라이언트인지 관심없다.
> 내장 워커를 운영할 수 있지만 내장 워커 역시 완전히 동일한 API를 함수로 호출한다는 점만 다르다. 딱히 외부에 구현된 클라이언트와 다른 로직으로 구현되지는 않는다

이 요구 가운데 "프록시 서버는 프로토콜별로 확정 구현", "바이너리로 배포"는 구현 뒤 사용자가 바꿨다(13장
"프록시 형태 변경"). JSON 설정은 그대로다.

> 난 워커풀도 서버이길 원해.
> 하나의 워커서버가 다수의 워커풀을 소유하고 이벤트서버와는 그냥 소켓통신하면 된다고 보고 있어

**프레임워크**

> 프레임웍은 이런 역할별 서버 등을 안정적이고 쉽게 훅 혹은 스프링의 컨트롤러 같은것만 구현하면 될 수 있게 단순화하고 제어를 역전시켜 프레임웍이 관제하게 한다.

**앞선 세션에서 확정된 원칙 (유지)**

> 변하지 않는 원칙중에 하나는 이벤트는 반드시 하나의 워커가 가져간다는것이다. 혹은 발송되거나. 만약 둘이상의 워커나 프로세스에 할당되어야하면 이벤트 자체를 여러개 발급해야해.

> 특히 mq의 락을 효과적으로 관리하는 구조로 pg를 배제하는 건으로 확정짓겠어. 하지만 인메모리만으로 운영되면 안된다.

## 3. 진단: 현재 코드와 결정의 차이

경로는 `crates/ruvent/src/` 기준이다.

| # | 차이 | 근거 | 영향 |
| --- | --- | --- | --- |
| D1 | 허가를 미리 확보하고 핸들러 반환 뒤 `finish`/`release` 응답까지 보유. 스텝 기한 기본 600초 | `worker/mod.rs` `lane`·`execute` | 긴 핸들러가 그 서비스의 허가를 모두 쥐면 새 일을 받지 못한다 |
| D2 | `Context::progress`는 결과를 받지 않는다. 완료가 먼저 반영되면 진행 이벤트가 소리 없이 버려진다 | `worker/context.rs`, `engine/state.rs` `emit` | 장기 작업을 관리해 넘기는 경로가 없다(독립 발행은 `Context::engine()`으로 가능) |
| D3 | 착수에 기한이 없다. visibility 만료 뒤 같은 메시지로 다시 `begin`해도 `Duplicate` | `engine/queue.rs`, `engine/state.rs` | 원격화하면 죽은 워커의 일이 재시작 전까지 묶인다 |
| D4 | 내장 워커가 구체 `Engine`의 `dequeue`·`begin`·`release`·`finish`를 부른다 | `worker/mod.rs` | 기존 원격 프레임으로 같은 워커를 구동할 수 없다 |
| D5 | 클라이언트→서버 프레임은 `Subscribe`·`Event`뿐 | `gateway/mod.rs` | 착수·완료·삭제를 원격으로 부를 수 없다 |
| D6 | 인증·정책 훅을 애플리케이션이 게이트웨이에 주입한다 | `app/mod.rs`, `gateway/mod.rs` | 훅 자체가 바이너리와 양립하지 못하는 것은 아니다. "프록시에 사용자 코드를 넣지 않는다"는 결정에 따라 인증을 어디서 할지 새로 정해야 한다(Q1). 구현 뒤 이 결정은 바뀌어 훅이 프록시 라이브러리로 돌아왔다(13장, 14장) |
| D7 | 게시 중 로그 쓰기 잠금을 쥔 채 클라이언트 대상 이벤트마다 해당 채널의 깨우개 목록을 순회 | `engine/mod.rs` `publish`, `engine/log.rs` | 엔진의 게시 비용이 그 채널의 구독자 수에 비례 |
| D8 | 정지를 폴링 없이 기다릴 API가 없고, `App::run`은 Ctrl-C만 기다리며 `shutdown`은 엔진 오류를 버린다 | `engine/mod.rs`, `app/mod.rs` | 기본 `App::run`은 엔진 장애로 종료되지 않는다 |
| D9 | 핫패스 항목(6.9). 경로는 존재하지만 무게는 측정 전 | 6.9 | 측정 후 채택 |
| D10 | `Events::Custom`이 새 이벤트 반영·스냅샷·생존 레코드 계산에서 사용자 함수를 호출 | `engine/config.rs`, `engine/state.rs` | 서버가 사용자 코드를 돌리지 않는다는 목표와 충돌 |
| D11 | 서버가 시도 상한·dead letter, 트랜잭션 키 중복·충돌 판정, 리액션 표, 보존·영속 선택을 갖는다 | `engine/state.rs`, `engine/config.rs` | 원문은 재시도·실패·후속 판단을 워커에 둔다. 서버가 유지하는 이벤트 처리 규칙은 4.1의 목록(같은 id 등록 거절, 착수 표지 대조, 기한 회수, 발송, 저널·스냅샷)뿐이다. 서비스·채널 권한 검사는 별도(6.8) |
| D12 | 클라이언트용 이벤트를 **발송 여부와 무관하게** 개수·바이트·나이로 지운다 | `engine/state.rs` `remember`, `engine/log.rs` | 원문: "언제 큐에서 제거할지 판단하기 어렵다" |
| D13 | `flush`·`compact`가 공개 `Engine` 메서드 | `engine/mod.rs` | 원문: 저널링은 메서드가 아니다 |
| D14 | `Envelope` 필드 18개, `Command` 13개. 문자열 필드는 `Arc<str>`(파생 이벤트끼리 공유). 저널 파일은 레코드 목록을 bincode로 직렬화해 길이·CRC·종류·사슬을 붙인다. `Put`·`Dead`는 `Command` 전체, 선택된 `Event`는 `Envelope` 전체를 담고 `Del`·`Epoch`·`Exec` 등은 각자 필드가 다르다 | `envelope/mod.rs`, `journal/mod.rs`, `journal/file.rs` | 새 모델에 필요 없는 필드가 많다. 이벤트당 바이트·인코딩 시간은 P0에서 잰다(필드 수만으로 비용을 산출하지 않는다) |

## 4. 목표 구조

### 4.1 이벤트 서버

* 메서드 일곱 개(6.2). 상대가 누구인지 묻지 않는다. 권한은 접속의 서비스 자격으로 판정한다.
* 사용자 코드를 돌리지 않는다. 서버가 갖는 규칙은 같은 id 등록 거절, 착수 표지 대조, 기한 회수, 발송, 저널·스냅샷뿐이다.
* 여러 프로토콜로 직접 받을 수 있고, 프레임 형식을 프록시와 공유한다.
* 단일 작성자. 큐 경합은 잠금이 아니라 소유로 중재한다.

### 4.2 접속자

* 프록시, 워커 서버, 내장 워커 모두 일곱 메서드를 부르는 클라이언트다.
* 메서드는 계약(trait) 하나, 구현 둘이다. 로컬 구현은 엔진에 연산을 직접 보내고, 원격 구현은 소켓으로 보낸다.
* 워커 프레임워크(`App`, `Service`, 작업 실행기)는 계약만 보고, 재시도 상한·실패 처리·후속 이벤트를 워커 쪽에서 정한다.

### 4.3 프록시 서버

* 프록시 서버를 만드는 라이브러리 하나(`ruvent-proxy`). 프로토콜은 cargo feature로 고르고, 켠 프로토콜은 한
  주소에서 함께 열린다. 훅을 쓰지 않은 세 줄짜리 `main`은 JSON 설정대로 도는 서버다. 도메인의 인증·인가는
  훅(인증, 구독, 등록, 전달)만 써서 붙인다(13장 "프록시 형태 변경").
* 채널별로 상위 구독 하나를 두고, 받은 발송용 이벤트를 그 채널의 사용자에게 나눠 보낸다(효력 시점은 6.5).
* 이벤트 서버의 연결 수는 "프록시 수 + 워커 서버 수"다.

### 4.4 워커 서버

* 여러 워커풀과 작업 실행기를 가진 클라이언트 프로세스. 이벤트 서버에 직접 연결한다.
* 가벼운 풀은 내장, 무거운 풀은 워커 서버 여러 대. 배치는 풀 단위.

| G1 | 대기 중인 착수용 이벤트 하나에 여럿이 착수 마킹을 하면 **정확히 하나만 성공**한다. 성공한 쪽만 착수 표지를 받는다 | 항상 |

## 6. 상세 설계

### 6.0 이벤트 엔벨롭

**엔벨롭은 한 가지다.** 착수용과 발송용은 `flags`의 종류 비트만 다르고 배치는 같다. 착수 마킹은 이 엔벨롭의 착수 블록을 **제자리에서** 채운다(원문: "이벤트 자체에 상태를 직접 변경"). 서버는 상대가 워커인지 프록시인지 구분하지 않으므로, 착수 정보는 이름이나 주소가 아니라 작은 숫자 몇 개다.

```text
 고정 머리 27바이트 (모든 이벤트)
 ┌──────────── id 16 ────────────┬─ channel 4 ─┬── type 4 ──┬flags 1┬retry 2┐
 작업 키 8바이트 (착수용, 서버가 보낼 때)
 ┌──── 세대 4 · 도착 순번 4 ────┐
 착수 블록 24바이트 (착수 중, 착수자에게 보낼 때)
 ┌──── 착수 표지 8 ────┬ 착수자 4 ┬ 워커 표지 4 ┬──── 기한 8 ────┐
 선택 필드 (flags 비트가 켜진 것만)
 reply 4 · correlation 16 · principal 4
 payload: 길이 4 + 바이트
```

| 필드 | 크기 | 뜻 |
| --- | --- | --- |
| `id` | 16 | UUIDv7(6.3a). RFC 9562의 16옥텟 순서 그대로. 앞 48비트는 **그 id의 발급 시각**이다. 최초 작업 생성 시각이 아니며 재발급하면 바뀐다. 이 시각을 쓰는 서버 로직은 없다. 등록 요청에서 모두 0(nil)이면 서버가 발급한다 |
| `channel` | 4 | 채널명. 와이어와 파일에서는 이름을 한 번 정의하고 이후 번호로 쓴다(아래 번호표) |
| `type` | 4 | 이벤트 종류(지금의 `action`). 채널과 같은 번호표 |
| `flags` | 1 | 비트 0 종류(착수용·발송용), 비트 1 **착수 여부**, 비트 2~4 선택 필드 유무, 비트 5 `delegate`(구현에서 추가, 14장), 비트 6~7 예약 |
| `retry` | 2 | 재시도 카운트. 서버는 회수 때 올리기만 한다. 65,535에서 멈추며 그 값은 "65,535 이상"을 뜻한다. 발송용과 등록 요청에서는 0 |
| 작업 키 | 8 | `(세대 u32, 도착 순번 u32)`. 서버가 **등록 건**마다 부여한다. 회수·재기동으로 id가 바뀌어도 유지되고, 같은 id를 다시 등록하면 새 값을 받는다. **대기 순서(FIFO)도 이 값의 수치 순서**다(G3) |
| 착수 표지 | 8 | `(세대 u32, 착수 순번 u32)`. 착수 마킹마다 새로 발급. 완료 보고 때 저장된 값과 같은지 대조(G2) |
| 착수자 | 4 | **착수 귀속 번호.** 착수 당시의 `(서비스 자격, 접속)`을 담은 귀속 표 항목을 가리킨다. 그 항목은 활성 착수가 참조하는 동안 유지되고, 번호는 세대 안에서 재사용하지 않는다. 원접속이 끊겨도 같은 자격의 새 접속이 완료할 수 있다(Q6(b)). 내장 워커도 귀속 항목을 하나 받는다 |
| 워커 표지 | 4 | 착수자가 스스로 붙인 번호(풀·워커 구분). 서버는 저장만 하고 해석하지 않는다 |
| 기한 | 8 | 착수 기한. 워커는 기한을 **기간(밀리초)**으로 정해 보내고, 서버가 착수를 처리한 순간의 단조 시계에 더해 **u64 밀리초**로 적는다. 원격 워커와 서버의 시계 차이가 기한을 바꾸지 않고, 가동 기간에 상관없이 넘치지 않는다 |
| `reply` | 4 (선택) | 결과를 보낼 채널. 번호표 |
| `correlation` | 16 (선택) | 한 흐름을 잇는 id |
| `principal` | 4 (선택, 서버가 채움) | 검증된 등록 주체 = 등록 접속의 서비스 자격(6.8, Q11) |
| `payload` | 4 + n | 서버는 해석하지 않는다 |

* **수치는 모두 리틀엔디언**이고, `id`·`correlation`만 RFC 9562 옥텟 순서다.
* **세대.** 서버 전체에 하나인 단조 증가 카운터다. 기동할 때, 그리고 도착 순번이나 착수 순번이 u32를 다 쓰면 다음 값으로 올리고, 저널에 내구화한 **뒤에** 그 세대의 번호를 쓴다. 순번은 새 세대에서 0부터 다시 센다. 같은 저널 계보 안에서 `(세대, 순번)`은 반복되지 않는다. 세대가 u32를 다 쓰면 서버는 기동을 거부한다(약 43억 번의 기동·순번 소진). 착수 순번 소진으로 세대가 올라도 기존 착수는 저장된 표지로 대조하므로 영향이 없다.
* **크기(인코딩 기준).** 발송용 31바이트 + payload, 대기 중 착수용 39바이트 + payload, 착수 중 착수용 63바이트 + payload(각각 payload 길이 4바이트 포함, 선택 필드 없음). 선택 필드는 쓸 때만 붙는다. 이름 정의, 프레임·저널 외곽, 상주 메모리의 정렬은 별도다. 상주 비용(레코드, 번호표, 기한 힙, id 색인, 수신 버퍼 보존)은 P0·P2에서 따로 잰다.
* **레코드 종류별로 실리는 필드.** 한 가지 논리 엔벨롭을 쓰되, 실리는 필드는 바깥 레코드 종류가 고정한다. 디코더는 레코드 종류와 `flags`만 보고 길이를 안다.

  | 바깥 레코드 | 실리는 필드 | 금지(받으면 그 프레임 거절) |
  | --- | --- | --- |
  | 등록 요청(메서드 1·2), 완료의 후속 | 고정 머리, 선택 필드(`reply`·`correlation`), payload | `claimed`, `retry`≠0, `principal` 비트 |
  | 착수 가능 알림, 구독 대기분 항목 | 고정 머리 + 작업 키(35바이트) | — |
  | 착수 응답(메서드 3) | 고정 머리 + 작업 키 + 착수 블록 + 선택 필드 + payload | — |
  | 발송 전달 | 고정 머리 + 선택 필드 + payload | `claimed`, `retry`≠0 |
  | 저널 등록 본문 | 고정 머리 + 작업 키 + 선택 필드 + payload. `claimed`는 항상 0 | `claimed` |

  어느 레코드든 `발송용 + claimed`, 예약 비트, 남는 바이트는 거절한다. 방향별 고정 바이트 예제를 시험 자료로 둔다.
* **제자리 변경은 작성자의 상주 사본에만.** 단일 작성자가 착수용 이벤트의 상주 엔벨롭을 단독 소유하고 착수 블록·id·retry를 제자리에서 바꾼다. 송신 버퍼, 저널 기록기, 운영 수집기에 넘길 때는 **그 순간의 머리 값(최대 63바이트)을 복사**하고 이름 핸들과 payload는 참조로 공유한다. 그래서 착수 A의 응답이 송신되기 전에 회수·재착수가 일어나도 A에게는 A의 id와 표지가 간다. 이벤트별 잠금이나 전체 복제는 없다.
* **발송용 `seq`는 두지 않는다.** 한 접속에 넘긴 이벤트는 넘긴 순서대로 도착하므로 순서는 연결이 보장한다. 인계 전 순서는 서버가 정한다(6.5).
* **엔벨롭에서 빼는 것과 그 의미:**

  | 지금 필드 | 새 모델에서 | 잃는 의미 |
  | --- | --- | --- |
  | `stream`, `position` | 없어짐. 보존 로그가 없다 | 범위 읽기 커서. `stream`을 입력으로 쓰던 현행 파생 id도 그대로 유지되지 않는다 |
  | `transaction_key` | `id`가 대신한다(G8) | **기존 멱등 의미를 폐기한다.** 지금은 서로 다른 id에 같은 키를 줄 수 있고 완료 뒤에도 일정 기간 판정한다. 새 모델은 활성 id 충돌만 막는다 |
  | `kind`, `audience`, `source` | 대응하지 않는다. 종류 비트는 이 이벤트를 **어떻게 처리할지**(착수 / 발송)를 고른다 | `audience`는 지금 이벤트가 클라이언트 읽기 색인에 들어가는지를 정하며, `Client` 대상 `Command`도 워커가 착수한다. 일대일 대응이 없으므로 두 효과가 필요하면 이벤트를 두 건 등록한다(6.1). `kind`·`source`는 서버에서 폐기하고 필요하면 `type` 이름이나 payload로 표현한다 |
  | `created_at` | 없어짐 | 지금 서버는 0일 때만 채우고, 나이 기반 보존 정리가 가장 오래된 이벤트의 이 값을 쓴다. 새 서버는 보존 로그가 없으므로 그 용도가 사라진다. `id`의 시각은 발급 시각일 뿐이다 |
  | `causation`, `correlation_id` | `correlation` 16바이트 하나 | 직전 원인 id(`causation`)는 폐기한다. 문자열 흐름 id는 16바이트 id로 바뀐다. 필요하면 payload로 |
  | `session_id`, `run_id`, `turn_id` | payload로 | 지금 `session_id`는 스트림 생성과 `OwnedSessions`의 소유·응답 채널 판정에 쓰인다. 새 모델에서 이 판정은 프록시와 서비스 자격의 채널 범위가 맡는다(6.8, Q1). `run_id`·`turn_id`의 파생 전파는 워커가 한다 |
  | 게이트웨이가 기록하던 인증 사용자 | `principal`은 서비스 자격 | 같은 프록시를 쓰는 사용자 둘이 같은 `principal`을 갖는다. 사용자 단위 신원은 Q1에서 따로 정한다(Q11) |

* **번호표(interning)는 세 공간으로 나눈다.**
  * **서버 안:** 이벤트는 채널·종류·주체를 번호가 아니라 **공유 이름 핸들**(참조 카운트)로 든다. 큐, 송신 버퍼, 저널 기록기, 운영 수집기 중 어디든 핸들을 쥐고 있는 동안 이름이 살아 있고, 마지막 참조가 사라지면 사전에서 빠진다. 사전 크기는 그 순간 살아 있는 이름 수에 비례하며 별도의 절대 상한은 두지 않는다. 단일 작성자만 사전을 바꾼다.
  * **접속마다:** 그 접속의 송신 태스크가 **송신 순서대로 인코딩하면서** 정의·사용·초기화를 함께 정한다. 사전에 없는 이름이면 정의를 먼저 쓰고, 사전이 상한을 넘으면 "사전 초기화"를 쓴 뒤 처음부터 다시 정의한다. 지연된 이벤트도 같은 순서로 인코딩되므로 옛 번호가 새 이름으로 해독되지 않는다. 수신 쪽 사전도 같은 상한이다.
  * **파일마다:** 저널 세그먼트와 압축본은 자기 안에 이름 정의를 갖는다. 파일 하나만으로 해독할 수 있다.
* **본문 코덱은 하나, 바깥 레코드는 둘.**
  * **와이어:** 접속 수립 때 프로토콜 버전을 맞춘다. 프레임은 `(프레임 길이, 레코드 수, 레코드들)`이고 레코드는 메서드 요청·응답·이벤트·사전 정의·사전 초기화다. 초기안은 버전 하나만 지원하므로 모르는 버전이나 금지 조합은 프레임째 거절한다. 혼합 버전을 건너뛰어야 할 때가 오면 레코드 길이를 더한다. JSON은 브라우저 쪽 프록시에서만 쓴다.
  * **저널:** 쓰기 단위는 **배치 프레임** `(길이, CRC, 사슬, 레코드들)`이다(지금 v1과 같은 경계). 레코드 종류는 등록, 착수 표시(작업 키만), 제거(완료·삭제), 회수(작업 키, 새 id, retry), 세대, 이름 정의다. **한 연산이 만든 순변화(완료의 부모 제거와 후속 등록 전부)는 반드시 한 배치 프레임에 들어간다.** 복구는 완전한 프레임까지만 재생하므로 쓰기가 어디서 끊겨도 `부모 유지·후속 0건` 또는 `부모 제거·후속 전부` 중 하나다. 형식 버전이 다른 파일은 `InvalidData`로 거부하고 바이트를 보존한다. 유효한 머리 뒤의 찢어진 마지막 프레임은 버리고 앞부분을 복구한다. 두 경우를 따로 시험한다.
* **payload 공유와 분리.** 받은 버퍼의 조각을 참조 카운트로 공유해 발송에 그대로 쓴다. 다만 작은 조각 하나가 큰 수신 버퍼 전체를 붙잡을 수 있으므로(예: 1 MiB 프레임에서 32바이트 이벤트 하나가 오래 대기), **착수용 큐에 오래 남는 이벤트는 조각이 원 버퍼보다 훨씬 작으면 한 번 분리 복사**하는 안을 P0·P2에서 측정해 정한다. 파일 쓰기는 최종 프레임 인코딩에서 한 번 복사한다. "복사 없음"은 수신에서 발송까지의 경로를 뜻한다.

### 6.1 두 종류의 이벤트, 두 개의 큐

| | 착수용 이벤트 | 발송용 이벤트 |
| --- | --- | --- |
| 등록 | 메서드 1 | 메서드 2 |
| 엔벨롭 | 같은 형식(6.0). 작업 키, 착수 블록을 쓴다 | 같은 형식. 고정 머리 + 선택 필드 + payload |
| 담기는 곳 | 착수용 큐(메모리, 저널 대상) | 발송용 큐(등록 처리 중에만 존재) |
| 받는 쪽 | 착수 마킹에 성공한 워커 하나 | 등록 처리 순간의 채널 구독 접속 전부 |
| 제거 시점 | 완료 보고, 삭제 | 송신 버퍼로 넘기는 순간 |
| 저널 | 미처리분을 기록(재기동 때 다시 올림) | 기록하지 않음. 설정된 채널·이벤트만 운영 스냅샷 |
| 기한 | 착수 때 워커가 정함 | 없음 |

한 사실이 클라이언트에게도 보여야 하고 워커도 처리해야 하면 이벤트를 두 개 등록한다.

### 6.2 메서드 일곱 개

| # | 메서드 | 동작 | 응답 |
| --- | --- | --- | --- |
| 1 | 착수용 이벤트 등록 | 대기 상태로 큐에 넣고 작업 키를 부여한다. id는 등록자가 줄 수 있고 없으면 서버가 발급(6.3a). 착수용 큐에 같은 id가 있으면 거절. 배치의 첫 외부 등록 직전에 기한 회수를 한 번 한다(6.4). 그 채널 구독자에게 착수 가능 알림(고정 머리 + 작업 키)을 보낸다 | id·작업 키 / 중복 거절 |
| 2 | 발송용 이벤트 등록 | 배치의 첫 외부 등록 직전에 기한 회수를 한 번 한다. 착수용 큐에 같은 id가 있으면 거절. 이 순간의 채널 구독 접속마다 송신 버퍼에 넣고 끝. 저장하지 않는다 | 접수 / 중복 거절 |
| 3 | 착수 마킹(id, 워커 표지, 기한 기간) | 대기 상태이면 엔벨롭의 착수 블록을 제자리에서 채우고(착수 여부, 착수 표지, 착수자 귀속, 워커 표지, 기한) 기한 힙에 넣는다 | 성공(착수 블록과 작업 키를 포함한 엔벨롭 전체. 인계 시점의 값) / 실패(없음·이미 착수) |
| 4 | 완료 보고(id, 착수 표지[, 후속 이벤트들]) | id·착수 표지가 현재 착수와 일치하고, 보고 접속이 착수 당시의 서비스 자격(착수 귀속 항목)과 같고, 후속이 모두 등록 가능하면(활성 id와도, 후속끼리도 겹치지 않음) 이벤트를 지우고 후속을 같은 스텝에 등록 | 완료 / 무효(이번 요청은 효력 없음, 사유) |
| 5 | 삭제(id, 결과 채널, 요청 표지[, 작업 키]) | 대기 상태이면 지운다. 작업 키를 주면 그 등록 건일 때만 지운다. 결과 채널에 발송용 성공 또는 실패 이벤트를 정확히 한 건 등록 | 성공 / 실패 |
| 6 | 채널 구독(채널[, 이어받을 작업 키]) | 이 접속을 채널 구독자로 등록한다. 착수용 이벤트가 있는 채널이면 **대기분 참조를 작업 키 순으로, 한 응답 상한(설정)까지** 함께 준다. 더 있으면 "이어짐"과 마지막 작업 키를 주고, 접속은 같은 메서드를 그 키로 다시 불러 이어받는다. 구독 반영 이후의 등록은 알림으로 온다 | 접수(대기분 일부, 이어짐 여부) |
| 7 | 채널 구독 취소 | 이 접속을 구독자에서 뺀다. 이 처리 이후의 발송은 받지 않는다 | 접수 |

* 저널링, 스냅샷, 압축은 메서드가 아니다(6.7). 지금의 `flush`·`compact` 공개 메서드는 내부로 옮긴다.
* 한 배치 안의 연산은 받은 순서대로 적용한다. 구독·취소·발송의 효력은 그 순서를 따른다(6.5).
* 착수 마킹과 삭제의 id는 **호출이 처리되는 시점에 큐에 있는 그 id**를 뜻한다. 같은 id를 다른 일에 재사용한 경우 옛 요청이 새 일에 닿을 수 있으며, 특정 등록 건을 겨냥하려면 삭제에 작업 키를 붙인다. 착수는 알림에 실린 작업 키와 응답의 작업 키를 워커가 비교해, 다르면 바로 완료 처리하지 않고 새 일로 다룬다.
* 대기분을 이어받는 구독 재호출은 이미 구독 중이면 목록만 준다. 회수된 일은 **작업 키를 유지한 채 새 id로** 돌아오므로 마지막 키보다 앞에 다시 나타날 수 있다. 워커는 받은 알림을 하나라도 버렸으면 다음 여유 때 키 없이 처음부터(상한 단위로) 다시 읽는다. 버리지 않았으면 마지막 키로 이어받는다.
* 프록시가 사용자 대신 부를 때는 프레임에 위임 신원이 붙는다(Q1).

### 6.3 착수용 이벤트의 라이프사이클

```text
 등록 ──► 대기 ──(3 착수 마킹: 워커 정보, 기한 → 착수 표지)──► 착수 ──(4 완료 보고: id + 표지)──► 제거
           ▲                                                    │
           └── 기한 지남(등록 처리 직전에 확인): 재시도 +1, id 재발급, 표지 무효 ──┘
 대기 ──(5 삭제)──► 제거 (+ 성공 통지)
```

* **완료 보고는 성공과 실패를 구분하지 않는다.** 워커가 실패하면 그 이벤트를 완료 처리하고, 이후 처리가 필요하면 새 이벤트로 등록한다. 실패 보고 이벤트를 낼지도 워커가 정한다(선택).
* **재시도 카운트**는 엔벨롭의 필드다. 서버는 회수 때 올리기만 하고 상한을 판정하지 않는다.
* **착수 정보는 엔벨롭 안에 있다.** 착수 마킹은 착수 블록을 채우고, 회수는 착수 여부를 끄고 블록을 비운다. 별도의 레코드 머리는 없다.
* **착수 표지**는 `(서버 세대, 착수 순번)`이다. 착수 마킹마다 새로 발급한다. 회수로 id가 바뀌면 일반적인 옛 완료는 id에서 이미 걸러지고, 표지는 **같은 id의 재사용과 서버 단독 재기동**까지 막는다. 서버 세대는 기동마다 한 번 정해 저널에 내구화한 **뒤에** 첫 응답을 낸다. 완료 이력이나 지나간 id 표는 필요 없다.
* **작업 키**는 서버가 등록 건마다 부여하는 `(등록 세대, 도착 순번)`이다. 회수·재기동으로 id가 바뀌어도 유지되고, 같은 id로 새로 등록된 일은 다른 키를 받는다. 워커가 외부 효과의 중복을 거를 때와 복구 비교에 쓰며, 대기 순서도 이 키의 순서다(G3).
* **서버에서 사라지는 것:** 시도 상한, dead letter, 재시도 지연 상태, 실패 결과 자동 생성, 리액션 표, 완료 기록 창, 기한 연장.

### 6.3a 이벤트 id

* 형식은 **UUIDv7**(앞 48비트 밀리초 발급 시각 + 난수). P0에서 생성 비용을 잰다(현행 엔진의 무작위 id는 v4이고, 의존성에 `v7` 기능을 켜야 한다).
* **같은 id의 이벤트는 등록할 수 없다.** 착수용 큐에 같은 id가 있으면(대기든 착수든) 착수용·발송용 등록과 후속 모두 `중복 거절`이다(G8). 해시 조회 한 번이다.
* id는 **영원히 고유할 필요가 없다.** 큐를 떠난 id는 다시 등록할 수 있다. 발송을 마친 id의 이력도 두지 않는다. id 재사용이 옛 보고와 섞이는 문제는 착수 표지가 막는다(G2).
* 등록자는 id를 줄 수 있다(Q5). 서버는 받은 id가 UUID 형식(버전·variant)인지 검사한다. 없으면 서버가 발급한다.
* **서버가 발급·재발급하는 id**는 현재 큐에 있는 id와 대조하고, 겹치면 다시 뽑는다. UUIDv7의 시각부만으로 충돌이 없다고 가정하지 않는다.
* 발송용 이벤트의 id는 수신자가 중복을 거르는 데도 쓴다.

### 6.4 착수 기한: 스케줄러 없는 일괄 회수

* 착수 마킹 때 워커가 기한을 기간으로 정하고, 서버가 자기 시계로 기한 시각을 적는다(6.0).
* 서버는 착수 이벤트를 기한 순 힙에 둔다. **배치의 첫 외부 등록(메서드 1·2)을 처리하기 직전에** 힙의 맨 앞만 보고 기한 지난 것을 모두 꺼내 재시도 카운트를 올리고, id를 재발급하고, 착수 블록을 비우고, 대기로 되돌린다. 지난 것이 없으면 비용은 비교 한 번이다.
* 회수를 일으키는 것은 외부에서 온 등록뿐이다. 완료 보고에 실린 후속 등록과 삭제 결과 통지는 회수를 일으키지 않는다.
* 힙 항목은 `(기한 u64, 작업 키, 착수 표지)`다. 꺼낼 때 그 레코드가 아직 같은 표지로 착수 중일 때만 적용한다. 완료된 항목은 버린다.
* 회수된 이벤트는 새 id로 착수 가능 알림이 다시 나간다. 작업 키와 대기 순서는 그대로다.
* **늦은 완료의 경계(Q10):** 기본안은 "실제 회수가 마감"이다. 회수 전에 도착한 완료 보고는 표지가 맞으면 받는다. 회수 전이면 다른 워커가 가져갈 수 없었으므로 G1이 깨지지 않는다. 대안은 "기한 자체가 마감"으로, 완료 보고 때 그 레코드의 기한만 비교해 지났으면 무시한다.
* **대가:** 등록이 끊긴 동안에는 회수도 일어나지 않는다(원문 방식의 성질). 그동안 기한 지난 착수를 삭제하려 하면 아직 착수 중이므로 실패한다.
* 접속이 끊긴 워커의 착수를 즉시 회수할지는 Q6.

### 6.5 발송: 등록하는 순간 보내고 지운다

* **효력 시점.** 발송 대상은 그 발송 등록이 처리되는 순간의 구독 집합이다. 같은 배치의 `구독 → 발송 A → 취소 → 발송 B`는 A만 받는다. 이미 송신 버퍼로 넘어간 이벤트는 취소 뒤에도 소켓에 도착할 수 있다.
* 송신 버퍼로 넘기는 순간 큐에서 사라진다. 이벤트 서버에는 클라이언트용 보존 로그, 이벤트 중복 제거 표, 범위 읽기, 보존 한도 판단이 없다(D12 해소).
* **버퍼 포화는 연결 종료다.** 놓침 표시를 같은 버퍼로 보낼 수 없을 수 있으므로, 가득 찬 접속은 끊는다. 클라이언트에게는 연결 종료가 손실 신호다(G5·G6).
* **순서는 연결이 보장한다.** 한 접속에 넘긴 이벤트는 넘긴 순서대로 도착한다. 별도의 발송 순번은 없다.
* **Strict에서의 공개 경계.** 착수용 등록, 완료와 그 후속, 삭제에 딸린 외부 통지(착수 가능 알림, 발송용 후속, 삭제 결과)와 성공 응답은 그 전이가 디스크에 닿은 **뒤에** 송신 버퍼로 넘긴다. 쓰기가 실패하면 그 전이의 통지와 성공 응답은 0건이다. 메서드 2로 바로 등록한 발송용 이벤트는 저널 대상이 아니므로 기다리지 않는다(아래 접속별 순서는 지킨다). `Scheduled`는 기다리지 않는다.
* **착수와 회수는 기다리지 않는다(Strict 포함).** 착수 응답과 회수 뒤의 재알림은 바로 보낸다. 착수 표시·회수 레코드가 쓰이기 전에 서버가 죽으면 재기동 뒤 그 이벤트는 대기 상태이고, 세대가 바뀌어 옛 표지는 어차피 무효다. 대가는 그 경우 Q7의 +1이 빠져 재시도 카운트가 하나 적을 수 있다는 것뿐이다. 착수는 가장 잦은 연산이므로 디스크를 기다리게 하지 않는다.
* **한 접속의 송신 순서는 처리 순서를 따른다.** 디스크를 기다리는 통지가 있는 접속에는 그 뒤에 처리된 항목(직접 발송 포함)도 그 뒤에 선다. 기다리는 것이 없는 접속에는 바로 넘긴다. 대상 구독 집합은 각 연산을 처리할 때 정한다.
* 끊겼던 클라이언트는 그동안의 발송을 받지 못한다(Q8).
* **프록시 집약.** 프록시는 채널별로 상위 구독 하나만 둔다. 첫 사용자의 구독 성공은 상위 구독이 반영된 **뒤에** 알린다. 공유 중인 채널에 새 사용자가 붙으면, 그 사용자 구독이 프록시에 반영된 시점 이후에 받은 이벤트만 보낸다(이미 프록시 버퍼에 있던 이전 이벤트는 보내지 않는다). 마지막 사용자가 떠나면 상위 구독을 취소한다. 상위 연결을 다시 맺으면 현재 구독 집합을 다시 등록한다.
* 깨울 대상 확보는 같은 임계구역에서, 통지는 잠금 밖에서 한다(D7).

### 6.6 장기 작업과 실패는 이벤트로

* 이벤트 워커는 짧게 끝낸다. 긴 일은 **작업용 착수 이벤트**를 완료 보고의 후속으로 등록하고(Q4) 자기 이벤트를 완료한다. 작업 실행기는 별도 예산으로 그 이벤트를 착수하며, 긴 기한을 직접 정한다.
* **Q4(a)의 원자성.** 서버는 현재 착수(id·표지·서비스 자격), 후속 id의 중복 여부(활성 id와, 후속끼리), 채널 권한을 먼저 모두 검사하고, 모두 유효할 때만 부모 제거와 후속 등록을 한 스텝으로 반영하고, 저널에도 **한 배치 프레임**으로 쓴다(6.0). 하나라도 무효면 부모는 착수 상태로 남고 후속은 0건이며 사유를 돌려준다.
* **무효 응답의 뜻.** "이번 요청은 효력이 없다"만 뜻한다. 완료 응답만 유실된 뒤의 재전송은 부모가 이미 지워졌으므로 무효이고, **후속은 자식이 이미 끝났든 아니든 0건**이다(G2). 워커는 무효를 근거로 후속을 따로 다시 등록하지 않는다.
* `Strict`에서는 부모 제거와 후속 등록이 디스크에 닿은 뒤에 완료 응답과 후속의 외부 통지를 낸다(6.5). 쓰기가 실패하면 성공 응답·통지 모두 0건이고, 재기동하면 마지막 완전한 내구 지점의 상태다. 소켓 수신이나 재기동 뒤 재발송은 보장하지 않는다.
* 작업 실행기가 죽으면 그 이벤트는 다음 등록 때 회수되고(id 재발급, 재시도 +1), 다른 실행기가 가져간다. 재시도 카운트를 보고 포기할지는 실행기의 로직이다.
* 실패를 알릴 필요가 있으면 실패 이벤트를 등록한다(선택). 외부 API의 실패 보고도 마찬가지다.

### 6.7 저널

메서드가 아니며 서버 설정으로만 동작한다.

| 목적 | 대상 | 방식 |
| --- | --- | --- |
| **재기동 복구 (최우선)** | 대기·착수 중인 착수용 이벤트(엔벨롭: id, 채널, 종류, 재시도 카운트, 작업 키, 착수 여부, 선택 필드, payload), 서버 세대, 이름 정의 | 순변화를 뒤따라 기록(레코드 종류는 6.0). 착수 블록 내용은 쓰지 않는다. 재기동 때 메모리에 다시 올린다. 쓰기 실패는 서버 정지(지금과 같다) |
| 운영 스냅샷 | 설정에서 고른 채널·이벤트(발송용 포함) | **이벤트가 발생할 때** 별도 수집기가 모아 일정 단위(개수·시간)로 별도 파일에 쓴다. 복구 저널과 섞지 않는다. 재기동 때 다시 발송하지 않는다. 쓰기 실패는 기록하고 서버는 계속 돈다. 정상 종료 때 남은 부분을 쓴다 |

* **재기동.** 새 세대를 정해 저널에 내구화한 뒤에 첫 응답을 낸다. 세대가 바뀌므로 재기동 전의 모든 착수 표지가 무효다(대기 상태로 복구된 이벤트에 대한 옛 보고도 포함). 착수 중이던 이벤트는 대기로 되돌리고 id를 재발급한다. 재시도 카운트 처리는 Q7.
* **대기 순서.** 큐 순서는 작업 키 `(등록 세대, 도착 순번)`의 순서다(UUID 정렬에 기대지 않는다). 복구한 이벤트가 재기동 뒤 등록보다 앞선다.
* **복구 동치(실행 가능한 기준).** 같은 내구화 지점에서 순변화 재생·압축본 재생·실제 재시작이 ① 같은 미처리 이벤트의 내용·상태·재시도 카운트·대기 순서를 주고, ② 착수 중이던 것에만 재발급과 Q7을 적용하며, ③ 재기동 전 표지의 보고가 모두 무효다. 재발급 id는 실행마다 다르므로 작업 키(등록 건마다 고유)로 대응시켜 비교한다.
* 순변화 기록, 쓰기 비중첩, 사슬, 압축, `Scheduled`/`Strict` 정책은 유지한다. 형식 버전을 2로 올리고, v1 파일은 `InvalidData`로 거부하며 바이트를 보존한다(Q9).

### 6.8 인증·권한 (Q1, 미결정)

* 이벤트 서버는 서비스 자격을 가진 접속만 받는다. 자격마다 쓸 수 있는 메서드와 채널 범위를 둔다. 엔벨롭의 `principal`은 P2에서 **등록한 접속의 서비스 자격**을 뜻한다. 프록시가 대신 부른 최종 사용자의 위임 신원은 `principal`과 섞지 않고 Q1에서 따로 정한다(Q11).
* 최종 사용자 인증은 프록시가 받는다. 처리 방식은 Q1: (a) 인증용 착수 이벤트를 인증 워커가 처리 (b) 이벤트 서버의 선언적 규칙 (c) 프록시 JSON의 정적 토큰.
* (a)를 고르면 인증 결과의 발급 주체(인증 워커 자격), 결과의 귀속(프록시 접속, 인증 요청 표지, 사용자 세션), 위임 신원과 결과 채널의 대조를 함께 정한다.

### 6.10 장애 표면화 (D8)

* `Started`에 엔진 정지를 폴링 없이 기다리는 future를 둔다. `App::run`은 엔진이 멈추면 원인과 함께 끝나고, 바이너리는 실패 코드로 종료한다. `shutdown`은 엔진 종료 오류를 전파한다.

**P2의 G별 합격 조건**

| 보장 | 결정적 합격 조건 |
| --- | --- |
| G1 | 대기 이벤트 하나에 워커 둘이 경합하면 정확히 한 성공. 패자의 완료 보고는 무효과 |
| G2·G8 | 대기·착수 중 같은 id로 착수용·발송용·후속 등록 모두 거절, 한 완료의 후속끼리 같은 id 거절(부모 유지·후속 0건). 회수 후 옛 id로 새 이벤트를 등록하고 같은 워커가 다시 착수한 상태에서 옛 완료·착수·삭제가 늦게 도착할 때의 결과(완료는 무효, 착수·삭제는 6.2대로 현재 id에 적용, 작업 키를 붙인 삭제는 실패). 다른 서비스 자격 접속의 완료는 무효. 재발급 후보로 옛 id와 다른 활성 id를 강제로 공급해 다시 뽑는지 확인 |
| G3 | 재실행에서 작업 키는 유지되고 착수 표지는 바뀜. **A의 `x`가 `y`로 회수된 뒤 B를 `x`로 등록하면 A·B의 작업 키가 다름.** 옛 워커가 살아 있는 단절과 실제 종료를 구분 |
| G4 | 같은 내구 지점의 순변화·압축본·실제 파일 재시작 비교. Strict 응답 전후, Scheduled가 대기까지만 기록한 서버 단독 재시작, 복구 중 재종료, 정상 종료, Q7의 카운트·대기 순서, v1 거부 후 원본 바이트 보존 |
| G5·G6 | 같은 배치의 `구독→발송→취소→발송`, 구독자 0명, 포화 시 연결 종료. 이벤트 서버에 직접 붙은 접속의 송신을 멈춘 상태에서도 다른 접속의 등록·착수·발송이 진행 |
| G7 | 대기·착수·없음 세 경우와 착수·삭제 양쪽 순서(`삭제 → 착수`는 성공 통지 1건과 착수 실패, `착수 → 삭제`는 착수 유지와 실패 통지 1건), 이미 발송된 id. 결과 채널과 통지 건수 일치 |
| Q4 | 부모 완료와 후속 중복 거절(부모 유지·후속 0건), 성공 응답 유실 뒤 재전송(무효·후속 0건), 회수 선행을 각각 주입. **Strict 쓰기 실패: 그 전이에서 공개된 후속·알림 0건, 성공 응답 0건, 재생 상태는 마지막 완전한 내구 지점.** Q4(b)를 고르면 이 행 대신 두 호출 사이 실패의 기대 상태를 정해 시험 |
| Q10 | 같은 만료 입력으로 `완료 → 등록`과 `등록 → 완료` 두 순서. 고른 안의 결과가 각각 정해진 대로 |
| 엔벨롭 | 본문 코덱 왕복(모든 flags 조합)과 레코드 종류별 고정 바이트 예제, 금지 조합·예약 비트·남는 바이트·모르는 버전의 프레임 거절, `retry` 65,535 포화. **인계 시점:** 송신·저널 기록·운영 수집을 각각 멈춘 상태에서 회수·재착수한 뒤 각 소비자가 원래 시점의 id·표지를 읽음. **기한:** 가상 시계로 단조 시계 49.7일 경계 전후에 30초 착수가 정확히 30초 뒤 만료. **세대:** 도착·착수 순번의 마지막 값을 주입해 세대 전진 → 압축 → 재시작 → 신규 등록 후 작업 키 보존·FIFO·옛 완료 무효. **귀속:** 원접속이 끊긴 뒤 같은 자격의 새 접속 완료는 성공, 다른 자격은 무효, 등록자와 착수자가 다른 경우. 번호표: 일회성 채널·주체를 재사용하는 부하에서 서버 사전·접속 사전이 상한 안, 마지막 참조가 지연 송신일 때 이름이 바뀌지 않음, 압축본 단독 해독, 재기동 뒤 이름 복원. 저널: 형식 버전 불일치(원본 보존)와 찢어진 마지막 쓰기(완전한 앞부분 복구)를 따로. **후속이 여럿인 완료의 배치 프레임을 바이트 경계마다 잘라 복구하면 `부모 유지·후속 0건` 또는 `부모 제거·후속 전부`만 나옴** |
| 순서·공개 | Strict에서 같은 접속에 `완료의 발송 후속 A → 직접 발송 B`면 A, B 순서. 착수 응답 직후 쓰기 실패·재기동이면 대기 상태, 옛 표지 무효. 배치 중 구독 취소와 쓰기 실패 조합 |

## 9. 검증 계획

* 정적·런타임·인수 테스트망과 변이 테스트를 유지하고 단계마다 확장한다. 서버 정책이 빠지는 만큼 해당 테스트(시도 상한, dead letter, 중복 판정, 보존 로그)는 워커 프레임워크 쪽으로 옮기거나 지운다.
* 인수 테스트는 2장 원문을 인용하고 5장 보장을 8장 합격 조건으로 판정한다.
* 성능은 이벤트당 비용(바이트, 인코딩 시간, CPU, 할당), 초당 발급·소비 이벤트 수, 엔진 p99로 잰다.

> 알아서 자기 플랫폼에 맞게 빌드하면 되는게 아닌가?

> 오히려 라이브러리기 때문에 여러 프로토콜별 프록시를 관리하지 않고 라이브러리로 구축할 때 라이브러리가 지원하는 프로토콜을 선택해서 빌드하는 것으로 갈음할 수 있지
