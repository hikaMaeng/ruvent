# 이벤트 서버 재설계 제안

> 상태: **승인 대기.** 구현 전 계획이다. 승인 전에는 코드를 바꾸지 않는다.
> 기준 커밋: `f5a1439` (2026-11-22). 외부 리뷰 반영: 2회(12장).

## 0. 요약

지금의 ruvent는 엔진·워커·게이트웨이가 **한 프로세스** 안에 있다. 단일 작성자 엔진과 순변화 저널은
검증되어 있지만, 사용자가 정한 목표와는 다음이 다르다.

1. 이벤트 워커가 오래 걸리는 일을 붙잡아 그 풀의 처리를 멈출 수 있다.
2. 착수(실행 소유권)에 **기한이 없어** 별도 프로세스의 워커가 죽으면 일이 묶인다.
3. 장기 작업을 워커 밖으로 넘기는 **프레임워크 경로가 없다.**
4. 내장 워커가 외부 프로토콜로 표현할 수 없는 엔진 메서드를 쓴다.
5. 클라이언트 발송 비용 일부가 엔진 경로에 붙어 있다.
6. 핫패스에 무거운 처리가 남아 있다.

목표 구조:

```text
일반 클라이언트들 ──► 프록시 서버(프로토콜별 바이너리, JSON 설정) ──┐
                                                               ├──► 이벤트 서버 (종합 API, 단일 작성자)
                      워커 서버(여러 워커풀, 작업 실행기) ─────┘
                      내장 워커 = 같은 API를 함수로 호출
```

이 문서는 **보장 계약**(5장)을 먼저 고정하고, 그 계약을 만족하는 설계(6장)와 반례가 실패하는 검증 계획(8장)을
제시한다.

## 2. 사용자가 정한 것 (원문)

판정 기준은 이 원문이다. 설계는 이것을 구현하는 방법이며, 원문과 충돌하면 원문이 이긴다.

**고가용성과 워커**

> 모든 워커는 재빨리 워커풀로 돌아와야해. 따라서 장기실행을 이벤트용 워커가 들고 있을 수는 없어.
> 꼭 프로세스를 만들지는 않아도 괜찮아. 단지 이벤트용 워커풀이 처리할 수는 없다는거지.

> 이벤트서버의 고가용성이 깨진다.

> 고가용성이 젤 중요한 이유는 이것만 확보되면 대부분의 로직은 전부 이벤트 발급을 많이 하는것으로 해결되기 때문이다.

> 아까 APIBOND시나리오에서 실제 API가 실패를 보고하는 것조차 실패이벤트를 등록해버리면 되기 때문이다

**착수 기한**

> 착수이벤트의 타임아웃은 일반적으로 스케줄러가 필요없어.
> 활성화된 이벤트서버는 지속적으로 이벤트가 수신되기 때문에 이벤트 등록시점에 착수이벤트 중 시간이 초과된것을 일괄 미착수 상태로 돌리기만 하면 되기 때문이야. 단 이 때 이벤트 고유번호를 업데이트한다.
> 그러면 타임아웃 이후에 워커가 완료보고해도 그 이벤트 번호에 해당되는 이벤트는 존재하지 않기 때문에 무시하면 된다.

**구현 태도**

> 매우 섬세하게 사이사이 사소한 로직도 귀찮다고 가장 안전하고 무거운 구현을 하면 안된다.
> 내가 바라는 이벤트 서버는 엄청 고가용성을 원하고 있어

> 이벤트의 불변성도 그렇게 중요하지 않아. 논리적으로 동시성에서 안전하기만 하면 된다.

**역할과 배치**

> 근데 말야..아주 엄밀하게 워커서버란 존재하지 않아. 왜냐면 이벤트 서버입장에서는 딱히 클라이언트와 워커서버를 구분할 이유가 없단말이지.
> 그저 메소드로 이벤트 등록, 채널 수신, 이벤트착수, 이벤트 완료 라는 기능을 제공해줄 뿐이고 다 자기에게 달라붙은 클라이언트일뿐이야. 인프로세스 워커조차 메소드로 호출하고 통신층을 안거칠 뿐인거지

> 이벤트 서버는 초 고가용성이라서 성능이 엄청나게 좋을텐데 그저 소켓연결이 많아지는 것으로 금방 한계에 봉착할거잖아

> 단지 프록시 서버는 있을 수 있고 이벤트서버와 프록시 서버간 전용 프로토콜도 있을 수는 있어
> 프록시서버가 존재하면 다수의 클라이언트를 프록시가 받아내고 상대적으로 이벤트서버는 프록시서버만 클라이언트로 접대하면 되기 때문에 손쉽게 스케일 아웃이 된다.

> 내가 그리는 그림은 일반 클라이언트는 프록시에 붙고 이벤트서버는 프록시서버와 워커서버와는 직접 연결된 상태로 보는거지

> 프록시 서버는 논리를 따져보면 커스터마이즈 되지 않는다. 그저 중계만 하니까.
> 단지 프록시 서버에는 종류가 있는거야. 통신 프로토콜별로.

> 이벤트 서버 자체는 여러 프로토콜을 받아줄 수 있다. 프록시 서버는 프로토콜별로 확정 구현으로 존재한다. 프록시서버는 바이너리로 배포되며 프록시서버용 설정은 JSON으로 한다.
> 이벤트서버는 종합적인 API를 제공하며 딱히 워커인지 프록시인지 클라이언트인지 관심없다.
> 내장 워커를 운영할 수 있지만 내장 워커 역시 완전히 동일한 API를 함수로 호출한다는 점만 다르다. 딱히 외부에 구현된 클라이언트와 다른 로직으로 구현되지는 않는다

> 난 워커풀도 서버이길 원해.
> 하나의 워커서버가 다수의 워커풀을 소유하고 이벤트서버와는 그냥 소켓통신하면 된다고 보고 있어

> 물론 인프로세스 워커도 만들 수 있겠지 규모가 작은 경우
> 하지만 무겁거나 어려운 작업을 하는 경우 워커서버를 다수 두는게 훨씬 유리해지겠지

**프레임워크**

> 프레임웍은 이런 역할별 서버 등을 안정적이고 쉽게 훅 혹은 스프링의 컨트롤러 같은것만 구현하면 될 수 있게 단순화하고 제어를 역전시켜 프레임웍이 관제하게 한다.

**앞선 세션에서 확정된 원칙 (유지)**

> 변하지 않는 원칙중에 하나는 이벤트는 반드시 하나의 워커가 가져간다는것이다. 혹은 발송되거나. 만약 둘이상의 워커나 프로세스에 할당되어야하면 이벤트 자체를 여러개 발급해야해.

> 특히 mq의 락을 효과적으로 관리하는 구조로 pg를 배제하는 건으로 확정짓겠어. 하지만 인메모리만으로 운영되면 안된다.

## 4. 목표 구조

### 4.1 이벤트 서버

* 종합 API 하나(6.3). 상대가 누구인지 묻지 않는다. 권한은 접속의 서비스 자격과 위임 신원으로 판정한다(6.9).
* 사용자 코드를 돌리지 않는다. 등록·착수 표시·완료 반영·회수·발송 깨우기·저널 기록만 한다. `Events::Custom`은 서버 모드에서 선언적 규칙(채널 접두어)으로 대체한다(D10).
* 여러 프로토콜로 직접 받을 수 있고, 프레임 형식을 프록시와 공유한다. 직접 접속하는 쪽도 서비스 자격이 필요하다. 최종 사용자는 프록시를 거친다.
* 단일 작성자. 큐 경합은 잠금이 아니라 소유로 중재한다.

### 4.2 접속자

* 프록시, 워커 서버, 내장 워커 모두 종합 API의 클라이언트다.
* 종합 API는 계약(trait) 하나, 구현 둘이다. 로컬 구현은 엔진에 연산을 직접 보내고, 원격 구현은 소켓으로 보낸다.
* 워커 프레임워크(`App`, `Service`, 작업 실행기)는 계약만 본다. 내장과 외부가 같은 코드다. 착수 맥락에서 나오는 쓰기는 반드시 번호가 붙은 경로(`complete`, `register_in`)로 보낸다(G2).

### 4.3 프록시 서버

* 프로토콜별 완성품 바이너리(WebSocket, HTTP SSE·롱폴링, 이후 WebRTC·gRPC), JSON 설정.
* 사용자 로직 없음. 프로토콜을 종합 API로 옮기고, 같은 채널의 사용자 구독을 상위 구독 하나로 모은다.
* 일반 사용자가 모두 프록시를 거치고 프록시가 상위 연결을 다중화하면, 이벤트 서버의 연결 수는 "프록시 수 + 워커 서버 수"다. 사용자별 고유 채널이 많으면 관심 채널 수를 별도로 측정한다.

### 4.4 워커 서버

* 여러 워커풀과 작업 실행기를 가진 클라이언트 프로세스. 이벤트 서버에 직접 연결한다.
* 배치는 풀 단위로 정한다. 가벼운 풀은 내장, 무거운 풀은 워커 서버 여러 대.

## 5. 보장 계약

설계보다 먼저 고정한다. 각 단계의 인수 테스트는 이 계약을 판정한다.

| # | 보장 | 범위 |
| --- | --- | --- |
| G1 | 각 순간, 레코드 하나를 엔진이 인정하는 착수자는 **최대 하나** | 항상 |
| G2 | 착수 번호가 붙은 쓰기(완료, 실패, 연장, 중간 등록)는 그 번호가 현재 효력이 있을 때만 반영되고, 그 쓰기가 만든 자식도 함께 반영되거나 함께 버려진다. **거절은 "이 쓰기는 효력이 없다"는 뜻일 뿐, 레코드가 완료됐다는 뜻이 아니다** | 번호가 붙은 쓰기 |
| G3 | 외부 효과(외부 API 호출, 과금, 프로세스 실행)의 중복은 막지 않는다. 회수 뒤 새 착수자가 같은 일을 다시 할 수 있다. 프레임워크는 재시도 사이에 **안정된 작업 키**를 핸들러에 주고, 수신 측이 그 키로 중복을 막는다 | 계약 (at-least-once) |
| G4 | 미처리 일, 시도 횟수, 지연의 재개 시각, 자식, dead letter, 라우팅 변경은 저널 내구화 지점을 기준으로 재시작을 넘는다. `Scheduled`는 마지막 완료 쓰기 이후의 변화를 잃을 수 있고, `Strict`와 `flush`는 응답 전에 디스크에 닿는다 | 저널 정책 |
| G5 | 인계에 성공한 일은 **레코드로 존재**한다. 넘긴 워커가 죽어도 책임이 사라지지 않는다. 단 `Scheduled`에서 이벤트 서버까지 죽으면 마지막 내구화 지점으로 돌아갈 수 있다(G4). 휘발로 선언한 작업은 제외 | 6.6 |
| G6 | 이벤트 서버는 어떤 접속의 소켓 송신도 기다리지 않는다. 보존 한도를 넘게 뒤처진 접속은 **통신이 이어지는 대로** `gap`을 받는다(새 이벤트가 없어도) | 6.7 |
| G7 | 한 등록은 하나의 판정을 받는다: 신규 / 진행 중 중복 / 완료 결과 / 충돌. 판정마다 응답과 채널 효과가 정해져 있다 | 6.5 |

## 6. 상세 설계

### 6.1 식별자와 소유자

| 식별자 | 무엇 | 범위 · 수명 |
| --- | --- | --- |
| 명령 키 | `(이름공간, transaction_key)`. 같은 일의 정체, 중복 판정 단위 | 이름공간은 등록 주체(서비스 또는 검증된 위임 사용자). 재접속·프록시 교체에도 안정. 완료 창이 지나면 재사용은 새 일 |
| 이벤트 id | 개별 사실·진행의 정체. 같은 명령에서 여러 사실이 나와도 각자 다르다 | 로그 보존 동안 중복 제거 |
| 자식 id | `(원인 이벤트 id, 대상 큐)`에서 유도(현행 `EventId::reaction`) | 안 바뀜 |
| 재통지 id | `(이름공간, 명령 키, 응답 채널)`에서 유도 | 6.5 |
| 착수 번호 | 이 착수의 효력 | 착수할 때마다 새로. 아래 소유자에 묶임 |
| 완료 요청 id | `complete` 호출 하나의 정체(재시도해도 같음) | 완료 기록과 함께 창 동안 보관 |

**소유자** = `(접속 인스턴스·세대, 착수 번호, 위임 주체)`. 위임 착수가 아니면 위임 주체는 비어 있다.

* 부모와 작업은 번호가 다르다. 이벤트 워커 W가 번호 `n₁`으로 인계하고, 실행기 E가 작업을 착수해 `n₂`를 받는다. 작업의 모든 쓰기는 `n₂`로 한다.
* 재접속한 접속은 새 세대다. 옛 번호로 이어 쓸 수 없고 새로 착수해야 한다.
* 위임 착수의 후속 쓰기는 착수 당시의 위임 주체를 다시 확인한다. 그 사용자가 로그아웃하거나 인증이 만료되면 그 사용자의 착수는 회수된다.
* 착수 번호를 비밀 난수로 만들지 않는다. 서비스 인증이 있는 접속에 묶으므로, 다른 접속이 같은 번호를 내밀어도 거절된다.

### 6.2 레코드와 전이표

큐 메시지와 실행 기록을 레코드 하나로 합친다. 단일 작성자가 소유하므로 제자리에서 바꿔도 동시성에서 안전하다.

| 현재 상태 | 사건 | 다음 상태 | 시도 횟수 | 효과 |
| --- | --- | --- | --- | --- |
| (없음) | 등록(신규) | 대기 | 0 | 리액션 자식은 원인 사실의 등록 스텝에서 생성 |
| 대기 | 착수 승인 | 착수(소유자, 기한 t) | +1 | 횟수가 상한이면 착수 대신 최종 실패(사유: 소진) + dead letter |
| 착수 | 완료(현재 번호) | 완료 기록 | — | 같이 보낸 이벤트·자식을 같은 스텝에 등록(전부 또는 전무, 6.6) |
| 착수 | 실패-재시도(현재 번호) | 지연(재개 시각) | — | 지연도 **활성**으로 취급 |
| 착수 | 실패-최종(현재 번호) | 완료 기록(실패) | — | 실패 결과 이벤트 등록 |
| 착수 | 기한 지남 / 소유자 무효(끊김·로그아웃) | 대기 | — | 번호 무효 |
| 착수 | 연장(현재 번호, 기한 전) | 착수(기한 t') | — | 번호 유지 |
| 지연 | 재개 시각 지남 | 대기 | — | |
| 완료 기록 | 창 지남(다음 완료 때) | 제거 | — | |

* **시도 횟수 = 서버가 승인한 착수 횟수.** 기한 지남과 끊김도 착수 때 이미 세어져 있으므로 회수가 무한히 순환하지 않는다.
* 끊김만으로 정상 작업을 영구 실패시킬 수 없는 큐는 큐별 정책으로 "핸들러가 보고한 실패와 기한 지남만 센다"를 고를 수 있다(Q7).
* 상한 소진은 **최종 실패(사유: 소진) + dead letter**를 한 전이로 만든다(현행과 같다). 등록자는 실패 결과 이벤트로 끝을 안다.
* 착수 때 명령 이벤트를 로그에 복사하지 않는다(Q4).

### 6.3 종합 API

| 메서드 | 내용 |
| --- | --- |
| `register(events) → [판정]` | 등록. 큐 대상이면 레코드 생성, 채널 대상이면 로그 기록. 이벤트마다 판정(6.5) |
| `receive(channels, from)` | 채널 스트림. 보존 한도를 넘게 뒤처지면 이벤트가 없어도 `gap(p)`를 보낸다 |
| `read(channel, after, limit)` | 범위 읽기. 권한 확인, **클라이언트 대상 이벤트만**(현행 `read_stream`과 다름) |
| `claim(queue, credit, wait, lease)` | 대기 레코드를 최대 `credit`개 착수해 보낸다. `wait`는 빈 큐에서 기다릴 시간, `lease`는 착수 유효기간 |
| `complete(n, request_id, outcome, events) → 판정` | 아래 판정 중 하나를 돌려준다 |
| `extend(n, lease)` | 기한 연장. 번호가 현재이고 기한 전일 때만 |
| `register_in(n, events)` | 착수 맥락의 중간 등록(사실, 진행). 번호가 현재일 때만. 자식도 같은 판정을 따른다 |
| `interest(set)` / `interest(add, remove)` | 관심 채널. 새 상위 접속은 **전체 집합과 시작 커서**를 먼저 보내고, 이후 증분만 보낸다 |
| `reactions(owner, generation, set)` | 소유 서비스의 리액션 갱신. 세대가 현재보다 낮으면 거절(6.8) |
| `flush()` | 지금까지의 변화가 디스크에 닿으면 응답 |

`complete`의 판정:

| 판정 | 뜻 |
| --- | --- |
| 반영됨 | 이번 요청으로 반영됐다 |
| 이미 반영됨 | 같은 `request_id`가 이미 반영됐다(응답 유실 뒤 재시도). 완료 기록이 창 안에 있을 때만 확인 가능 |
| 효력 없음 | 번호가 현재가 아니다(만료·회수·다른 소유자). **레코드는 완료되지 않았을 수 있다** |
| 확인 불가 | 완료 기록이 창 밖이라 이전 반영 여부를 알 수 없다 |
| 자식 거절 | 필수 자식이 충돌·권한 거절·포화로 실패해 **아무것도 바뀌지 않았다**(6.6) |

모든 메서드는 배치를 받는다. 원격 프레임에는 요청 번호와(프록시의 경우) 위임 신원이 붙는다.

### 6.4 착수 기한과 회수

* **경계:** 서버 시각 기준 `now >= deadline`이면 지난 것이다.
* **일괄 회수 시점(Q3):** 기본안은 **등록 배치와 착수 요청 배치**에서 기한 힙의 맨 앞만 보고 지난 것을 대기로 되돌린다. 등록은 원문 그대로이고, 착수 요청은 일감을 찾는 순간이라 회수할 것이 있으면 바로 쓰기 위해서다. 완료·연장 같은 다른 연산에서는 일괄 회수를 하지 않는다. 지난 것이 없으면 비용은 비교 한 번이다.
* **대상 한 건 검사:** 번호가 붙은 쓰기(`complete`·`extend`·`register_in`)는 일괄 회수와 별개로 **그 레코드의 기한**을 직접 확인한다. 회수가 아직 안 돌았어도 지난 기한의 쓰기는 효력이 없다.
* **오래된 힙 항목:** 힙 항목은 `(기한, 레코드, 번호)`다. 꺼낼 때 레코드의 **현재 상태·번호·기한이 모두 일치**할 때만 적용한다. 연장된 착수는 기한이 달라 옛 항목에 회수되지 않는다. 오래된 항목 비율이 커지면 힙을 재구성한다(상한은 P2 측정으로 정함).
* **소유자 무효:** 접속 인스턴스마다 세대를 둔다. 끊김·로그아웃 처리는 레코드의 소유자가 일치할 때만 적용한다. 재접속한 같은 신원의 새 접속은 다른 세대이므로, 옛 접속의 늦은 종료 통지가 새 착수를 풀지 못한다.
* **반개방 연결:** 끊김을 관측하지 못하는 연결은 기한이 맡는다.
* **감독자 제한시간 < 착수 기한:** 작업 감독자의 제한시간은 착수 기한보다 짧게 둔다. 감독자가 실패를 보고할 때 이미 기한이 지났다면 그 보고는 효력 없음이고, 레코드는 이미 회수된 상태다.

### 6.5 등록 시점 판정 계약

| 같은 명령 키의 기존 상태 | 판정 | 등록자에게 | 채널 효과 |
| --- | --- | --- | --- |
| 없음 | 신규 | 신규 | 큐 대상: 레코드 생성. 채널 대상: 로그 기록 |
| 대기 · 착수 · 지연 | 진행 중 중복 | 진행 중(원래 이벤트 id) | 없음. 결과는 원래 요청의 응답 채널에만 간다(이벤트 하나 = 답 하나) |
| 완료 기록(창 안, 성공·실패·소진 포함) | 완료 결과 | 저장된 결과를 응답에 담아 돌려줌 | 재통지 id가 그 채널의 보존 로그에 없으면 결과 이벤트를 하나 추가, 있으면 추가하지 않음 |
| 같은 키, `action` 또는 내용이 다름 | 충돌 | 충돌 | 등록자 응답 채널에 충돌 이벤트 |

* 충돌 검사를 **먼저** 한다. 비교 대상은 `action`과 내용 식별값이다.
* 내용 식별값은 같은 키가 있을 때만 새 내용을 해시해 비교한다. 완료 기록에는 완료 때 한 번 계산한 식별값만 남기고 원본 payload는 남기지 않는다.
* 완료 기록이 남기는 것: action, 내용 식별값, 결과, 완료 시각, 반영된 완료 요청 id.
* 이름공간이 다르면 같은 `transaction_key`도 다른 일이다. 결과·재통지 id에 이름공간이 들어가므로 같은 공유 채널에서 서로 가리지 않는다.
* 현행과 달라지는 점: 지금은 두 번째 요청의 `begin` 시점에 판정해 완료 전후 순서에 따라 응답이 달라진다. 제안은 등록 순간 확정된다. 의도된 변경이며 인수 테스트로 고정한다.

### 6.6 작업 인계

장기 작업을 이벤트 워커풀에서 떼어 내되, 그 책임은 레코드로 남긴다.

1. 핸들러는 `complete(n₁, 인계, [작업 요청])`을 보낸다. 작업 요청은 고정 id를 가진 **필수 자식**이다.
2. **전부 또는 전무.** 작업 요청이 신규로 생기거나 같은 id·내용의 요청이 이미 책임을 지고 있으면, 부모 완료와 함께 반영된다. 작업 요청이 충돌·권한 거절·포화로 실패하면 **부모도 바뀌지 않고** `자식 거절`을 돌려준다. 파일 모드에서는 두 변화가 같은 저널 반영 단위에 실린다.
3. `자식 거절`을 받은 프레임워크는 부모를 지연(재시도)으로 반납해 이벤트 워커 허가를 즉시 푼다. 허가를 쥔 채 자리를 기다리지 않는다.
4. 작업 실행기는 이벤트 워커와 다른 예산으로 작업 큐를 `claim`한다(긴 `lease`, 필요하면 `extend`). 작업의 모든 쓰기는 작업 번호 `n₂`로 한다.
5. 작업은 `register_in(n₂, …)`으로 진행·사실을, `complete(n₂, …)`로 최종 성공·실패를 등록한다. **실패도 이벤트다.**
6. 실행기가 죽으면 그 착수는 끊김 또는 기한으로 회수되어 다른 실행기가 이어받거나, 상한에서 소진 실패가 된다(G5).
7. 작업이 침묵(감독자 제한시간 초과)하거나 panic하면 감독자가 `n₂`로 실패를 보고한다. 감독자도 죽었으면 6번이 맡는다.
8. 결과 응답이 유실되면 같은 `request_id`로 재시도한다. `이미 반영됨`이면 끝, `효력 없음`이면 레코드가 회수된 것이므로 더 할 일이 없다(다른 착수자의 몫).
9. 원래 명령의 결과는 "인계됨"이고, 작업의 최종 결과는 작업 레코드의 결과다.
10. 복구가 필요 없는 작업은 **휘발 작업**으로 선언한다(Q6). 작업 요청은 transient 큐로 가고 저널에 쓰지 않는다.
11. 취소는 작업 id를 대상으로 하며, 권한은 원래 명령의 등록 주체에게 있다.

**포화:** 작업 큐에는 수·바이트 상한을 둔다(큐 설정). 상한에서 작업 요청은 `포화`로 거절되고 2·3번이 적용된다. 대기가 이벤트 서버 메모리에 무한히 쌓이지 않는다.

작업 시작을 따로 저널에 쓰지 않는다. 작업 요청 레코드가 곧 "남은 일"이고, 순변화 저널은 창 안에서 끝난 작업을 쓰지 않는다. 새 프로세스도, 별도 시작 기록도, 매번의 동기 쓰기도 필요 없다.

### 6.7 발송

* 한 배치의 로그 반영·보존 정리와, 깨울 대상 확보를 **같은 쓰기 임계구역**에서 끝낸다. 채널당 배치당 한 번만 확보하고, `notify_one`은 잠금을 놓은 뒤 한다. 독자는 깬 뒤 자기 커서부터 다시 읽는다. 구독자 등록과 시작 커서는 지금처럼 같은 잠금에서 정한다.
* **`gap(p)`의 뜻:** 위치 `p` 이하의 일부 이벤트를 더 이상 받을 수 없다. `gap`은 이벤트가 없어도 단독으로 전달된다(현행 `next()`가 이벤트를 기다리기만 하는 문제를 고친다). 클라이언트는 자기 근원에서 재구성한 뒤 `p` 다음부터 읽는다. `Gateway::poll`도 `lagged`를 반환한다.
* **프록시:** 사용자별 마지막 전달 위치를 들고, 상위 구독과 백필(`read`)의 경계 위치를 정해 겹쳐도 한 번만 전달한다. 새 상위 접속은 전체 관심 집합과 시작 커서를 먼저 복원한다. 사용자별 송신량 상한을 두고, 넘긴 사용자는 그 사용자에게만 `gap`을 준다.
* "바뀐 큐만" 처리할 때 바뀜의 원인은 모두 포함한다: 새 대기자, 레코드 도착, 반납, 회수, 지연 재개, 대기자 기한.

### 6.8 리액션 표

* 이벤트 서버의 설정이다. `reactions(owner, generation, set)`은 소유 서비스 범위만 교체하고, 세대가 현재보다 낮으면 거절한다. 같은 서비스의 롤링 배포에서 재접속한 옛 인스턴스가 새 설정을 덮지 못한다.
* 워커 프레임워크는 재접속할 때마다 표를 쓰지 않는다. 설정 세대가 바뀔 때만 보낸다.
* 변경은 저널에 남고(G4), 이미 발급된 자식은 발급 당시의 대상을 유지한다.
* 리액션 변경 권한은 서비스 자격으로 제한한다(6.9).

### 6.9 인증·권한 (Q1)

* 이벤트 서버는 서비스 자격을 가진 접속만 받는다.
* 서비스 자격마다 허용 범위를 둔다: 등록 가능한 action·큐·응답 채널, 수신·읽기 가능한 채널, 착수 가능한 큐, 위임 호출 가능 여부, 리액션 변경 범위. 배치의 각 항목, 재통지 목적 채널, 위임 착수의 후속 쓰기, 로컬 호출에 같은 검사를 적용한다.
* 최종 사용자 인증 — Q1(a) 제안:
  1. 프록시가 사용자 세션마다 인증 요청 id를 만들어, 사용자 자격을 담은 요청을 **전용 큐**에 등록한다. 이 큐는 로그·팬아웃·dead letter 보존이 없다(소진되면 보존하지 않고 버린다).
  2. **인증 결과 등록 권한을 가진 서비스만** 그 큐를 착수하고 결과를 등록할 수 있다.
  3. 결과는 인증 요청 id, 검증된 사용자, 사용자 세션, 대상 프록시 접속 세대, 유효기간, 허용 범위에 묶인다. 이벤트 서버는 이 결과로 위임 신원의 `principal`과 범위를 정하고, 프록시가 프레임에 붙인 신원을 이 결과와 대조한다.
  4. 프록시는 같은 범위를 사용자별로 집행한다. 상위 구독을 공유해도 권한이 다르면 사용자별 발송 단계에서 거른다.
  5. 재접속 뒤 도착한 옛 결과는 세대가 달라 무효다. 로그아웃·만료는 그 사용자의 위임 착수를 회수한다(6.1).
* 대안: (b) 이벤트 서버의 선언적 규칙, (c) 프록시 JSON의 정적 토큰. 배치가 이것으로 충분하면 전용 큐와 인증 서비스를 들일 이유가 없다.

### 6.11 장애 표면화 (D8)

* `Started`에 엔진 정지를 폴링 없이 기다리는 future를 둔다. `App::run`은 Ctrl-C 또는 엔진 정지 중 먼저 온 것으로 끝나고, 정지라면 원인을 오류로 돌려준다.
* `Started::shutdown`은 엔진 종료 오류를 전파한다.
* 원격 접속자는 사유 프레임 없이 EOF만 받아도 끊김을 안다.

### 6.12 저널 v2: 복구 동치

| 복구 대상 | 재생 후 |
| --- | --- |
| 대기 · 착수 레코드 | **모두 대기.** 소유자와 번호는 무효 |
| 지연 레코드 | **지연 유지.** 재개 시각을 레코드에 함께 기록하고, 재시작 시 이미 지난 것만 대기로(백오프는 최소 대기시간 계약) |
| 시도 횟수 | 유지(내구화된 값). 재시작 자체는 횟수를 더하지 않는다 |
| 자식(리액션) | 원인과 같은 스텝에 기록된 그대로. 재생에서 다시 생성하지 않음 |
| 리액션 변경(세대 포함) · dead letter | 유지 |
| 완료 기록 | 정책(`Persist::settled`)에 따라 |
| 이벤트 | 정책(채널 규칙)에 따라 |

* **비교할 외부 관측:** 같은 내구화 지점에서 (a) 순변화 재생, (b) 압축본 재생, (c) 실제 재시작에 **같은 질의**를 넣는다. 미처리 일의 `claim` 결과(순서 포함), 같은 키 재등록의 판정, 같은 커서의 `read`/`receive` 결과와 `gap`.
* **허용하는 차이:** 메모리 보존선 이하에 있던, 저널 정책상 기록된 이벤트는 재시작 뒤 다시 보일 수 있다. 그 구간의 `read`는 이벤트를 주거나 `gap`을 준다. 보존선 위의 관측은 같아야 한다.
* 포함할 경계: 쓰기 중 추가 변경, 빈 순변화의 `flush`, 압축 직후 append, 종료 시 압축, 같은 키의 삭제·재생성(옛 삭제가 새 등록 뒤에 적히면 안 됨), 부모 완료와 자식 등록이 한 스텝인 경우, 소진 직후.
* 순변화 기록, 쓰기 비중첩, 사슬, 압축 규칙과 `Scheduled`/`Strict`/`flush` 경계는 유지한다.
* 형식 버전을 2로 올린다. v1 고정본은 보관하고, v2는 v1 파일을 `InvalidData`로 거부하면서 바이트를 보존하는지 확인한다(Q5).
